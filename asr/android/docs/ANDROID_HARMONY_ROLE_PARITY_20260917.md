# Android 角色结果与鸿蒙对齐

本轮修复两个已证实的问题，保留原始身份精度边界。修复前源码为 `88a35fb1`；当前交付分支上的修复须在回流主线后才能关闭主线跟踪项。

## 根因和行为变化

1. Android `DingqiaoRecognitionEngine.resultPayload` 用截断将浮点秒转为毫秒，角色会话及鸿蒙则四舍五入。原双人录音中同一尾 token 为 15220 ms，公开句尾却是 15219 ms，形成负时长尾字并绕过既有零时长补全。统一公开时间换算后，保留原 token 和声学时间线，允许现有有界、显式标记的句尾补全正常执行。公开 beginTime/endTime 最多有 1 ms 舍入差异；调用方无需修改接口，不应将毫秒值与旧版截断结果逐字节比较。
2. 两端 SDK 的角色切段/UNKNOWN 补全规则一致，但 Android Demo 把每个角色片段当成独立段落；鸿蒙按 sourceUtteranceId 展示完整原句并保留角色详情。Android 现在采用同一展示语义，混合主角色显示“多位说话人”，部分 UNKNOWN 显示“部分待确认”，推断与重叠分别明示，原片段可在“查看角色详情”检查。不会给混合原句强行指定一个人物。

## 对照与不变量

- 保存的原始失败：15 个 ASR 原句、339 字，SDK 角色输出 23 段，包含“说两 / 句”“跟 / 谁”和负时长尾字。SDK 与原 Demo 输出一致证明了片段来源，不能据此认为显示方式符合鸿蒙。
- 时间回归先捕获 15219/15220 不一致，再验证原句文字、原始 speakerTurns、真实短换人、唯一结束标记与空 token 的公共时间语义；同一状态的鸿蒙实现作为契约对照。
- 真机 UI 回归先捕获“随便说两句你好”断开，再验证完整原句、混合/未知/重叠/推断标签和已发布窗口不再被迟到更新修改。
- 最终真机验收须绑定新构建，使用相同的 89.16 秒双人录音、159.30 秒客户会议和必要生命周期用例。旧包证据只作为失败基线，不能冒充新包验收。

## 明确范围

按原句展示是可读性修复，不是声学身份精度修复。“说两”处前后为不同已知角色，“跟”所在原句存在已知重叠；本轮没有放宽两端共有的保守补全规则，没有按多数人吞掉 UNKNOWN 或重叠。短插话误认、争议区间、轻声过滤与 Android 后台/锁屏问题继续独立记录，不由此宣布已解决。原双人及客户原音的 MOSS 辅助标注复用 `delivery/harmony-dingqiao/docs/DIARIZATION_UNKNOWN_REASONS_20260917.md` 与 `CUSTOMER_MEETING_MOSS_AUDIT_20260917.md` 中的范围，不将其升级为人工真值。
