# 端侧目标说话人 ASR：调研、方案与实测报告

本文记录我们在 amphion-runtime（基于 sherpa-onnx 的端侧语音识别运行时）上，为"只识别某一个指定说话人"这一需求所做的完整工作：从需求澄清、业界调研、方案选型，到在 6555 条测试音频上的实测验证。

读者不需要预先了解语音识别领域的术语，关键概念会在用到时解释。如果你只想看结论，直接读下面的 TL;DR 和第五、六章。

配套落地代码在 [asr/tools/speaker/](../../../asr/tools/speaker/)，工程化方案定稿在 [docs/speaker/PIPELINE.md](../../../docs/speaker/PIPELINE.md)，本文是它们背后的"为什么"。

---

## TL;DR（先看结论）

1. 需求方向可行，但要先破除一个误解：业务自有的流式 ASR 模型可以直接对整段音频做推理，不需要在内存里再塞第二个非流式模型。
2. 在端侧、支持"注册一段音频"、实时、且能处理多人重叠这四个约束同时成立的前提下，业界没有现成可下载的开源方案。我们能落地的唯一路径是用现成组件拼装：语音活动检测 + 声纹验证 + 整段流式识别（下文称"方案 A"）。
3. 实测最重要的一条结论：加上目标说话人这套机制，本质不是用来"把字认得更准"，而是用来"防止机器把别人的话和噪声当成目标记录下来"。它在挡杂音上效果很大（误记率从 54% 降到 4%），代价是会误丢约 10% 目标自己的话。
4. 是否值得用，完全取决于业务更怕"错记别人的话"还是更怕"漏记目标的话"。
5. 性能毫无压力：整条流水线处理 1 秒音频只花 0.05 秒。

## 一、问题背景

### 1.1 业务需求

设备上已经跑着一套流式语音识别（ASR，Automatic Speech Recognition，自动语音识别）。现在来了一个新需求：用户可以先录一段自己的声音作为"注册"，之后系统只把这位注册者说的话转成文字，其他人的声音要忽略掉。

这类任务在学术上叫目标说话人语音识别（TS-ASR，Target-Speaker ASR）。"目标说话人"就是那个被注册、需要被识别的人；其他人统称"干扰说话人"。

### 1.2 先厘清两个常见误解

在做需求时，团队最初有两个判断，调研后发现其中一个站不住脚，必须先纠正，否则后面的方案会走偏。

第一个判断："流式识别做不了目标说话人，所以妥协成——等一句话说完，再把整段音频拿去做识别。"
这个妥协方向本身是合理的（按句处理更容易做说话人判断），但"流式做不了"这个理由只对了一半。

第二个判断："ONNX 模型的输入形状是固定的，没办法用流式模型做整段（非流式）推理，除非内存里再放一个非流式模型。"
这个判断是错的。流式模型的固定形状是针对"一个小数据块（chunk）"的，不是针对整段音频的。所谓"整段推理"，底层就是把整段音频切成连续的小块依次喂进同一个模型、并一直保留中间状态。sherpa-onnx 的在线识别器本来就是这么工作的，完全不需要第二个模型。

这个纠正很重要：它直接省掉了"额外加载一个上百兆模型"的内存开销。代价只有一个——精度上限被锁定在流式模型本身的水平（流式模型因为只能看到有限的未来信息，天然比能看到整句的非流式模型略差一点）。

### 1.3 会反复出现的几个术语

| 术语 | 通俗解释 |
| --- | --- |
| 注册 / enrollment | 用户预先录一段自己的声音，系统据此记住"目标说话人长什么声音" |
| 声纹 embedding | 把一段语音压缩成一串数字向量，同一个人的两段语音向量会很接近，不同人则相差较远 |
| 声纹验证 | 比较两段语音的声纹向量，判断是不是同一个人，常用"余弦相似度"打分 |
| VAD | Voice Activity Detection，语音活动检测，用来判断音频里哪段有人说话、哪段是静音 |
| 流式 / 非流式 ASR | 流式是边说边出字（低延迟，精度略低）；非流式是等整句说完再出字（精度略高，有延迟） |
| 重叠语音 | 两个或更多人同时说话的片段，是所有说话人相关任务里最难处理的情况 |

## 二、调研：业界怎么做，哪些能落地

### 2.1 把目标说话人 ASR 拆成三件事

不管用什么方法，要"只识别目标说话人"，本质上都要完成三个动作：

- F1 判断：判断某一段（或某一帧）音频是不是目标说话人在说话。
- F2 投喂：把目标说话人的音频送进识别模型。
- F3 抑制：在多人重叠的片段里，压制其他人对识别结果的干扰。

不同流派的差别，就在于这三件事各自放在哪一层做。

### 2.2 五个方案家族

| 方案家族 | F1 判断在哪做 | F2 投喂粒度 | F3 抑制重叠的能力 |
| --- | --- | --- | --- |
| A 语音检测 + 声纹验证 + 识别（我们的初步方案） | 整段切出来后做二分类 | 整段要么全送、要么全弃 | 基本没有 |
| B 个性化语音检测 PVAD | 逐帧三分类 | 逐帧筛选 | 有限 |
| C 前端分离 VoiceFilter-Lite | 逐帧生成一个滤波遮罩 | 直接改写识别模型的输入特征 | 在特征层面压制非目标 |
| D 端到端 TS-ASR | 在模型编码器里注入说话人信息 | 模型本身只认目标 | 训练时内建 |
| E 说话人分离 diarization 后整理 | 完整切分出每个人 | 按人归类 | 取决于分离模型 |

### 2.3 按"端侧能不能落地"筛选

理论方案很多，但能在手机这种端侧设备上、用现成开源件直接落地的极少。

| 方案 | 有没有现成端侧开源件 | 有没有真实产品案例 | 能否用 sherpa-onnx 直接实现 |
| --- | --- | --- | --- |
| A 检测 + 验证 + 识别 | 有，sherpa-onnx 自带声纹提取、声纹管理、CAM++ / 3D-Speaker 模型 | 大量声纹 + 识别的演示项目 | 能，零自研算子 |
| B 个性化语音检测 | 只有论文，代码不全 | 谷歌内部使用 | 不能，要自己训练 |
| C 前端分离 | 谷歌只发了模型未开源权重 | 谷歌 Pixel 手机已上线 | 不能，要自训并转换 |
| D 端到端 | 见 2.4 节，权重基本没公开 | 服务器侧有，端侧几乎没有 | 不能，要重训重导出 |
| E 说话人分离 | sherpa-onnx 已支持离线分离 | 多个端侧演示 | 能，但是离线、速度较慢 |

一个值得记住的事实：真正在消费级产品上验证过的端侧目标说话人方案，只有谷歌 Pixel 的 VoiceFilter-Lite（方案 C），但它的预训练权重没有公开，下不到。

### 2.4 端到端方案为什么集体出局

端到端 TS-ASR（方案 D）听起来最优雅——一个模型直接搞定。我们专门核查了它的开源现状，结论是这条路目前走不通：

- CONF-TSASR：论文承诺通过 NVIDIA NeMo 开源，但截至目前 NeMo 仓库、HuggingFace、NGC 模型库里都找不到权重或完整训练代码。等于"要用就得自己从零复现"。
- NVIDIA 的新路线（Multitalker Parakeet，2025）：确实开源了权重，但它走的是"自动分簇"路线，不支持"注册指定某个人"，且模型约 2GB，端侧跑不动。它的"目标说话人"是算法自动编号的 speaker 0/1/2，不是用户注册的那个人。
- BUT-FIT DiCoW 系列：是目前唯一既开源权重、又支持注册的端到端方案，但它基于 Whisper large-v3-turbo，800M+ 参数，端侧不现实。

一句话：端侧 + 现成开源权重 + 支持注册，这三个条件的交集是空集。

### 2.5 处理"多人重叠"的四个流派

由于重叠语音是这个需求里最难啃的部分，我们额外调研了 2024–2026 年工业界处理重叠的真实路径，按"在哪一层压制非目标"分四类：

| 流派 | 压制位置 | 代表方案 |
| --- | --- | --- |
| 前端分离 | 在音频或特征层面做遮罩 | VoiceFilter-Lite、SpEx+、神经波束成形 |
| 模型内部条件 | 在编码器注入说话人信息 | TS-RNNT、Pražák 2025、TS-ASR-AD |
| 多说话人并行解码 | 解码端开多个分支 | SURT、NVIDIA Multitalker Parakeet |
| 多模态 | 借助摄像头唇动等视觉线索 | Apple AV-TSE、AV-Dialog |

把"端侧、实时、支持注册、能解决重叠"四个约束叠在一起去筛这些方案，结果如下：

| 方案 | 端侧 | 实时 | 支持注册 | 解决重叠 | 权重公开 | 产品案例 |
| --- | --- | --- | --- | --- | --- | --- |
| VoiceFilter-Lite（谷歌 Pixel 2020） | 是 | 是 | 是 | 是 | 否 | Pixel 上线 |
| NVIDIA Multitalker Parakeet（2025） | 否 | 是 | 否 | 是 | 是 | 服务器部署 |
| TS-ASR-Whisper / DiCoW（2025） | 否 | 否 | 是 | 是 | 是 | 学术 |
| Pražák 2025（捷克电视台） | 是 | 是 | 是 | 是 | 否 | 电视台部署 |
| 方案 A（我们当前） | 是 | 是 | 是 | 否 | 不需要 | 自部署 |

四个约束全部满足、且有真实生产案例的，只有 VoiceFilter-Lite 和 Pražák 2025 两家，但两家都没有开源权重。

### 2.6 调研小结

调研把可选空间收敛到了一个明确结论：在我们的约束下（sherpa-onnx 端侧、注册制、复用现有 ASR），唯一能零自研落地的就是方案 A。它先天解决不了严重重叠，但能解决"挡掉非目标说话人"这件最核心的事。前端分离、个性化检测等更强的方案，都需要自己准备数据并训练，属于后续演进选项，不在第一版范围。

## 三、方案：我们选了什么

### 3.1 方案 A 总览

方案 A 的全称是"语音活动检测 + 声纹验证 + 整段流式识别"，全部用 sherpa-onnx 现成组件拼装：

- 语音活动检测：silero VAD 模型（约 1.8MB），负责切出有人说话的片段。
- 声纹验证：3D-Speaker eres2net 中文模型（约 38MB），负责判断这段是不是目标说话人。
- 识别：复用业务自有的流式 zipformer 模型，对验证通过的整段做识别。

整套只比原来多了约 40MB 模型，且不引入第二个 ASR。

### 3.2 处理链路

```
输入音频（16k 单声道）
  → silero VAD 切段
  → 太短的片段（< 1.5s）丢弃或并入下一段
  → 在片段内用滑动窗口多次提取声纹，与注册声纹算余弦相似度，取最高分
  → 双阈值判定：高于上阈值 → 接受（送识别）；低于下阈值 → 拒绝；中间 → 低置信，交业务决定
  → 接受的片段用流式 zipformer 做整段识别，输出文字
```

完整可运行实现见 [asr/tools/speaker/ts_asr/core.py](../../../asr/tools/speaker/ts_asr/core.py)。

### 3.3 五个加固点（对应五类风险）

调研阶段定位出方案 A 的五类失败原因，每一类都对应一个工程加固点。这五点是方案能不能用的关键，全部内置在代码里：

| 加固点 | 做法 | 针对的风险 | 风险的量化依据 |
| --- | --- | --- | --- |
| 多模板注册 | 注册至少 3 段、每段 5-10 秒、覆盖不同语速和距离，取平均声纹 | 短音频不稳、换环境就失效 | 跨设备 / 距离场景声纹错误率会翻倍 |
| 最短片段门限 | 短于 1.5 秒的片段不做说话人判断 | 片段太短时声纹极不稳定 | 1 秒片段的错误率是 3 秒的约 3 倍 |
| 滑窗多次打分 | 长片段按窗口多次打分取最高，而非整段只打一次 | 重叠片段会把声纹拉偏 | 重叠会让声纹漂向"两人混合中心" |
| 双阈值 | 高、低两个阈值，中间设缓冲区 | 单一默认阈值在不同场景不可靠 | 默认阈值在跨域时误差不可控 |
| 整段流式识别 | 复用现有流式模型整段推理 | 避免再加一个非流式模型 | 见 3.4 节 |

这里的几个数字（1.5 秒门限、3 倍退化、阈值取值）都不是拍脑袋，而是来自调研到的公开基准，例如 VoxCeleb1 上短音频的声纹错误率：3 秒时 6.64%、2 秒时 8.93%、1 秒时 20.41%。

### 3.4 一个反直觉的关键点：流式模型可以整段推理

第 1.2 节提到的纠正，落到代码上就是下面这段——它用的是已有的流式识别器，把整段音频一次喂进去，末尾补一点静音触发收尾，然后循环解码：

```python
def asr_decode_full_segment(recognizer, samples, sr):
    stream = recognizer.create_stream()
    stream.accept_waveform(sample_rate=sr, waveform=samples)
    tail = np.zeros(int(sr * 0.5), dtype=np.float32)  # 末尾补 0.5s 静音，触发收尾
    stream.accept_waveform(sample_rate=sr, waveform=tail)
    stream.input_finished()
    while recognizer.is_ready(stream):
        recognizer.decode_stream(stream)
    return recognizer.get_result(stream)
```

没有第二个模型，没有额外内存。这就是"流式模型固定的是数据块形状、不是整段形状"这一事实的直接体现。

## 四、实验：怎么验证

### 4.1 测试集

我们用一份专门构造的目标说话人测试集 ts_hw_test 来评测，共 6555 条音频：

| 维度 | 情况 |
| --- | --- |
| 样本构成 | 目标在说话的 6227 条；目标没说话的 328 条（其中纯干扰 164、纯静音/噪声 164） |
| 重叠程度 | 重叠比例 0.1-0.2 占 22%、0.2-0.3 占 16%、0.3-0.5 占 35%、≥0.5 占 22% |
| 片段时长 | 中位数 5.19 秒；短于 1.5 秒的仅占 0.3% |
| 说话人数 | 737 个不同的目标说话人 |
| 噪声类型 | 交通噪声 49%、通用噪声 29%、音乐 19% |

需要强调：这是一份刻意构造的高难度测试集，每条目标语音都强行混入了 1-3 个干扰人和噪声，重叠比例普遍偏高。真实业务里通常没有这么吵，所以下文的绝对错误率会比真实场景偏高，应主要看"加方案前后的相对变化"。

"重叠比例"指目标和别人同时说话的时长占比，0.5 表示有一半时间在被别人盖话。

### 4.2 评测方法

核心思路是对比两种配置在同一批音频上的表现：

- baseline（基线）：不做任何说话人判断，直接把音频送进识别模型出字。这代表"不加目标说话人功能"的现状。
- 方案 A：在识别前加一道声纹验证门控，只有验证通过才采纳识别结果。

实现上有一个省算力的技巧：识别结果对两种配置是同一份，所以每条音频只跑一次识别，baseline 直接用结果，方案 A 则根据声纹分数决定要不要采纳这份结果。这样一次计算同时支撑两条曲线。评测脚本是 [asr/tools/speaker/03_eval.py](../../../asr/tools/speaker/03_eval.py) 和 [04_eval_summary.py](../../../asr/tools/speaker/04_eval_summary.py)。

模型配置：识别用业务自有的流式 zipformer 中英文模型（INT8 量化，训练数据本身带交通和通用噪声，与测试集噪声类型吻合）；声纹用 3D-Speaker eres2net 中文模型；注册采用每条音频自带的单段注册音频（多段平均的加固点留待后续验证）。

### 4.3 指标说明

这是看懂结果的前提，先把每个指标讲清楚。沿用一个场景：会议室里多人说话，我们只想记录"老板（目标说话人）"的话。

| 指标 | 全称 | 通俗含义 | 数值越大越 |
| --- | --- | --- | --- |
| CER | 字错误率 Character Error Rate | 中文识别，100 个字里错了几个（认错、漏字、多字都算错） | 差 |
| WER | 词错误率 Word Error Rate | 英文识别，同上但按单词算 | 差 |
| FAR | 误识率 False Accept Rate | 老板没说话，系统却把别人的话当成老板记下来的比例 | 差 |
| FRR | 漏识率 False Reject Rate | 老板说了话，系统却没认出来、把它丢掉的比例 | 差 |
| EER | 等错误率 Equal Error Rate | 调到误识率和漏识率正好相等的那个点，用一个数概括声纹整体水平 | 差 |
| 阈值 | threshold | 声纹相似度的及格线，卡得越高越严（越倾向于宁可错杀） | 看场景 |
| RTF | 实时率 Real-Time Factor | 处理 1 秒音频要花几秒，小于 1 就是比实时快 | 差 |

两个要点：

第一，误识率（FAR）和漏识率（FRR）是一对此消彼长的跷跷板。声纹门槛卡得越严，错记别人的越少（FAR 降），但漏掉老板的越多（FRR 升）。选阈值就是在这对矛盾里找平衡。

第二，测试集分两类样本，看的指标不同。目标在说话的样本看 CER/WER（识别得准不准）和 FRR（有没有被漏掉）；目标没说话的样本看 FAR（有没有被误记）。

## 五、结果：数据说了什么

### 5.1 核心对比

下表是全量 6555 条的总体结果，@0.25 / @0.40 / @0.55 表示方案 A 在不同声纹阈值下的表现：

| 指标 | baseline 不门控 | 方案 A @0.25 | 方案 A @0.40 | 方案 A @0.55 |
| --- | --- | --- | --- | --- |
| 中文字错误率 CER（目标在说话，3975 条） | 25.68% | 27.81% | 33.54% | 51.69% |
| 英文词错误率 WER（目标在说话，2252 条） | 24.09% | 26.99% | 33.87% | 60.24% |
| 误识率 FAR（目标没说话，328 条） | 54.27% | 8.23% | 0.91% | 0.30% |
| 漏识率 FRR（目标在说话） | 0% | 6.70% | 20.99% | 52.71% |

### 5.2 发现一：挡杂音效果显著（核心价值）

目标没说话时，基线识别模型有 54.27% 的概率凭空"脑补"出文字（这类没人说话却冒出来的文字，俗称鬼影）。加上声纹门控后，这个误记率在阈值 0.25 时降到 8.23%，0.40 时降到 0.91%，相对消除了 85% 到 98%。

这是方案 A 最实打实的收益，也是它真正的存在意义：防止系统把别人的话和噪声当成目标记录下来。

### 5.3 发现二：目标自己的话反而略降（代价）

只看"目标确实在说话"的样本，加了方案 A 之后中文字错误率从 25.68% 升到 27.81%（阈值 0.25）甚至 33.54%（阈值 0.40）。这看起来反直觉，原因是：声纹门控会把一部分目标自己的话也误判成"不是目标"而丢弃（即漏识率 FRR），被丢掉的部分等于全错，于是拉高了错误率。

这条结论很关键：如果你已经确定"现在就是目标在说话"，那加这套门控只会帮倒忙。它的价值只在"不确定是不是目标"的时候才体现。

补充一句，baseline 本身错误率就有约 25%，并不是模型差，而是这份测试集是强制重叠的极限难度集；真实场景通常没这么吵。

### 5.4 发现三：越重叠越差

按重叠比例分组看（重叠越多 = 目标和别人同时说话的时间越长）：

| 重叠比例 | 样本数 | 基线中文 CER | 方案 A @0.40 中文 CER | 漏识率 FRR |
| --- | --- | --- | --- | --- |
| 0.1-0.2（轻微插话） | 1464 | 18.03% | 25.35% | 16.39% |
| 0.2-0.3 | 1056 | 22.54% | 29.39% | 19.13% |
| 0.3-0.5 | 2282 | 26.47% | 33.91% | 19.94% |
| ≥0.5（一半时间被盖话） | 1425 | 34.23% | 43.98% | 28.77% |

规律非常清楚：重叠越严重，基线错误率越高，目标被误丢得也越多。根本原因是方案 A 只会"整段保留或整段丢弃"，并不会把混在一起的两个人声音拆开——这正是 2.5 节里前端分离类方案存在的理由。

### 5.5 发现四：速度不是瓶颈

整条流水线处理 1 秒音频只需要约 0.05 秒（实时率 0.053），比实时快约 19 倍。

| 阶段 | 处理每条的中位耗时 |
| --- | --- |
| 注册声纹 | 0.058 秒 |
| 声纹验证 | 0.109 秒 |
| 整段识别 | 0.146 秒 |
| 整条流水线实时率 | 0.053 |

折算到手机端预计也就 0.1 左右，端侧实时毫无压力。

### 5.6 发现五：声纹区分力 EER

等错误率 EER 为 7.36%，意思是用声纹区分"是不是目标"时，在最优平衡点上仍有约 7% 的判断会出错。这个数字没达到"优秀"标准（业界通常希望 ≤5%），但也没到"差"（>10%）。注册时多给几段不同条件的录音，预计能压到 5-6%。

### 5.7 阈值怎么选

阈值是方案 A 唯一需要现场调的旋钮，下表是完整扫描结果，帮助按业务取舍：

| 阈值 | 误识率 FAR | 漏识率 FRR |
| --- | --- | --- |
| 0.20 | 15.55% | 4.29% |
| 0.25 | 8.23% | 6.70% |
| 0.30 | 3.96% | 10.55% |
| 0.35 | 1.22% | 15.21% |
| 0.40 | 0.91% | 20.99% |
| 0.55 | 0.30% | 52.71% |

我们推荐起步用 0.30：它把误识率压到 3.96%、漏识率控制在 10.55%，是两者平衡得最好的点。原方案文档里写的起步阈值 0.55 在这份数据上偏严，会漏掉一半以上的目标语音，不建议直接用。

### 5.8 决策门对照

工程方案文档 [docs/speaker/PIPELINE.md](../../../docs/speaker/PIPELINE.md) 第 6 节预设了一组"是否需要升级方案"的判断标准。实测对照如下：

| 判断标准 | 实测值 | 结论 |
| --- | --- | --- |
| 整体 EER ≤ 5% | 7.36% | 不达标（差 2.36 个百分点） |
| 整体 FAR ≤ 5% | 8.23%（阈值 0.25）/ 3.96%（阈值 0.30） | 阈值 0.30 起达标 |
| 实时率 ≤ 0.2 | 0.053 | 达标 |
| 重叠场景 FAR > 20% 才需升级 | 8.23% | 未触发升级 |
| 短片段占比 > 30% 才需升级 | 0.3% | 未触发升级 |

落点很明确：方案 A 没有完美达到"阶段一通过"的全部标准（EER 略高），但也远没到需要上更重方案（前端分离、个性化检测）的程度。属于"现状基本可用、再微调一下更好"的中间区。

## 六、结论与建议

### 6.1 方案是否有效，取决于业务怕什么

| 业务最怕的情况 | 该不该加目标说话人 |
| --- | --- |
| 怕把别人的话或噪声错记成目标的（如电视、媒体声漏入，或多人在场但目标没开口） | 该加，收益巨大，误记率从 54% 降到 4% |
| 怕漏掉目标说的任何一句 | 别加，它会误丢约 10% |
| 只是单纯想提升识别准确率 | 别加，对识字本身是负作用 |
| 现场经常一半时间多人抢话 | 加了只能部分缓解，需要更重的方案 |

### 6.2 推荐配置

- 声纹阈值起步用 0.30（平衡点），后续按业务对"漏 vs 错"的偏好微调。
- 注册时引导用户录至少 3 段、覆盖不同距离和语速，这是预计能把 EER 压到 5-6% 的最低成本手段。
- 识别复用现有流式模型整段推理，不加第二个模型。

### 6.3 下一步可量化的优化

按性价比排序：

| 候选 | 预期收益 | 工作量 |
| --- | --- | --- |
| 阈值从双阈值改为单一 0.30 | 直接拿到误识率 3.96% / 漏识率 10.55% 的平衡点 | 改配置即可 |
| 多段注册（按说话人聚合 ≥3 段取平均） | EER 预计降到 5-6% | 约半天 |
| 换 CAM++ 声纹模型对比 | 速度预计减半，精度待测 | 约半天 |
| 用真实业务音频替代合成重叠测试集 | 真实 EER 预计更低 | 取决于数据准备 |

暂不建议投入的方向：升级到离线说话人分离、自训个性化检测、自训前端分离。原因是实测的重叠误识率仅 8.23%，远未触及这些重方案的启动门槛，且它们都需要 1-3 人月的训练投入。

完整原始数据见 [asr/tools/speaker/results/eval_full_summary.md](../../../asr/tools/speaker/results/eval_full_summary.md)，逐条记录见同目录的 eval_full.jsonl，可用于后续优化的前后对比。
