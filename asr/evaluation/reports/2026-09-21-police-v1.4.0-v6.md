# Police 1.4.0 模型接入与 V6 警务增强

Android/Harmony 中英模型打包默认输入已更新为指定的 Police 1.4.0 FP32 包；两端 ORT
资产转换、manifest 校验及 Harmony 模型来源 MD5 校验通过。新增 6 条完整指令纠错，
在 4,156 条桌面配对结果中改善 18 条、退化 0 条；原有警务抽样 383 条输出保持一致。
本次完成的是模型资产接入和定向规则优化，未完成移动端发布验收。按本轮约定先提交 PR、
暂不合入；真机 SDK 门禁后续补充。

## 实现

复用 `term_exact_homophones.csv` 的完整 final 匹配，Android/Harmony 同步同一词典。
纠正记录仪 NFC、录像分辨率、视频分段时长、延录时长及亮度零档的六个已观测误识。
不改变公共 API、增强开关、会话结束条件或声纹逻辑。

新增 29 条共享用例：六个原始失败、带标点/前空白变体、正确目标不变、放入其他句子后不触发，
以及“电子录音”“沿路风景”“零度”“第一档”等相邻合法表达。修改前 12 个断言失败，修改后
原有 647 条和新增 29 条全部通过。没有将“电子录音”直接改成“停止录音”，也没有猜填漏掉的词。

## 配对结果

两组使用完全相同的 Police 1.4.0 ASR 转写，只切换旧/新警务词典；这不是新旧模型版本 A/B。
Linux CPU，`sherpa-onnx==1.13.1`，modified beam search，8 paths，1 thread/recognizer；
16 kHz，20 ms 分帧，endpoint 参数 2.4/1.4/20 秒，结束补 1.2 秒右上下文。
后处理执行仓库 Harmony 的 terms → plate → station → polish 实现；未执行 SDK 的
AGC/VAD、ITN、标点模型、热词或人名模块，不据此推断完整 SDK 的精度、性能或回调契约。

CER 为 NFKC、统一大写、去空白标点后的字符编辑率，句准确率要求规范化后完全相同。
不把中文数字与阿拉伯数字强制等价，因此特殊代码中的格式差异也计入编辑；这些样本仅用于
确认本轮前后输出不变，不能用其绝对 CER 衡量数字格式能力。

## 验证与剩余限制

- 初次 300 ms 尾部补偿不足导致截断，随后只调整尾部上下文至 1.2 秒，保持模型、输入、顺序和其他参数一致，得到本报告基线。初次结果保留在本地 `baseline.jsonl`，属于无效评测工装结果，不归因为 SDK 或模型退化。
- 模型/交付/manifest 相关 Python 测试首轮 45 项通过；模型来源新增旧 INT8 拒绝用例及资产/语料索引检查共 32 项通过；共享警务规则 676 条通过。两端警务资产一致性、打包 shell 语法和 diff 空白检查通过。
- 两端中英模型 ORT 打包成功：Harmony ORT 1.16.3、Android ORT 1.24.3，各 9 个资产通过校验。运行期沿用旧文件名，manifest 中 encoder 来源明确为 `encoder.onnx`。
- 本机未配置 JDK、Android SDK、Harmony CLT 或 USB 测试设备；本地未运行 Android Gradle/JUnit、Harmony HAP/HAR 编译和真机 SDK 门禁。PR 的 CI 结果单独记录，不能替代真机验收。
- FP32 encoder 约 588 MiB，明显大于旧 INT8。现有 SDK-only ZIP 320 MiB 门禁未放宽；正式打包大小及 ARM 内存/时延尚待验收。

- 拉取主线后 `third_party/sherpa-onnx` 工作区仍处于原有本地修补版本，并含本地构建改动；未重置或把该 gitlink 差异纳入本次实现。平台构建前须按仓库流程恢复对应主线依赖。
