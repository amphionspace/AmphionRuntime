# 热词半匹配导致整段数字被删除：安卓现象、机制、鸿蒙复现（2026-10-29）

## 现象

客户安卓 App（`com.tdtech.tiassistant`，离线 ASR，`recognizerMode=long`，`vadEnd=1600`）：
说"我的新手机号是幺三幺幺二三四五六七八"，热词池含 `遣返` 时数字全部丢失，不含时正常。

| | 热词含 `遣返`（53 词） | 热词不含 `遣返`（51 词） |
|---|---|---|
| 录音真值（主机 greedy 解码） | 我的新手机号是幺三幺幺二三四五六七八 | 我今天的手机号是幺三幺幺二三四五六七八 |
| 设备 partial 序列 | 新手机号 → 新手机号是 → 新手机号是**遣** → 新手机号是（数字再未出现） | 今天 → … → 今天的手机号是幺三幺幺二三四五六七八 |
| 设备 final | 新手机号是。 | 今天的手机号是13112345678。 |
| endpoint 时刻 | 音频约 5.5 s，数字说到一半 | 数字说完之后 |

日志：`热词包含遣返.txt` / `热词不含遣返.txt`（客户 logcat，10-27 20:20 / 20:21），录音同名 `.wav`。

## 机制

1. 0.3.25 起调用方热词（`sysGeneralLexicon`）逐词加权 3.0（`PoliceEngineConfig.USER_HOTWORDS_SCORE`，
   安卓与鸿蒙相同），预置池保持 1.0。客户把 `遣返`、`谴责`、`黄色`、`下午` 等 53 个常用词都当热词传入。
2. 说"幺"的那一帧，"遣"借 3.0 的加分进入 `遣返` 的半匹配状态。
3. `ContextGraph::ForwardOneStep` 只在输出非 blank token 时结算回退扣分；输出 blank 不结算。
   于是"停在半匹配前缀上一直输出 blank"的假设保留着加分，而任何真实数字 token 都要一次性扣回，
   beam 被沉默假设占满，数字永远出不来。
4. endpoint 规则看到 1.5 s 没有新 token 就切句，final 为"新手机号是。"；后半段数字落到新一段，
   也没有恢复。

## 主机复现（同一模型、同一热词池、`modified_beam_search`、beam 8、全局 1.0）

- 原始 53 词 + 3.0：数字正常（设备上的触发点取决于那一帧的声学得分，主机未复现触发）。
- 把热词改成 `新手机号是遣返 :3.0`（让前缀更容易进入）：输出 `我的新手机号是遣`，数字全部消失；
  beam 64 仍不出数字。`遣返 :5.0` 单独一个词不触发。
- 去掉开头 VAD 切段、2~4 倍增益、改用安卓包自己的 encoder 资产都没有让 53 词 + 3.0 触发。

## 鸿蒙真机（包内 0.3.26 Diagnostics Demo，默认短句模式，`--skip-build-install`）

| 用例 | 结果 |
|---|---|
| 含遣返录音 + 原样 53 词 | 新手机号是13112345678。（正常） |
| 不含遣返录音 + 51 / 53 词 | 今天的手机号是13112345678。（正常） |
| 含遣返录音 + `遣返` / `是遣返` | 正常 |
| 含遣返录音 + `新手机号是遣返` | **新手机号是遣。然后。** —— 数字全部丢失 |
| 不含遣返录音 + `手机号是遣返` | 正常 |

结论：鸿蒙与安卓是同一缺陷类，机制在鸿蒙上同样成立；这条录音上鸿蒙需要更强的前缀才会被打中，
安卓设备用单个 `遣返` 3.0 就打中，差别来自两端 ORT 版本不同的量化模型、AGC、线程数和 long 模式
前缀压缩造成的那一帧得分差。

## 修复方案

1. 解码器（sherpa 原生补丁，两端共用）：modified beam search 中，停在未完成热词前缀上的假设连续约
   600 ms 只输出 blank 就结算回退扣分并回到根节点；endpoint 过渡时对残留半匹配状态做 Finalize。
   把最坏损失从"整句"压到 0.6 s 以内。
2. 配置缓解：调用方热词分数 3.0 → 约 2.0，用 AISHELL3 热词集与这两条录音做 A/B。
3. 对接：`sysGeneralLexicon` 只放业务专名，不放常用词。
