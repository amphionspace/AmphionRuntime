# 端侧按数量离线授权（额度证书链）方案与验证

状态（2026-11-27）：分支 `feat/edge-quota-license`。安卓与鸿蒙 SDK 已接入初始化流程，签发点已在 113 用真实 VDie 实测，
正式签发门禁已就绪；安卓（AndroidKeyStore）真机验证已通过，鸿蒙 HUKS 尚未上真机。
现有 SN 白名单授权（[dingqiao-offline-license.md](dingqiao-offline-license.md)）不变，两种格式并存。

## 1. 解决什么问题

白名单授权要求客户先交 SN 清单，换机、加设备都要我方重签。本方案让我方只签「数量」：
客户内网有一个签发点，在额度内自行给设备签授权，全程不需要公网。

离线环境里设备之间互不相通，单台设备无法知道全局已经激活了多少台，所以计数必须落在一个
所有激活都要经过的点上。本方案把计数点放在客户内网签发点，用三层手段约束它：

| 层 | 谁强制 | 能防什么 |
|---|---|---|
| 设备端校验（硬） | 每台设备的 SDK | 伪造额度、签发点越权（序号超过 N、加能力、延期限）、授权拷到别的设备、克隆同 SN 设备 |
| 签发点控制（软） | 签发工具 | 正常运维下的超发、拷到别的机器运行、日志被改或整体回滚到旧副本 |
| 离线对账（事后） | 我方 | 签发点私钥被盗用或工具被改后的超发：会留下签发点签名的证据，无法抵赖 |

**边界要说清**：客户如果拿到签发点私钥、改掉签发工具，就能给更多设备签出序号 ≤ N 的授权，
设备端看来都合法。离线方案阻止不了这一点，只能保证超发一定会在对账时暴露。需要硬阻止时，
签发点私钥和计数器要放进带安全计数器的加密狗或 HSM（第 6 节）。

## 2. 信任链与文件

```text
我方根私钥（现有 .lic 同一信任集，KMS/受控签发机）
  └─签→ 额度证书 amphion.quota.v1：数量 N、能力、签发窗口、运行期限、SDK 大版本、维护期、
        应用包、盐、签发点公钥与硬件绑定、回收预算
签发点私钥（客户内网生成，口令加密落盘，不出机器）
  └─签→ 设备授权 amphion.device-license.v1：序号 seq∈[1,N]、SN 盐哈希、设备公钥摘要、
        能力（≤额度）、期限（≤额度）、日志位置
设备私钥（HUKS / AndroidKeyStore 内生成，不可导出）
  └─签→ 激活请求、运行时随机挑战、注销回执
```

设备拿到的 `amphion-license.lic` 文件名不变，内容是 `{"format":"amphion.quota-chain.v1","quota":<信封>,"device":<信封>}`，
约 2.5 KB（3 万台白名单约 2 MB）。两层信封都和现有 `.lic` 一样：ECDSA P-256 签名覆盖 payload 原始字节。
顶层没有 `payload_b64`，旧版 SDK 和旧校验工具会报格式错误、失败关闭（已验证）。

## 3. 流程

1. **签发点入网**（客户现场）：`site_issuer.py init` 生成签发点密钥和 `enrollment.json`（自签证明持有私钥，
   带硬件标识的加盐哈希；推荐部署在私有化 ASR 服务器上，绑定 NPU VDie）。
2. **签额度证书**（我方）：正式签发走 `quota_delivery.py plan → issue → verify → record`（第 4 节「我方签发门禁」），
   底层由 `vendor_quota.issue_quota` 校验入网申请签名，写入数量、期限、签发点公钥，用根私钥签名。拒绝测试硬件方案。
3. **安装额度**（现场）：`install-quota` 校验根签名、额度证书确实发给本机（入网申请摘要、本机公钥）、硬件命中。
4. **设备激活**：设备在 HUKS 生成密钥，导出激活请求（SN 盐哈希 + 设备公钥，设备私钥签名）→ 签发点
   `activate`（单台）或 `activate-batch`（工厂批量）→ 设备授权文件放回设备。
5. **运行时**：SDK 初始化时按顶层 `format` 字段分派（链格式走本方案，否则走原白名单校验），本地校验整条链，
   再让设备密钥签一个新随机挑战，验签通过才放行。
   SDK 接口：安卓 `AmphionRuntime.quotaActivationRequest(context, deviceIdProvider, saltId)` /
   `quotaDeactivationReceipt(licenseText)`；鸿蒙 `AmphionQuotaLicense.activationRequest(serial, saltId, bundleName)` /
   `deactivationReceipt(licenseText)`。授权文件拿回后照常传给 `AmphionOptions.license`，`licenseStatus()` 的
   `installTier` 为 `quota`，`licenseId` 为 `额度号#序号`，`authorizedDeviceCount` 为额度总数。
6. **对账**（定期，离线介质带回）：`audit-export` 导出带签名封条的全量日志 → 我方 `audit-verify`，
   可附上次导出（查回滚/分叉）和现场抽检的设备授权（查未入账的授权）。

换机/恢复出厂：设备密钥丢失后重新激活，签发点按同一 SN 沿用原序号，不多占名额；旧授权因密钥不在而失效。
注销回收：额度证书默认不允许回收。确需回收时，我方在额度证书里写明回收次数上限；设备先签注销回执、
再销毁密钥，签发点凭回执释放序号。

## 4. 安全控制清单

**设备端（SDK 强制，Python 与 Kotlin 两份实现逐条对齐）**
- 额度证书只认 SDK 内置根公钥；设备授权只认额度证书里写明的签发点公钥。
- 设备授权必须引用这张额度证书的精确摘要，不能拿 A 额度的授权配 B 额度证书。
- `1 ≤ seq ≤ maxDevices`；能力不得超出额度；签发日期须在签发窗口内；运行期限不得晚于额度、额度有期限时不得改成永久。
- SDK 大版本、维护期、应用包白名单只从根签的额度证书读取，签发点改不了。
- SN 盐哈希匹配本机，且设备密钥对新随机挑战签名成功（防拷贝到同 SN 的克隆机/模拟器、防重放旧签名）。
- 严格解析：字段集合必须完全一致；重复键、浮点、NaN、尾随内容一律拒绝（安卓 org.json 与鸿蒙 `JSON.parse` 遇重复键
  都会静默取后一个，所以两端 SDK 都自带严格解析器）；每类签名对象带 `type`，不能拿日志条目冒充设备授权。
- 时钟水位：SDK 在应用私有存储（安卓 SharedPreferences、鸿蒙 Preferences）记录已见过的最大日期，判断到期时取设备时钟
  与水位中较晚者。离线设备把时钟调回，已过期的授权也不会复活。
- 设备密钥不可用（未生成、Keystore/HUKS 异常、恢复出厂后丢失）一律按设备不匹配拒绝。

**签发点（软控制）**
- 签发点私钥口令加密（≥12 字符，经环境变量传入），所有文件 0600、目录 0700，原子写 + fsync，文件锁防并发。
- 计数状态不单独存：每次启动都重放并验签整条哈希链日志，单改计数或删改条目都会被发现。
- 见证文件（建议放另一块盘或移动介质）记录日志最高位置，日志被整体换回旧副本时拒绝工作。
- 硬件绑定：VDie 等标识加盐哈希后写进额度证书，签发点至少要命中 `minHardwarePresent` 个（容忍单卡更换）。
- 激活请求必须带设备私钥签名，不能替别人的设备伪造请求；同一设备重复提交原样返回，不多占名额。
- 先写授权文件、再写日志：中途崩溃最多留下一个未入账、也未交付的文件。

**我方签发门禁**（`quota_delivery.py`，与 SN 白名单的 `license_delivery.py` 同一套约束）
- `plan`：严格校验申请（数量、期限、合同号、应用包、回收预算等）与入网申请（持有证明、拒绝测试硬件），生成计划摘要和
  warning：永久运行期、允许回收、签发窗口超过一年、不限应用包、硬件绑定偏弱、客户名不一致、客户累计额度增加、同一签发点已有额度。
- `issue`：重算计划，任何输入变化都阻断；每条 warning 必须逐项确认；要求干净的 Git 工作区、执行的是仓库受控的这份工具；
  根私钥必须在四个 SDK 内置公钥的信任集里。演练只能用显式 `--drill --root-key`，产物文件名带 `-DRILL`，不能入台账。
- `verify`：只打开最终 ZIP，核对成员集合、校验和、根签名（用 SDK 内置公钥）、额度证书确实发给入网的签发点、字段与计划一致。
- `record`：追加 `delivery/quota-delivery-history.json`（文件锁），同一 quotaId 不能登记两次，按客户累计已授权数量。

**对账（事后发现）**
- 校验额度证书、日志全链签名与序号规则、回收预算、封条与日志一致。
- 与上次导出比对：日志变短判定为回滚，前缀不一致判定为分叉。
- 现场抽检授权：签发点签过但不在日志里的授权（未入账）、同一序号出现在两台设备上（重复序号），都列为发现项。

**数据最小化**：激活请求、签发点、日志、审计里只有 SN 盐哈希和硬件标识盐哈希，没有明文（已用用例扫描确认）。

## 5. 验证结果（2026-11-27）

| 项目 | 结果 |
|---|---|
| Python 用例 `tools/license/quota/` | 46/46 通过：链与签发点 36 项（正常流程、设备端伪造与越权、签发点软控制、注销回收、数据最小化），签发门禁 10 项 |
| 跨语言互测 | Python 签出 22 条用例；安卓 Kotlin（JVM）与鸿蒙 TS（node 上用 node:crypto 代替 cryptoFramework/HUKS）逐条得到与 Python 相同的结果 |
| 变异测试 | Python 依次删掉 8 处关键检查；鸿蒙删掉 9 处（序号上限、额度摘要绑定、能力上限、期限上限、重复键、设备密钥挑战、SN 绑定、时钟水位、类型隔离）；安卓删掉额度摘要绑定、设备密钥挑战、序号上限。每次都有用例失败 |
| SDK 接入 | 安卓 `QuotaChainVerifierTest` 8 项：分派后的授权状态、时钟水位推进、时钟调回不能复活过期授权、设备密钥缺失失败关闭、激活请求与注销回执由设备密钥签名且不含明文 SN；原 `LicenseVerifierTest` 6/6 不受影响 |
| 鸿蒙接入 | 往返测试：鸿蒙端生成激活请求 → Python 签发点签授权 → 鸿蒙端校验（换设备密钥被拒）→ 鸿蒙端签注销回执 → 签发点回收序号。新增 ArkTS 文件用 DevEco SDK 的类型声明做了类型检查（HUKS、cryptoFramework、Preferences 接口签名一致） |
| 安卓输出被签发点接受 | 安卓生成的激活请求、注销回执，Python 签发点校验通过 |
| 113 真实硬件 | 签发点绑定 8 张卡 VDie（最少命中 6 张）；N=3 时单台 + 批量激活 3 台，第 4 台 `QUOTA_EXHAUSTED`；重复提交原样返回；恢复出厂沿用原序号；对账无发现项；错口令 `SITE_KEY_LOCKED`、没有这些 NPU 的环境 `HARDWARE_UNAVAILABLE`、日志回滚 `ROLLBACK_SUSPECTED`；文件 0600/0700；逐个比对 8 个真实 VDie 值，签发点文件里均无明文。远端临时目录已清理 |
| 旧格式兼容 | 旧 `verify_license.py` 对链文件报错失败关闭；旧版 SDK 读到链文件按格式错误拒绝 |
| 规模 | 批量激活 1 万台 5.3 s；1 万条日志时单台激活约 0.5 s；1 万条审计导出 9 MB、核对 < 1 s |

所有验证只用临时测试密钥，未读取 `.secure/` 下任何文件。

## 6. 剩余风险与后续

| 项 | 状态 / 处理 |
|---|---|
| 签发点私钥被提取、工具被改 | **固有边界**。设备端只能卡住序号 ≤ N，同序号重复签发离线无法阻止，靠对账发现（证据带签发点签名）。合同写明对账义务；需要硬阻止时，签发点私钥与计数器放进带安全计数器的加密狗/HSM，接口在 `Site._key` 与 `_append`。需要采购硬件后再接 |
| 整机快照回滚（日志与见证一起回滚） | **靠对账**。现场可多签，对账时用上次导出发现分叉、用抽检授权发现未入账。见证文件建议放签发点以外的介质 |
| 设备时钟 | **已处理**：SDK 时钟水位。剩余：应用数据被清除时水位一起丢失，此时设备密钥也已丢失、需重新激活 |
| 回收 | **已控制**：默认不允许；开启时额度证书写明次数上限且全部入账。root 设备把授权与密钥都备份恢复仍可能出现同序号两台，对账可发现 |
| 鸿蒙端 | **已移植**：`QuotaChain.ts`（校验核心与严格解析）、`QuotaDeviceKey.ets`（HUKS 密钥与 cryptoFramework）、`QuotaLicense.ets`（激活/注销接口、时钟水位），`License.ets` 按格式分派。**待真机**：HUKS 导出公钥格式与签名格式需在真机确认（本机没有连接设备） |
| 安卓端 | **已接入并通过真机验证**（2026-11-27）：`LicenseVerifier` 分派、`AmphionRuntime.quotaActivationRequest` / `quotaDeactivationReceipt`、AndroidKeyStore 设备密钥 |
| TTS SDK | **未接入**。安卓/鸿蒙 TTS 各有独立的授权校验，读到链文件会按格式错误拒绝（失败关闭）。客户需要端侧 TTS 按数量授权时，把同一套校验核心接进 TTS SDK |
| 我方签发 | **已就绪**：`quota_delivery.py`。首次正式签发需在干净的主分支检出上、用固定根私钥执行；企业后台端侧授权的 `limits.devices` 应与台账累计数对齐（后台在另一仓库，未改） |
| 签发点交付 | **已实测**（113）。剩余：打包进私有化服务器交付包（交付包在 audiollm-go 仓库），并写现场操作手册（口令保管、见证介质、定期导出审计） |
