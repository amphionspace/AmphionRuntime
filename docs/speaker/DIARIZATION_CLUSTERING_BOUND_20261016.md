# 角色分离聚类代价随会议时长增长：成因、修法与验证（2026-10-16）

记录的改动是 `98bf9f86`（PR #266，已合入主线）。本文说明为什么一次聚类的代价会随会议长度
失控、改了什么、以及两道验证（真机耗时曲线、公开说话人归属对照）的实测结果，包括**未覆盖
的场景**。

该改动合入时本文尚未提交，因此主线上一度只有改动而没有依据；第五节列出的两项空白在合入前
未被覆盖，**属于下一个交付包出货前应补的验证**，不是已关闭的评审项。

## 一、成因

`SpeakerDiarizationSession.updateSpeakers()` 取证据的那一步是全部历史窗口的前缀，提交与
预览走同一条路：

```ts
const available = this.windows.filter(window => isSessionFinal ||
  (window.windowStartSample + 160000) * 1000 / SAMPLE_RATE <= evidenceEndTime);
const evidence = this.client.readEvidence(available.length);
const clustered = await this.client.cluster(segments, embeddings, ...);
```

于是**每次提交都把整场会议从第 0 秒重新聚类一遍**。两个超线性项：

- `Ahc` 对训练向量数是 O(N²)，且每次聚类被调用**两次**（准入检查算过的拟合在末尾被重算）；
- 说话人数未达 `maxSpeakers` 时，短 run 准入循环**对每个候选重跑一次全量 `Ahc`**，候选数也
  随时长增长，整体变成 O(N³)。

主机实测（出厂聚类器，合成 2 s hop 会话）：

| 场景 | 3 min | 13 min | 20 min | 40 min | 2 h |
|---|---|---|---|---|---|
| 4 个说话人 | 0.02 s | 0.12 s | — | 0.59 s | ~5.3 s |
| 2 个说话人 | 0.08 s | 2.92 s | **9.93 s** | ~79 s | ~35 min |

与现场一致：客户 10-15 晚的 63 分钟会话 `speakerCount` 第 16 分钟才到上限 4，而锁屏期
lag 前 20 分钟平稳、之后开始爬升。

`Ahc` 并非唯一贵的那一步——`35dcd1da` 撤销 AHC 距离缓存时测得 960 秒会话在角色分离上花
294 秒计算，其中一次 `Ahc` 只占约 0.1 秒。**那个结论在它测的区间内是对的**；本文讨论的是
长会话区间，两者不矛盾。

## 二、改动

模型、阈值、10 秒窗口、2 秒 hop、提交周期均未改动。

1. 训练集上限 `kMaxTrainingVectors = 512`，按时间均匀抽样，使样本仍覆盖整场会议；
2. 短 run 候选上限 `kMaxShortRunCandidates = 32`，同样均匀抽样；
3. 复用准入检查已算过的 `Ahc` 拟合，不在末尾重算（**严格等价**）。

ArkTS 侧同形状的循环（每次提交为整场会议重算逐窗口 activity，一小时会话 330 万次迭代）
改为窗口完成时累加一次，已发布区间的遍历只覆盖该区间（**严格等价**）。

两个上限以下 `EvenlySpaced` 返回全部元素且保持原序，**短会话逐位不变**。

## 三、验证一：真机耗时曲线

诊断构建，客户原始录音循环至 7332 秒（单一连续会话），亮屏前台，hop 2000。

| | 窗口 | 单次提交聚类 | 指数 |
|---|---|---|---|
| 主机 · 修复前 | 1200 → 3600 | 0.59 s → ~5.3 s | **~2.0** |
| 主机 · 修复后 | 1200 → 3600 | 0.25 s → 0.63 s | ~0.8 |
| **真机 · 修复后** | 398 → 3663（9.2×） | 0.87 s → 5.71 s（6.6×） | **0.85** |

指数 0.85 < 1，超线性项消失。会话质量：`overall=PASS`、785 条 final、空 final 0、
4 个说话人、`degraded=0`、原生流泄漏 0、进程 CPU 中位 202%。

同一会话的耗时拆分（与 SDK 自报的 `speakerDiarizationInferenceMs` 吻合）：

| | 次数 | 合计 | 占比 |
|---|---|---|---|
| 窗口推理 | 3663 | 450.7 s | 38.1% |
| 提交聚类 | 65 | 198.7 s | 16.8% |
| **预览聚类** | 255 | **534.1 s** | **45.1%** |

合计 1183.5 s，RTF 0.161。**预览已是最大单项**，且跑在其设计预算（音频时长的 1/10）上限
附近——这是本改动之外的下一处，另行跟踪。

## 四、验证二：公开说话人归属对照

从该会话的诊断流重建全部 65 次提交的聚类输入（含每窗口分割、嵌入与 run 张量；非有限值按
原样还原为 NaN），分别喂给修复前后的聚类器，再把两条结果按提交顺序喂给**真实的
`CommunitySpeakerIdentity`**，按 10 ms 粒度比对公开说话人。

**对照工具的校验**：模拟出的公开映射与设备记录的 `clusterToFrozenId` 在 **65/65 次提交上
完全一致**，0 次不符。

### 内部标签确实会动

| 提交 | 训练向量 | 抽样比 | `hard` 偏差 |
|---|---|---|---|
| #001 | 148 | 1×（未抽样） | **0 / 348** |
| #004 | 340 | 1×（未抽样） | **0 / 846** |
| #016 | 1192 → 512 | 2.3× | 0.03% |
| #032 | 2289 → 512 | 4.5× | 0.19% |
| #048 | 3384 → 512 | 6.6× | 7.19% |
| #064 | 4410 → 512 | 8.6× | 9.61% |

上限以下**真实数据逐位相同**，等价性不只是构造上的推断。上限以上按类型拆分：

| | #032 | #048 | #064 |
|---|---|---|---|
| 纯编号置换 | 1 | 587 | 1034 |
| 真换组 | 0 | 0 | **4** |
| 由未归属变为有归属 | 10 | 15 | 18 |
| 由有归属变为未归属 | **0** | **0** | **0** |
| 说话人数 | 4 → 4 | 4 → 4 | 4 → 4 |

主体是编号置换：#048 是 `1` 与 `3` 整体对调，时间边界逐位相同。没有任何槽位从有标签退回
未归属；反方向有少量增加。

**偏差对上限不是单调的**：#032 在上限 1024 下偏差 9.92%，比 512 的 0.19% 差 50 倍，而
2048 下为 0。抽样是离散选择，调大上限只会换一批会偏的会话，不是可靠修法。

### 经注册表后的公开归属

`CommunitySpeakerIdentity` 按 (窗口, 声道) 槽位身份投票，不引用簇号，因此置换被吸收。实测：

```
已发布音频                                   7332.4 s
公开说话人不一致                                5.90 s   (0.0805%)
├─ 一边具名、一边未知（边界抖动）                5.29 s   (0.072%)
└─ 两边都具名（真正的归属互换）                  0.61 s   (0.0083%)
```

65 次提交中 12 次存在任何差异，最大一次 1.29 s（其中双具名 0）。双具名差异集中在 #046
的 0.41 s，其余散落约 0.2 s。

内部 `hard` 最高偏差 9.61% → 公开归属 0.08%（时长），注册表吸收了其中约 99%。

## 五、未覆盖的场景

1. **长静音后换人未覆盖。** 本段音频是客户录音循环 14 轮，4 个说话人全程存在、`speakerCount`
   很早到上限。注册表对**没有投票的簇**按首次出现顺序分配新公开号；若抽样改变了与已提交内容
   重叠很少的区域（会话开头、长静音之后）的分组，公开编号可能真错位。这是唯一能让公开编号
   错位的机制，**未验证**。
2. **短 run 候选上限未被触发。** 该会话说话人数已达上限 4，准入循环直接跳过
   （`shortRunTrainingCount` 两版均为 0）。而它正是治 O(N³) 的那一半，其等价性**未被本次验证
   覆盖**，需要一段说话人数少于上限的音频。

两条都需要"说话人数少于上限 + 含长静音"的音频覆盖。

## 六、本改动不解决什么

- **预览聚类占角色分离计算 45%**（见第三节），本改动未动；
- **内存峰值 1.15 GB / HWM 1.28 GB**（2 小时实测，斜率 2.0 MB/min）。`readEvidence` 仍每次
  提交读取整场证据前缀，本改动未动；
- **SDK 无遇热或按积压降级的机制**，降级只认 `STORAGE_UNAVAILABLE` / `INFERENCE_UNAVAILABLE`
  / `FINISH_TIMEOUT`，热等级与队列深度都不是输入；
- 逐窗口推理占 38%，线性于时长，是必要开销；
- 设备发热的主体是屏幕与整机负载，不在 SDK 侧。

## 七、共用面

`community_cluster.h` 由 Android JNI 目标一并编译（见 `SharedTranslationUnitCompilesForAndroidTest`），
两端都需重建原生库才能生效。0.3.23 与当前 Android AAR 均不含本改动。
