# 安卓真机长跑：发热与内存报告

- 日期：2026-11-04
- 设备：**OnePlus PHK110（一加 Ace 2 Pro）**，骁龙 8 Gen 2（taro），Android 16，8 逻辑核
- 被测包：`com.amphion.dingqiao.demo`（本地 debug 构建，以 release 证书签名以通过 license 的 certSha256 绑定）
- 实际时长：**86.5 分钟**（计划 120 分钟，按决定提前停止）
- 负载：instrumented 长跑 `DqThermalLongRunTest`，20 ms / 640 字节定长帧按**实时速率**喂入，
  **开启角色分离**（`SpeakerDiarizationConfig(maxSpeakers=4)`，Sortformer），每 5 分钟一个会话轮转
- 语料：12 条由 AliMeeting 真实会议说话人拼成的 3 人对话（合计 25.2 分钟，循环），
  另有 1 条随 APK 打包的 `001_recognize.wav`（约 10 秒）也进入轮换，占比 <1%
- 采样：主机侧 `sampler_android.sh`，30 秒一点；温度来自 `/sys/class/thermal`，内存来自 `/proc/<pid>/status`，
  CPU 来自 `/proc` 节拍差分，节流来自 `dumpsys thermalservice`

## 0. 结论

| 项 | 结果 | 判定 |
|---|---|---|
| 后壳 shell_back | 31.0° → **35.5°**，升幅 **+4.7°**（峰值 35.7°） | **20 分钟后进入热平台** |
| 前面板 shell_front（用户摸到的最热处） | 31.6° → **37.9°**，+6.4° | 平台 |
| 升温斜率（后壳） | +11.5 → **+0.5 → +0.5 → +1.3 °/小时** | **平台明确** |
| skin-msm-therm（系统节流依据） | 33.9° → 43.3°，峰值 43.8° | 未达节流阈值 |
| **节流** | **全程 `Thermal Status: 0`，164/164 个采样点无节流** | **从未降频** |
| CPU | 单核等效中位 **163.7%**，p95 175.5%，峰值 181.5%；整机 20.5% | 约 1.6 核常驻，跑在中核簇 |
| 内存 RSS | 分段中位 737~752 MB，**无增长**；峰值 807 MB，HWM 836 MB | **平坦，不是饱和型也不是泄漏** |
| 线程 | 54~55，零增长 | 稳定 |
| 喂入节拍 feed_ratio | 0.990 → 0.996（会话 1~13） | **真实时** |
| 稳定性 | ERROR 回调 0，看门狗 0 次触发，设备侧零掉线 | 通过 |

一句话：**安卓侧发热与鸿蒙形状一致——前 20 分钟快速升温，之后平台；全程没有触发任何降频；内存从头到尾平坦。** 后壳 +4.7° 是原始值，这台机**没有环境温度传感器**，无法像鸿蒙那轮一样扣除房间漂移，真实自发热只会更低。

### 1.2 是否进入热平台（后壳 shell_back，分段回归）

| 时段 | 中位 | 斜率 |
|---|---|---|
| 0~20 min | 33.6° | **+11.49 °/小时** |
| 20~40 min | 35.1° | +0.54 °/小时 |
| 40~70 min | 35.1° | +0.50 °/小时 |
| 70 min~ | 35.5° | +1.29 °/小时 |

斜率在 20 分钟处衰减 20 倍以上，之后三段都在 ±1.3 °/小时以内。**20 分钟后机身温度基本不再上升。**
70 分钟后略有回升（+1.29）与 cpuss/aoss 在 68 分钟附近的一个小峰对应，幅度 0.3°，仍在平台噪声范围内。

### 1.3 没有环境传感器，净自发热给不出

鸿蒙那轮能把"机身 − 环境"算出来（原始 +5.6° 扣掉房间 +3.4° 后净 +2.2°）。这台一加**没有 `ambient` 传感器**。
离热源最远的两个传感器可作弱代理，但它们自己也受机身加热：

- `wlc-therm` +3.7°、`battery` +4.3° —— 它们本身在升，说明机身整体在热，不能当环境用
- 房间在这 86 分钟里漂了多少，**未知**

因此本报告只给原始升幅 **+4.7°**，并明确它是**上界**：真实自发热 ≤ 4.7°。

### 1.4 节流与频率：全程未降频

| 项 | 读数 |
|---|---|
| `Thermal Status` | **0**，164 个采样点全部为 0 |
| 大核 policy7 | 绝大部分时间 **787 MHz**（上限 3187），偶发短促冲到 1440 / 2131 MHz |
| 中核 policy4 | 2227~2342 MHz（接近满载） |
| 小核 policy0 | 556~1804 MHz 浮动 |

**SDK 的负载跑在中核簇上，大核几乎没被调度。** 这是发热能快速平台的直接原因——中核的功耗远低于大核。
skin-msm-therm 停在 43° 附近，距一加常见的节流起点（约 45~48°）还有余量。

## 2. CPU

| 指标 | 值 |
|---|---|
| 单核等效占用 中位 | **163.7%** |
| 单核等效占用 p95 | 175.5% |
| 单核等效占用 峰值 | 181.5% |
| 整机容量占用 中位 | 20.5%（8 逻辑核） |

约 **1.6 个核常驻**。与鸿蒙那轮（中位 149.6%、12 核、整机 12.5%）同一量级；整机占比更高是因为核数少。
CPU 由 `/proc/<pid>/stat` 与 `/proc/stat` 的节拍差分得出——**安卓的 `top -n 1` 单次采样恒为 0.0%，不可用**，
本次曾据此误判一次运行"没在干活"并中止了它（见第 5 节）。

| 段 | 时间 | 中位 | p90 | 最大 |
|---|---|---|---|---|
| 1 | 0.0~10.7 min | 752 MB | 768 | 779 |
| 2 | 11.2~21.4 min | 748 MB | 768 | 772 |
| 3 | 21.9~32.0 min | 737 MB | 759 | 767 |
| 4 | 32.6~42.7 min | 742 MB | 766 | 773 |
| 5 | 43.2~53.9 min | 747 MB | 766 | 776 |
| 6 | 54.4~64.6 min | 747 MB | 762 | 770 |
| 7 | 68.6~75.3 min | 739 MB | 760 | **807** |
| 8 | 75.8~86.0 min | 737 MB | 763 | 768 |

- 分段中位在 **737~752 MB** 之间，跨度 15 MB，**没有任何趋势**（7 个台阶里只有 3 个上升）
- 全程回归斜率 +9.6 MB/小时，后半程 −19.2 MB/小时——正负相间，是噪声
- RSS 峰值 807 MB，HWM 836 MB；线程 54~55 零增长

**与鸿蒙的对照**：鸿蒙那轮是饱和型（前 90 分钟从 658 爬到 800 MB 再平台，HWM 1044 MB），安卓**从一开始就平坦**，
峰值也低 200 MB。两端的 Sortformer 链路相同，差异最可能来自鸿蒙额外开着的 CAM++ 声纹身份（嵌入缓存与 PCM 环形缓冲）
以及两端内存分配器的行为不同。**这不是 A/B，只能作为线索。**

## 4. 负载的真实性

发热测试的前提是"真的在干活"。本次用了四层证据，而不是只看进程存活：

1. **喂入节拍**：每个会话落盘 `feed_ratio`（实际喂入音频秒数 / 墙钟秒数），会话 1~13 为 **0.990 → 0.996**，
   差额是会话起停开销。1.0 才是实时；之前用每帧 `Thread.sleep(20)` 的实现会超调到 0.7~0.8。
2. **识别回调**：运行 22 分钟时已累计 PARTIAL 2369 条、FINAL 110 条、COMPLETE 5 条；**FINAL 相邻间隔中位 19.8 秒**，
   与语料结构（每段发言 5 秒、3 人一轮后有较长间隙、`vadEnd=800ms`）严丝合缝——喂零或静音不会有任何 PARTIAL/FINAL。
3. **CPU 节拍差分**：5 秒窗口内进程节拍增量稳定在 700~770（约 150% 单核等效）；冻结时为 0。
4. **模型身份**：运行中的进程里有 **6 个 `amphion-sortformer-client` 线程**（仅 `SortformerLocalClient.kt:52` 创建），
   工作目录里装的是 `sortformer-66M-4spk/encoder_layers.int8.onnx` 等全套新模型文件。
   安卓的角色分离代码只有 Sortformer 一条路，**没有新旧切换开关**。

语料内容也量过：12 条文件 RMS 中位 −31~−43 dBFS、峰值 −3.7~−9.3 dBFS、静音窗占比 7~26%，是正常电平的语音。

## 5. 本次测量的边界与事故（必须随结果一起说）

1. **与鸿蒙不是同一配置，不能直接相减。** 鸿蒙那轮全程开着 CAM++ 声纹身份；安卓没有 `speakerIdentityMode`，
   声纹分配器也未接入管线，本次只跑了 Sortformer 这一条路。两端的 +4.7° 与 +5.6° 不能解读为平台差异。
2. **没有环境传感器**，净自发热给不出，+4.7° 是上界（见 1.3）。
3. **86.5 分钟而非 120 分钟**：平台在 20 分钟已明确、之后 65 分钟斜率 ≤1.3 °/小时，按决定提前停止。
4. **采样有一段 243 秒空档**（约 64.6~68.6 min）：主机侧 `adb shell am instrument -w` 两小时没有输出，被 USB/adbd 空闲
   掉线提前返回；运行器据此停了采样器，而设备侧的测试（截止时间在设备侧）其实仍在跑。
   重挂采样器后两段按主机墙钟拼接（第 2 段平移 +4118 s），空档不插值。**这个坑已修**：运行器现在以设备侧落盘的
   收尾记录判断结束，不再依赖 `am instrument` 连接。
5. **设备侧最终记录未能取回**：停止时第一次拉取撞上了 force-stop 返回空，随后设备被拔下。
   会话 14 之后的 feed_ratio 与回调计数没有留档；截至 65 分钟的 13 个会话数据是在运行中多次读取并记录的。
6. **三次假"卡死"**：正式跑之前，测试三次在会话 +48 秒停止出回调、全部线程休眠、CPU 为 0，先后被误判为 SDK 死锁、
   角色分离触发、墙钟回跳。真因是**一加/OPPO 的后台应用管控**——instrumented 测试没有前台 Activity，进程在启动约 48 秒
   后被冻结（logcat `OplusAlarmAdjustment proxyAlarmsByUid`，时间戳与停住点分毫不差）。把 `MainActivity` 拉到前台后
   同一测试 +170 秒仍在出回调。**SDK 没有问题。** 修复已固化进运行器。
7. **一次被我误停的正常运行**：依据是 `top -n 1` 的 "CPU 0.0%"，而该读数在安卓上恒为 0。此后一律用 /proc 节拍差分。

| | 鸿蒙 Mate 80 / Kirin 9020 | 一加 Ace 2 Pro / 骁龙 8 Gen 2 |
|---|---|---|

共同点：都没有触发降频，都进入了热平台，负载量级相同。**两端的发热都不是问题。**

## 7. 复现

```bash
# 一键：等基线 → 建装（或 --skip-build）→ 采样 → 长跑 → 以设备侧记录判结束 → 报告
asr/tools/speaker/run_android_longrun.sh <输出目录> 120 30 [--skip-build]

# 构建测试包时必须带这两个属性：
#   -PdingqiaoDebugUseReleaseSigning=true   license 的 certSha256 绑 release 证书，默认 debug 密钥会被判 INVALID(6005)
#   -PdingqiaoEvalAudioDir=<语料目录>        androidTest 自身没有 wav，语料在构建时注入
```

踩过的坑，供下次参考：
- 被测进程**必须有前台 Activity**，否则一加/OPPO 在约 48 秒冻结它；运行器会在 instrument 起来后自动拉起 `MainActivity`
- `am instrument -w` 不能当作测试存活的依据，两小时的静默 adb shell 会掉线
- 安卓 `top -n 1` 的 CPU 恒为 0.0%，用 `/proc` 节拍差分
- 安卓各机型温度单位有毫/分/摄氏三种，报告脚本按读数区间自动判别
- 该机型 89 个 thermal_zone，不要全采
- 重装 test APK 会因签名不一致失败，需先卸载旧包；主包也要同签名
