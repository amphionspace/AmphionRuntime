# 角色分离发热真机实测总报告：encoder 后端矩阵、角色分离增量、以及 NPU 可行性边界（2026-10-08／09，Mate 80）

本文汇总同一台 Mate 80 上的三组真机测试，回答四个问题：

1. 把 Community 说话人 encoder 从 CPU 挪到 Kirin NPU，16 分钟、30 分钟、1 小时连续会议转写各能降多少发热（**A 组**，第 2–4 节，六轮矩阵）。
2. 角色分离这条链本身在发热里占多少——仅识别与开角色分离的配对对照（**B 组**，第 5 节）。
3. 冷起点（31 °C）下的升温形态，以及同起点配对的早期验证（**C 组**，第 6 节）。
4. 能否把 ASR encoder 或分割模型也挪上 NPU。**两个都不能**——证据链见第 8、9 节。

**三组用的是三个不同的 HAP**（A 组 `10622fd2`、B 组 `a70223a6`、C 组 `cf6b356c`），所以**组内配对可以直接相减，跨组只能比方向**。三组共用同一台设备、同一段 960 秒音频（A 组的 30/60 分钟档另有更长片段）、同一套温度采样与载体口径。

结论先行（前壳 shell_front，同起点对比）：

| 时长 | CPU encoder 升温 | NPU encoder 升温 | 降幅 | 峰值 CPU→NPU | 进程 CPU 均值 |
|---|---:|---:|---:|---|---:|
| 16 分钟 | +6.86 °C | **+4.79 °C** | **−2.06 °C（−30%）** | 41.14 → 39.17 °C | 235.4% → 204.4% |
| 30 分钟 | +8.90 °C | **+6.11 °C** | **−2.78 °C（−31%）** | 43.20 → 41.07 °C | 240.4% → 208.3% |
| 60 分钟 | +9.26 °C | **+7.13 °C** | **−2.12 °C（−23%）** | 44.90 → 42.59 °C | 249.4% → 212.8% |

三个时长都稳定少升 2 °C 以上，机身峰值低 2.0–2.3 °C，电池峰值低 2–3 °C。识别文本逐字节相同，角色标签帧级一致率 99.2%（16 分钟）/ 100%（30、60 分钟）。

### 3.3 测量条件的诚实说明

- **充电托底**：USB 供电无法断开（hdc 需要连接），`charger` 传感器全程 33–37 °C，因此所有起点只能定在 34–35.7 °C，而非室温。这对两档一致，不影响档间对比，但绝对值不能外推到断电场景。
- **环境漂移**：`ambient` 在 60 分钟档内持续下降（cpu60 30.70 → 25.02 °C，npu60 28.26 → 26.85 °C），这解释了两个 60 分钟档末尾的温度回落。两档起始 ambient 相差 2.4 °C（CPU 档更高，对 CPU 档不利），这是本次六轮里最大的环境不匹配，需要在解读 60 分钟档的 2.12 °C 差值时一并考虑。
- **30 分钟档起点差 0.65 °C**：NPU 档起点更高，属于对 NPU 不利的偏差。

### 4.2 encoder 占用率（NPU 利用率的可测替代）

这台设备不开放 NNRt 利用率计数器：`/sys/class/devfreq`、`/sys/devices/platform`、`/sys/kernel/debug` 对 shell 均为 Permission denied，`hidumper -ls` 的服务列表里没有 NNRt/NPU/HiAI 服务（`XpowerManager`、`SocPerfService` 对 shell 返回空 dump），`hitrace -l` 也没有相关 tag；HiAI/NNRt 的公开 NDK 接口同样只提供设备枚举、性能模式与优先级，没有占用率。

可测的替代是 encoder 占用率：用哈希绑定的逐窗 `encoderMs` 乘窗口数，除以会话时长。

| 轮次 | 窗口数 | 单窗中位 | 累计占用 | 会话时长 | 占用率 |
|---|---:|---:|---:|---:|---:|
| cpu16 | 951 | 307.7 ms | 292.6 s | 965 s | **30.3%**（一个 CPU 核） |
| npu16 | 951 | 27.7 ms | 26.3 s | 965 s | **2.7%**（NPU） |
| cpu30 | 1791 | 309.0 ms | 553.5 s | 1810 s | **30.6%**（一个 CPU 核） |
| npu30 | 1791 | 27.7 ms | 49.6 s | 1810 s | **2.7%**（NPU） |
| cpu60 | 3591 | 326.4 ms | 1172.0 s | 3621 s | **32.4%**（一个 CPU 核） |
| npu60 | 3591 | 27.6 ms | 99.0 s | 3621 s | **2.7%**（NPU） |

NPU 档三个时长的占用率都是 2.7%，加速器余量很大；CPU 档为 30.3–32.4%（一个核），且 60 分钟档因热降频升到 32.4%。这说明瓶颈不在加速器算力，而在仍跑在 CPU 上的 ASR。

此数值是从本 SDK 自己的逐窗耗时推出的占用率，不是硬件计数器读数，不包含 NNRt 的排队与数据搬运开销。

### 6.4 过程中的问题

1. **设备被并行占用导致前两次 CPU 臂作废。** 04:26 与 04:48 两次 `diarization-windows` 运行都没有拿到 SUMMARY；hilog 显示同一时间段 demo 进程在执行另一条流水线的 `finish-shutdown-relicense` 运行（产物在 `.cache/harmony-community-npu-gitarm64.ocMMdS/`），UIAbility 单实例被占用，本会话的 want 没有执行。之前记录的“载体在 16.1 分钟被 PROCESS_KILL”与“屏幕超时”判断不成立，本次已改为 `paced` 模式并与用户的短片对比保持同一套参数。
2. **`verify_community_encoder_execution.py` 在 paced 模式误报 `runner-diagnostic-session-count-mismatch`。** 载体在没有 finish-recovery 阶段的模式下写 `recoveryStarts=-1`，验证器把它直接累加进期望会话数（1 + (−1) = 0 ≠ 1）。用户的 30 秒短片恰好因导出事件被环形缓冲裁掉而“通过”。已在验证器中把负哨兵按 0 处理（`max(int(...), 0)`），14 个单元测试通过，三臂重新验证均 PASS。
3. **充电托底。** USB 供电下机身降到约 35 °C 后不再下降（`charger` 传感器 36.6–37.2 °C，`ambient` 读数在 B 臂前升到 28.3 °C），所以 B、C 臂只能在 35 °C 同起点对比，而不是 A 的 31 °C。


## 7. 结论

1. 角色分离 encoder 上 NPU 在三个时长上都稳定降温 2.06–2.78 °C（相对降幅 22.9–31.3%），峰值低 1.97–2.31 °C，电池峰值低 2–3 °C，进程 CPU 低 31.0–36.6 个百分点（相对 13.2–14.7%）。
2. 降温效果不随时长衰减；30 和 60 分钟都已进入平台期，NPU 档的平台比 CPU 档低约 2–3 °C（60 分钟档的 ambient 起点差 2.4 °C 对 CPU 档不利，解读该档差值时需计入）。
3. 热降频只打击 CPU 档：60 分钟 CPU 档 encoder 中位耗时从 307.7 升到 326.4 ms、p95 升到 495.4 ms，NPU 档三档中位 27.6–27.7 ms 不变。
4. 识别结果不变（文本逐字节相同），角色结果 30/60 分钟帧级完全一致。
5. 角色分离是这次发热的主因，不是 ASR：16 分钟仅识别只升 2.06 °C，开角色分离升到 6.37 °C（3.1 倍）。encoder 迁到 NPU 去掉了角色分离 CPU 增量的 57%（+53.0 → +22.7 个百分点），但温升增量只从 +4.31 降到 +3.31 °C，因为分割模型、聚类、fbank、池化仍在 CPU 上。
6. **CPU 时间占比不能当发热占比用。** 按时间算 ASR 占 89.4%、角色分离只占约 11%，但仅识别那 181% 的负载只换来 2.06 °C，而角色分离那 11% 换来 3.31 °C。差别在负载形态：仅识别全程不超过 2.7 核且从不触及 300%，角色分离把瞬时占用推到 4.2 核（4.1% 的采样 >300%），尖峰驱动大核高频档，每 CPU·秒的能耗高得多。详见 8.1。
7. 发热并未解决，只是缓解：NPU 档 60 分钟仍到 42.59 °C。继续降的空间在角色分离剩余的 CPU 部分（分割 91.8 s + 聚类 61.5 s，见 8.1），尤其是削掉它的尖峰，而不在 ASR encoder（见第 8 节）。

## 8. 为什么没有"ASR encoder 也在 NPU"这一档

### 8.1 CPU 时间归因（16 分钟 NPU 档，951 个窗口的诊断日志）

整轮约 1970 CPU·秒（均值 204.4% 单核等效，观测 964 秒）。按 951 个窗口的逐窗耗时与 72 次聚类拆开：

| 组成 | 该会话累计 | 占总 CPU |
|---|---:|---:|
| **ASR（zipformer 流式解码）+ 框架/诊断日志** | ~1762 CPU·s | **89.4%** |
| 角色分割 segmentation（ORT 单线程） | 91.8 s | 4.7% |
| 聚类 AHC/VBx（`clusterElapsedMs`，72 次） | 61.5 s | 3.1% |
| fbank 特征 | 22.2 s | 1.1% |
| 说话人 encoder（已在 NPU） | 26.8 s | 1.4% |
| 池化/统计 | 5.9 s | 0.3% |

**这张表是 CPU 时间的拆分，不是发热的拆分，两者不能混用。** B 组的对照直接否掉了"大头是 ASR 所以优化空间小"这个推论：仅识别跑满 181.0% CPU 只升 2.06 °C，而角色分离只多占 22.7 个百分点却多升 3.31 °C。

原因在逐秒瞬时 CPU 的分布上（由各轮 `memory.csv` 的 `process_cpu_ticks` 差分得出）：

| 档 | 均值 | p50 | p90 | p99 | 最大 | 峰值/均值 | >300% 的采样占比 | >400% |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `asronly16` | 179.9% | 180.5% | 208.0% | 254.0% | **265.5%** | 1.48 | **0.0%** | 0.0% |
| `diarcpu16` | 232.6% | 230.8% | 275.3% | 341.8% | **415.4%** | 1.79 | **4.1%** | 0.2% |
| `diarnpu16` | 202.6% | 200.9% | 241.5% | 290.8% | 394.8% | 1.95 | 0.9% | 0.0% |

仅识别是一条**平的约 1.8 核负载，全程不超过 2.7 核**；角色分离叠加的是**尖峰**——每 10 秒窗触发一次分割+特征+编码，聚类另有 72 次、中位 657 ms 的突发，把瞬时占用推到 4.2 核。手机 SoC 的功耗对频率电压是超线性的，尖峰会把调度器推上大核高频档，因此同样一秒 CPU 时间的能耗相差数倍。

按稳态温升与功耗近似成正比反推：2.06 °C 对 6.37 °C 意味着角色分离贡献的功耗约为 ASR 的 2 倍，而它只占 0.3 倍的 CPU 时间——每 CPU·秒的能耗差约 7 倍。尖峰分布是实测的；"能耗差源于频率电压档与指令组合（分割的 FP32 卷积 vs ASR 的 INT8 GEMM）"是推断，未直接测量功耗。

因此 8.1 的正确用法是：**它告诉我们接下来该优化哪一块的 CPU 时间（分割 91.8 s 最大），但不能用它的百分比去预测降温幅度。** 实际降温要看 B 组那样的配对实测。

### 8.2 尝试把 ASR encoder 搬上 NPU：逐步证据

ASR encoder 是 zipformer2（`decode_chunk_len=64`、`T=77`、`num_encoder_layers=2,2,4,5,4,2`、`encoder_dims=256,384,512,768,512,256`），12,235 节点、117 输入 / 117 输出（116 个 cached state）。

| 步骤 | 结果 | 证据 |
|---|---|---|
| 交付用 INT8 encoder 直接转 MindIR | **失败** | `UNSUPPORTED OP LIST: ONNX DynamicQuantizeLinear / MatMulInteger`——MindSpore Lite 2.7.0 的 ONNX 前端不接受动态量化（`MatMulInteger` ×344、`DynamicQuantizeLinear` ×312） |
| 反量化 INT8 → FP32（`asr/tools/dequantize_asr_encoder.py`，344 组改写） | 成功 | encoder_out 与 INT8 图 cosine 0.99993 |
| 取得上游原生 FP32（`encoder.upstream.fp32.onnx`，616,801,465 B，SHA-256 `8c2e6368…e474ed`） | 成功 | 与反量化版**结构逐项相同**（10,891 节点、每种算子计数一致、117 进 117 出、同 opset），encoder_out cosine 0.99985 → 交付 INT8 实为同源量化 |
| 逐算子族探测 HiAI 接受度（自造固定形状微模型，上机逐个 build+Predict） | 见下 | 接受：MatMul（含 batched）、Softmax、带 bool mask 的完整注意力（0.37 ms）、BiasNorm、SwooshL/R、Sigmoid、Tanh、ReduceSum、Conv（2-D 与 depthwise 1-D）、Transpose/Reshape/Concat/Slice/Gather/Range/Tile/Expand/ConstantOfShape/Where、int32 `Equal`、int64 `Greater`、bool 的 Unsqueeze/Expand/Slice/Concat。**拒绝**：`GatherElements`（任何索引类型）、**float** `Equal`、**float** `LessOrEqual`、恒等 `Cast`（bool→bool）、以及 `Shape`→`Gather`→`Concat`→`Reshape` 动态形状链 |
| 修掉全部拒绝项（`asr/tools/rewrite_asr_encoder_npu_ops.py`） | 成功 | `GatherElements` ×19 → `Reshape+Mul+Add+Gather`（数值精确）；95 处 softplus 溢出保护 `where(log1p(exp z)==+inf, z, ·)` → 稳定式 `max(z,0)+log1p(exp(-|z|))`；恒等 `Cast` ×107 删除；`LessOrEqual` → `Greater+Not`；`Shape` ×574 与 2,582 个常量节点静态折叠。节点 10,891 → 3,766，117 个输出最大差 7.9e-4 |
| 改写后整图在 Kirin NPU 上 build | **失败** | `NNRt: Authentication failed, input model cannot run by npu` → `OH_NNCompilation_Build failed` → `MS_LITE: BuildKirinNPUModel# Create full model kernel failed`，build 287 ms |
| 前缀二分定位边界 | **容量上限** | 前 **741** 节点通过（≈19 层里的前 3.7 层），第 742 节点起整模型被拒。第一个被拒节点是 `Conv /causal_conv_6/Conv`（depthwise，group=384，kernel=16），而**完全相同的卷积在节点 559 和 621 是通过的** → 不是算子不支持，是模型规模过线 |
| 被接受前缀的两端实测（741 节点，20.7 MB MindIR） | **NPU 更慢** | NPU 中位 **39.58 ms**（min 36.41 / max 65.13，build 889 ms）；MS Lite CPU 中位 **23.28 ms**（min 18.82 / max 41.94，build 56 ms）→ **NPU 慢 1.70×** |

反量化版与上游原生 FP32 两条路径给出**完全一致**的结论（边界 749 vs 741 节点、同一个被拒节点、NPU/CPU 比 1.59 vs 1.70）。

上游原生 FP32（`encoder.upstream.fp32.onnx`，616,801,465 B，SHA-256 `8c2e6368…e474ed`，producer `pytorch 2.5.1`）的真机复核逐项记录：

| 环节 | 实测 |
|---|---|
| 改写 | 19 `GatherElements` + 1 `LessOrEqual` + 95 softplus 保护 + 107 恒等 `Cast` + 574 `Shape` 折叠 + 2,582 常量折叠 → 3,766 节点，117 输出最大差 7.9e-4 |
| 转 MindIR | `CONVERT RESULT SUCCESS`，308,088,480 B |
| 整图 NPU build | **FAIL**，`stage=build code=-1 buildMs=287.2` |
| 前缀 741 / 742 | **PASS**（build 851.9 ms）／ **FAIL**（build 450.1 ms） |
| 前缀 741 两端 | NPU 中位 39.58 ms（min 36.41 / max 65.13，build 888.8 ms）；CPU 中位 23.28 ms（min 18.82 / max 41.94，build 55.9 ms）→ **1.70×** |

需要说明：**六轮发热测试不使用这份 FP32**。ASR encoder 上不了 NPU，没有可替换的对象；而把交付用的 INT8 ASR encoder 换成 FP32/MindIR 的 CPU 路径会移动两档共享的 ASR 基线，那样测的就不再是"分离 encoder 后端"这一个变量。六轮里 ASR 始终是同一套 zh-en INT8 zipformer（ORT CPU，4 线程）。

### 8.3 为什么 zipformer 在 NPU 上更慢，而说话人 encoder 快 11 倍

说话人 encoder 是一次性的大密集前向：输入 `[1,998,80]` → 输出 `[1,2560,125]`，单次 Predict 把整段 fbank 算完。zipformer 的一个 chunk 只有 T=77 帧，19 层里全是小张量的 matmul、slice、逐元素操作，算子下发与 NPU↔CPU 数据搬运的固定开销盖过算力收益。这也解释了为什么 conv 子采样前端（59 节点）在 NPU 上是 0.80 ms vs CPU 2.58 ms（快），而整层堆叠起来就反过来。

### 8.4 结论

**这台设备上 ASR encoder 不能也不值得上 NPU**：整图被 HiAI 拒绝（容量上限），而被接受的前 3.7 层在 NPU 上比 CPU 慢 1.70×，拆分执行只会更慢更热，且需要在 sherpa 的 encoder 调用路径里跨两套 runtime 搬运 25 进 32 出的 state，工程代价高、收益为负。MindSpore Lite 的 NNRT delegate 是整模型 offload（`CreateFullModelKernel`），也不会自动做 CPU/NPU 切分。

## 9. 分割模型上 NPU：也被拒绝

对照实验把剩余热源定位到角色分离仍在 CPU 的部分，其中分割模型最大（91.8 s，占角色分离链 44%，另有聚类 61.5 s、fbank 22.2 s、池化 5.9 s）。它是 pyannote 分割网络，**与 ASR encoder 不是同一个模型，也不属于同一条链**——角色分离链是「分割 → fbank → 说话人 encoder → 池化 → 聚类」，ASR 是另一条独立的链。两张图差了 240 倍（50 节点对 12,235），所以 ASR encoder 撞上的容量上限对它不适用，必须单独测。

| 项 | 值 |
|---|---|
| 模型 | `pyannote-segmentation-3.0.onnx`，50 节点，5,986,908 字节，opset 17，producer pytorch 2.3.0 |
| 运行形状 | `[1,1,160000]`（10 秒窗）→ `[1,589,7]` |
| 作用 | 窗内帧级语音活动与换人点检测 |

### 9.1 先让它能转换：三处改写，全部逐位一致

| 问题 | 原因 | 处理 |
|---|---|---|
| 导出图里有 `If` 控制流 | 条件是 `Shape(x)[1] == 1`，固定 10 秒窗后恒为真 | 内联 `then_branch`（单个 Conv），删掉 17 节点的 `else_branch`；折叠时必须把控制流子图读取的张量算作 live，否则会删掉分支还要用的常量 |
| `MaxPool` 带 `dilations: [1]` | 这是 ONNX 默认值，但 MindSpore Lite 只接受 `<1,1>` | 删掉该属性，语义不变 |
| 1-D MaxPool 形状推断直接失败 | NNACL 池化核只接受 4 维（`Unexpected input format 0`） | 每个池化前后加 Reshape 到 `[N,C,1,L]` |

结果：50 → 46 节点，动态形状与控制流算子全部消除，转出 3,003,048 字节 MindIR，**输出与原图最大差 0.0**。

### 9.2 上机结果

| 后端 | 结果 |
|---|---|
| Kirin NPU | **FAIL**，build 阶段 26.8 ms 即拒绝，而且 **demo 进程直接崩溃**，没有像 ASR encoder 那样干净返回 −1 |
| MS Lite CPU | PASS，build 16.4 ms，单次 min / 中位 / max = 31.8 / 35.2 / 75.0 ms |

接受边界只定位到一半：前 3 节点（`InstanceNormalization` + `Conv` + `Abs`）在 NPU 上可用（中位 25.2 ms），前 8 节点崩溃，嫌疑在提升后的 2-D MaxPool、第二个 `InstanceNormalization`、或 `LeakyRelu`；**4 个双向 LSTM 还没测到**。逐节点二分未完成，记为待办而不是猜测。

### 9.3 一个不依赖 NPU 的线索

同一张图在 MS Lite CPU 上只要 35.2 ms 中位，而当前 ORT 路径约 97 ms/窗（91.8 s ÷ 951 窗）。**这不是受控对比**：ORT 会话被刻意钉成单线程、探针用了 4 线程、探针喂的是零填充输入。但它提示分割这一段在 CPU 侧可能还有两倍以上余量，比继续撞加速器更可能有收益。

逐步证据见 `ASR_ENCODER_NPU_FEASIBILITY_20261008.json` 的 `segmentationModelProbe`。

## 10. 待办

- **验证"ASR 的 CPU 时间里有多少是低功耗自旋"**：ASR 当前开着 `spinning`（ORT 线程忙等），忙等会抬高 CPU 时间但产热很低，这可能正是 181% 只换来 2.06 °C 的部分原因。载体有 `--asr-disable-spinning`，跑一轮仅识别对照即可判定：若 CPU 占用大幅下降而温升几乎不变，就证明这部分时间是低功耗的，8.1 的时间口径需要再加一层修正。
- **削角色分离的尖峰而不是总时间**：既然发热跟尖峰相关，把分割/聚类的突发摊平（例如错开窗口触发、给角色线程更低的 QoS 档）可能比单纯减少 CPU 时间更有效。这需要一轮带尖峰指标的对照来验证。
- **分割模型的逐节点接受边界未定**：前 3 节点可用、前 8 节点崩溃，4–7 之间哪个算子是元凶（2-D MaxPool / 第二个 InstanceNormalization / LeakyRelu）未定，4 个双向 LSTM 未测到。
- **分割换 MS Lite CPU 后端需要受控复测**：9.3 的 35.2 ms vs 97 ms/窗不是受控对比（线程数、输入都不同），要在同线程数、真实输入下重测才能当作收益。
- **60 分钟 RSS 增长**：A 组两档都超过载体 64 MB 阈值（cpu60 108.3 MB、npu60 178.6 MB），NPU 档更高。B 组显示仅识别轮内存判定 PASS（增长 27.3 MB、峰值 568 MB），两个角色分离轮都是 INCONCLUSIVE，所以这一项由角色分离链引入，与 encoder 后端无关。
- **峰值内存反直觉**：B 组 NPU 档比 CPU 档高 45.6 MB；A 组里 NPU 档在 16 与 60 分钟更高（+20.7 / +114.2 MB）、30 分钟更低（−39.8 MB）。三比一说明不是偶然，根因未定位。
- **60 分钟档没有仅识别基线**：B 组只做了 16 分钟，长时发热无法归因到角色分离，要闭合需再补一轮 60 分钟仅识别档。
- **单轮、无重复**：每档只跑一轮，结论是方向性配对差值，不是统计置信区间。
- **角色精度门禁**：帧级一致率只说明两档等价，不等于精度合格。MindIR 仍为 `converted-not-device-accepted`，需要 12 例冻结 RTTM 与人工打分。
- **`auto` 后端**与 NPU 路径上的完整生命周期（finish/shutdown/relicense）真机验证仍为 PENDING。
- **断电场景的绝对温度**：三组全程 USB 充电，`charger` 托底（34.0–42.5 °C），绝对值不能外推。
- 若将来设备或 MindSpore Lite 支持按子图 offload，前缀二分的工具与设备探针都已就位，可直接复测 ASR encoder 与分割模型。
