# 安卓真机复测：热词删数字与机主接话泄露（2026-10-30）

两个客户报的问题在安卓真机上复测。热词那条一次通过；机主换人那条**修复前 6 例中有 4 例泄露**，
定位出两处鸿蒙这一轮才做、而安卓移植时漏掉的判断，补齐后 6/6 通过。

## 器材与身份

| 项 | 值 |
|---|---|
| 设备 | OnePlus PHK110，Android 16，arm64-v8a |
| 分支 | `fix/android-speaker-turn-split`（已并上 main 的 `3e61e956`） |
| 原生库 | `libsherpa-onnx-jni.so` md5 `e29ac540`，由带补丁 0036 / 0037 的源码重编 |
| 喂音频速率 | 20 ms/帧，即实时速率，与鸿蒙那轮 `--pace-ms 20` 对齐 |

**原生库必须重编**：仓库里的 `.so` 是预构建产物、不入库，APK 构建不会重新编译它。鸿蒙那边
第一次真机测试就因此空跑过一次（结果与修复前逐字节相同）。本轮逐层核对了 jniLibs 与主 APK
内那份的 md5 都等于重编产物。

## 一、热词删数字：7 例全对

夹具与鸿蒙 0.3.26 同一份（客户两条原始录音 + 客户 53 词热词表），每例先不带热词解一遍作基线。

| 用例 | 热词 | 结果 |
|---|---|---|
| qf-01 | 客户原样 53 词 | `新手机号是13112345678。` |
| qf-02 / qf-03 | 52 词 / 53 词，不含该热词的录音 | `今天的手机号是13112345678。` |
| qf-04 / qf-05 | 「遣返」/「是遣返」 | 正确 |
| **qf-06** | 「新手机号是遣返」七字前缀探针 | **正确** |
| qf-07 | 「手机号是遣返」，不含该热词的录音 | 正确 |

11 位号码全部完整，没有任何一位被改写成「遣」。

**qf-06 两端不同，不要读成「安卓修得更好」**：这条是构造的最坏情况，热词前六字与录音里的话
一字不差；鸿蒙上修复后仍丢 5 位数字，这台安卓机上过了。两端共用同一份 sherpa 补丁，差异来自
声学路径（设备、音频前端）不同，不是修复程度不同。

## 二、机主接话泄露：修复前 4/6 泄露

夹具与鸿蒙同一份（aishell3 构造，3 条注册 + 6 例「机主一段后无间隙接另一人 1.4~1.6 s」），
判归属而非识别准确率。

先排除了一个夹具干扰：首轮音频是**瞬间灌入**的（所有回调的 `audioMsAtCallback` 都等于全长），
而换人判定依赖滑动窗随时间推进，等于把要测的机制绕过去。改为实时速率后结论不变，整句分
0.711 一字不变，确认是产品缺口。

还修正了一处断言漏判：turn-02 的禁止词取自主机解码写作「永洪」，这台设备解成「永红」，
字不同所以没匹配上，但那一句其实也泄露了。现在禁止词按同音异写的变体列表匹配。

### 缺口一（turn-02 / 03 / 04）：收尾兜底在最该生效时退出了

诊断链条：

```
state=below score=0.298 below=1
resolver=acoustic decision=ambiguous reason=insufficient-refine-context
decision=await-context waitedSamples=0
（音频结束，此后无任何事件）
```

流式已确认离场，声学解析器要求更多上下文再判，而非机主只说了 1~2 s、音频到此为止。收尾补判
入口写的是「已有待处理离场就直接返回」，于是它在最该兜底的场景退出，整句（含非机主）按整句分
0.711 发布。

**修法**：待处理离场正是收尾该退保守前缀的情形——切在最后一次确认还是机主的位置，其后作为
非机主重放。这与鸿蒙 `c2a97bb5` 的同一条判断，移植时漏掉了。

### 缺口二（turn-05）：收尾切片只按配置阈值判，而它落在实测空带里

流式分数最低 0.374 从未跌破 0.35；收尾那 1.2 s 切片打 **0.445**，也没跌破。但 0.445 落在
实测空带（0.35~0.52）中间：

| 段长 | 机主自己最低 | 非机主最高 |
|---|---:|---:|
| 1.0 s | 0.525 | 0.400 |
| 1.5 s | 0.600 | 0.377 |
| 2.0 s | 0.603 | 0.432 |
| 3.0 s | 0.636 | 0.459 |

**修法**：收尾切片按实测下沿 0.45 判离场。切片只有一两秒，正是这条测量覆盖的区间。判错的代价
是机主尾部被保守切点截掉几个字，判漏的代价是把别人的话录成机主的。

鸿蒙上 turn-05 是另一条路拦住的：那边的端点检测把两人切成了两句，非机主独立成句后被句级下沿
拦住。安卓这边没切开，只剩收尾切片这一条路，所以同一个现象需要两处不同的判断。

## 三、修复后：6/6 拦住

| 用例 | 触发路径 | 发布的 final |
|---|---|---|
| turn-00 | `finish-slice-departure` | 而目前英特尔整体业务进展。 |
| turn-01 | `finish-slice-departure` | 昆仑决希望在这个政策利好的年。 |
| turn-02 | `finish-pending-departure` | 对于英特尔来说也难。 |
| turn-03 | `finish-pending-departure` | 祥和饭店辉煌。 |
| turn-04 | `finish-pending-departure` | 搜狐娱乐讯据港媒。 |
| turn-05 | `finish-slice-departure`（切片分 0.44515342） | 来一首死了，都要爱。 |

两条修复各自命中它针对的用例。代价可见：机主句尾被保守切点截掉几个字，turn-04 发布的
「搜狐娱乐讯据港媒。」与鸿蒙同一条的结果一致。

主机回归：`:sdk` 83 个、`:sdk-dingqiao` 143 个 JVM 用例通过。

## 四、仍未解决

- **鸿蒙的收尾切片可能有同样的空洞**。鸿蒙 turn-05 是靠句级下沿拦住的，其收尾切片是否也只按
  配置阈值判，现有夹具没暴露（6/6 通过）。已交付的 0.3.26 不动，记为跟进项。
- **0.45 下沿仍是同会话注册实测**，机主一侧偏乐观。跨会话注册下机主短句会不会被误拒，必须用
  客户真实声纹加一段机主短句复测。安卓与鸿蒙共享这一限制。
- **机主尾部截断**是本修复的既有代价，不是缺陷，但它让机主最后一两个字可能丢失。
- **安卓角色分离仍为 Community 链路**，与鸿蒙的 Sortformer 不一致，待 Android 重建。
- 复测用的是 debug 构建重签授权证书的包，**未覆盖 release（R8 开启）构建**。

## 五、复现方式

音频夹具不入库，构建时用 `-PdingqiaoEvalAudioDir` 外挂：

```
~/.cache/amphion-runtime/android-retest-20261030/eval-audio/
  hotword-qf/{with,without}.wav        客户两条原始录音
  speaker-turn/enroll-0{0,1,2}.wav     注册音
  speaker-turn/turn-0{0..5}.wav        六例换人
```

两个用例在 `DingqiaoCustomerBugEvidenceInstrumentedTest`，按实时速率跑：

```
adb shell am instrument -w -r -e ownerHandoffFrameSleepMs 20 \
  -e class com.amphion.dingqiao.demo.DingqiaoCustomerBugEvidenceInstrumentedTest#bug13OwnerHandoff_doesNotRecordTheNextSpeakersFirstUtterance \
  com.amphion.dingqiao.demo.test/androidx.test.runner.AndroidJUnitRunner
```

应用包与测试包必须用同一张证书签名，且该证书要与授权文件里的 `certSha256` 一致，否则激活报
`code=6005: INVALID`。本轮用 `asr/android/keystore/dingqiao-demo-release.jks` 给两个包重签。
