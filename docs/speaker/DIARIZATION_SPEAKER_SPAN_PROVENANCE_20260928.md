## 症状与第一个错误状态

在前一轮 base 对比中，10 个输入里有 4 个出现整句没有 `speakerTextSpans` 的句子。这些句子对用户显示为 UNKNOWN，即使该时间段已有具名的声学轮次。

按设备事件逐层核对后，第一个错误状态出现在文字层 `presentationAlignment`：发布出去的文本无法与 ASR token 对齐，于是整句不生成任何角色段。ASR 解码、聚类和身份映射都不是原因。导致无法对齐的是 ITN 之后两个没有位置映射的后处理步骤：

| 原因 | 证据 | 涉及 |
| --- | --- | --- |
| sherpa CT 标点模型只在两个 ASCII 词之间保留空格，所以中英之间的空格一定会被删掉 | `text-utils.cc` 的 `MergeCharactersIntoWords` 和 CT 标点的拼接规则；设备上 `WHAT IS 阿拉` 变成了 `WHAT IS阿拉` | 客户录音 1 句 |
| 警务增强（术语、车牌、派出所、人名）改写文字，却没有记录改写位置 | 3 句都是车牌规则把"这这"改成了"浙J" | AISHELL-4 三人片、AliMeeting 三人片、AliMeeting 四人片，共 1188 字 |

"这这"被改成"浙J"本身是一个用户可见的错字。它的根因在警务车牌规则，与角色分离无关，按用户决定另开 PR 修复，本 PR 不改变任何警务输出。

## 修复

1. **标点删空格。** 文字对齐接受一种删除：token 中的空格在展示文本里消失，而且消失处两侧并非都是 ASCII 字符。这与 sherpa 的拼接规则完全一致；两个英文词被粘连的情况仍然无法对齐。提交 `7fdffeb0`。
2. **警务改写记录。** 提交 `0a44add8`。
   - 每个警务步骤把自己的局部改写（在该步输入中的区间 → 新文字）交给 `PoliceTextTrace`，由它逐步合成"原文区间 → 最终区间"的记录。
   - 只要某一步的改写记录不能精确重建该步输出，或该步的输入不是被追踪的文本，追踪就作废，不产出记录。
   - 管线只有在每一步都被追踪时才返回记录。
   - 输出文字仍由原来的改写代码生成，追踪只是旁路记录。
3. **文字层如何使用记录。** 只有在直接对齐失败、并且存在警务记录时才使用：
   - 未改写的区间按字符继承 token 的归属；
   - 被改写的区间作为一个不可拆分的单元，内部若有换人，只把这个单元标为 UNKNOWN；
   - 插在边界处的文字（例如补上的句号）跟随前一个单元；
   - 没有记录时仍然不做任何猜测。
4. **作废的首版方案。** 首版按标点分句、每句单独做一遍警务增强再拼回来，在真机上 3 句全部被拒：派出所规则会把整句结尾统一改成句号，分句处理与整句处理的结果对不上。该方案已被本方案替换，首版真机结果标为 non-canonical。

## 附属问题：voiceprint-vad-begin-idle 偶发超出判定窗口（既有，与本 PR 无关）

- **症状。** 该模式要求声纹 + `vadBegin=1000` 的空闲会话在第 45–70 帧之间自动结束。上一轮真机有 1 轮在第 71 帧才结束。
- **对照。** 在同一台设备上，分别安装 base（`origin/main` `04e053c4`）和本 PR 的构建，各跑 20 轮：

  | 构建 | 静音结束帧 | 噪声结束帧 | 超窗轮数 |
  | --- | --- | --- | --- |
  | base | 65–70 | 66–71 | 1/20（第 71 帧） |
  | 本 PR | 65–72 | 67–72 | 4/20（第 71–72 帧） |

  base 同样会超窗，这是既有问题，不是本 PR 引入的。每帧 30 ms（20 ms 音频加 10 ms 节拍），70 帧约 2.1 秒，超窗 1–2 帧相当于 30–60 ms 的调度延迟。
- **未证实。** 本 PR 的结束帧分布整体偏晚约 1–2 帧。本 PR 对音频路径唯一的新增开销，是每条 final 多一次警务追踪；但空闲会话没有非空 final，不会执行这段代码。两轮各 20 次的差异可能只是调度抖动，现有证据不足以下结论。
- **处理状态。** 判定窗口没有修改，也没有放宽。该门禁在 base 上同样会偶发失败，需要单独定位 `vadBegin` 计时与载体节拍的关系。
