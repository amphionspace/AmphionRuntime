# 角色分离三项改动的 2 小时真机验证（2026-10-16）

同机（Mate 80）、同语料（客户原始录音循环至 7332 秒的单一连续会话）、同参数
（hop 2000、4 线程、亮屏前台、diagnostics 构建）与基线对照。

基线为 0.3.23 代码（`delivery/candidate-reports/harmony-0.3.23-20261015`），
本轮为 `c8cd4b51`，含三项改动。

## 二、逐项结论

### 2.1 预览预算减半：达到预期，是全部收益来源

534.1 → 269.3 s，预览次数 255 → 148。与设计预期（约 279 s）吻合。
**本轮 −21.9% 的总收益全部来自这一项。**

### 2.2 聚类上限：本轮持平，符合预期

198.7 → 202.2 s。该项的作用是消除随会议时长的超线性增长，已在前一轮验证
（指数 2.0 → 0.85）；在固定 2 小时长度上不产生额外收益，持平即正确。

本轮实测增长指数 0.69（窗口 398→3663 为 9.20×，耗时 1324→6073 ms 为 4.59×）。

### 2.3 证据缓冲复用：归因被证伪，改动已撤回

**提出的依据**：基线中 RSS 峰值随窗口数涨 399 MB，而单次证据读取只涨 58 MB，
据此推断同时有六七代缓冲区未被回收，改为复用一个只增长的存储即可消除该倍数。

**实测否证**：峰值几乎未动（1152.3 → 1160.0 MB）。本轮拿到的逐点 `VmHWM` 曲线
显示峰值是**单调上升**而非锯齿堆积：

| 分钟 | 20 | 40 | 61 | 81 | 101 | 121 |
|---|---|---|---|---|---|---|
| HWM MB | 757 | 855 | 925 | 983 | 1120 | 1222 |

单调上升说明峰值不是"多代缓冲区同时存活"，而更可能是堆在单次大块分配下持续扩张
且不归还。复用缓冲区因此解决不了它。

净效果是此消彼长：内核 HWM −57.4 MB，但结束 RSS +52.6 MB、斜率 +0.3 MB/min——
复用的存储按最大前缀（1.25 倍过冲，约 91 MB）常驻到会话结束，而原先可被回收。
两者差值均在单次对照的波动范围内，无法判定为收益。

**该改动已撤回**（分支删除，未进主线）。它换掉了 `DiarizationEvidenceSpool.read()`
"快照拥有自己的存储"这一有名字的保证——改为"快照只在下次读取前有效"。当前唯一
生产调用点安全，但对未来调用者是静默读错数据的坑。用一个被证伪的归因换掉这个保证
不成立。

## 三、温升曲线

基线那轮因采样接口用错（`/sys/class/thermal/` 对 shell 用户为 Permission denied）
未取得，本轮改用 `hidumper -s ThermalService -a -t` 取得：

```
31.8 → 39.8 °C（峰值），会话期 0.066 °C/min
```

与客户 10-15 晚锁屏段实测的 **0.065 °C/min** 几乎一致。两小时会话仅靠推理本身即可
把机身从 31.8 升至 39.8 °C——接近该客户记录到热等级 2 的 39.1 °C，印证此前"长会议
自身即可摸到温控线"的外推。

## 四、仍未解决

- **内存峰值约 1.15 GB / HWM 约 1.22 GB**。成因未定位：已知 HWM 单调上升，已排除
  "多代证据缓冲堆积"。下一步应先解释该单调上升，再动代码。
- **无遇热或按积压降级的机制**（本轮按要求不处理）。
- 设备发热的主体仍是屏幕与整机负载，不在 SDK 侧。

## 五、口径限制

单次对照，未做重复性检验；50 MB 级的内存差异在约 900 MB 基数上处于单次波动范围内。
diagnostics 构建的绝对值不可直接当作发布指标。
