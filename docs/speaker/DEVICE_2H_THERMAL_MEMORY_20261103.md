- 日期：2026-11-03
- 设备：`7GK0226326015655`（HarmonyOS）
- 被测包：设备上已安装的 `com.amphion.asr.harmony.demo`（`--installed-package`，包身份已记入 `installed-bundle.json`）
- 实际时长：**143.8 分钟**（2.4 小时），2100 cycles，`--mode paced --pace-ms 20`（20 ms 帧 = 实时速率）
- 配置：启用角色分离 + **声纹身份**（`--speaker-identity-mode voiceprint`）、`--diarization-display-may-turn-off`

### 1.2 必须扣掉环境漂移

**环境温度自己涨了 3.4°**（23.4° → 26.8°），所以机身的 +5.6° 里有一大半不是设备自己发的热。看"机身 − 环境"的差值才是设备的自发热：

| | 起始 | 峰值 | 终值 | 净升幅 |
|---|---|---|---|---|
| shell_back − ambient | 5.4° | 9.1° | 7.6° | **+2.2°** |

**设备真正的自发热只有 +2.2°。** 原始读数 +5.6° 会把房间升温算进来，对外报数应该用净值。

（环境为什么会涨 3.4°：机器自身散热 + 房间无强制通风。这正是必须做此修正的原因。）

### 1.3 是否进入热平台

取后壳 `shell_back` 分段回归：

| 时段 | 中位温度 | 升温斜率 |
|---|---|---|
| 0~20 min | 31.5° | **+10.60 °/小时** |

| 40~70 min | 33.9° | +0.93 °/小时 |

斜率衰减近 50 倍，**70 分钟后基本停止升温**。这是明确的热平台，不是还在爬升被观测窗截断。

按末段 +0.22 °/小时外推，再跑 8 小时也只会再升不到 2°。**长会工况下发热没有风险。**

## 2. 内存

`--sample-interval 2.0`，3451 个采样点，覆盖 143.5 分钟。

### 2.1 分段中位

不看首尾差——首尾差受采样时刻的瞬时抖动支配。看八等分的分段中位：

| 段 | 时间 | 中位 | p90 | 最大 |

| 2 | 17.9~35.9 min | 698 MB | 722 | 863 |
| 3 | 35.9~53.8 min | 739 MB | 762 | 859 |
| 4 | 53.9~71.7 min | 770 MB | 793 | 909 |
| 5 | 71.8~89.7 min | 788 MB | 813 | 940 |

| 7 | 107.7~125.6 min | 797 MB | 815 | 947 |
| 8 | 125.6~143.5 min | 809 MB | 827 | **1001** |

### 2.2 判定：饱和型，不是泄漏

- 7 个相邻台阶中 **6 个上升**（第 7 段比第 6 段低 3 MB，属抖动）
- **前半段累计 +112 MB**，后半段几乎不动
- **末三段跨度只有 12 MB**（797~809 MB）
- 斜率：全程 +71.2 MB/小时 → 后半程 **+17.4** → 最后 1/4 **+28.0** MB/小时

形态是**前段明显上升、后段进入平台**，收敛在约 800~810 MB。这是缓存/池类结构填满的典型形状，**不是无界泄漏**。

注意最后 1/4 的斜率（+28.0）略高于后半程（+17.4），所以不能说已经完全收敛到零。但以末三段 12 MB 的跨度看，残余增长的量级远小于前段。

### 2.3 需要关注的是峰值，不是增长

| | 值 |
|---|---|
| RSS 峰值 | **1000.6 MB** |
| HWM（历史最高水位）峰值 | **1044 MB** |
| 平台期中位 | ~805 MB |
| 线程数 | 53 → 53（**零增长**）|
| vm_data 增长 | +65 MB |
| swap 峰值 | 80 MB |

**峰值已经摸到 1 GB。** 平台中位 805 MB 与峰值 1001 MB 之间有近 200 MB 的瞬时波动，意味着某个阶段会短时多占 200 MB。这是本次最值得跟进的一项——不是因为它增长，而是因为它的绝对水位和波动幅度。

压测脚本的通用 RSS 预算是 64 MB，本次增长 80.6 MB 超预算（`generic=FAIL`），但角色分离场景下该项是 advisory，所以 `overall=PASS`。脚本自己的判定是 `INCONCLUSIVE`——它需要阶段对齐的证据才能给结论，而本次没有做阶段标注。

## 4. 本次测量的边界（必须随结果一起说）

1. **这是单臂绝对测量，不是 A/B。** 本次全程开着 `--speaker-identity-mode voiceprint`（CAM++ 声纹），**没有跑关闭声纹的对照臂**，所以**不能**从本报告得出"声纹身份带来多少额外发热/内存"。要回答那个问题需要再跑一次 `model` 模式的同配置长跑。
2. **语料不是会议长音频。** 默认设备语料是 500 条短 WAV（合计 0.48 h，44.1 kHz），选中 24 条共 85.9 秒，靠 2100 次循环凑满 2.4 小时。所以这是**反复起停的持续负载**，不是"单个会话连续两小时"。真正的单会话长跑要用 `--mode continuous-long-session`，但它强制要求 `--expected-tail-manifest`，而仓库里没有现成的清单——**这是一个待补的测试资产**。
3. **温度是我并行采的，不是压测脚本产出的。** `--sample-power` 的 `report.json` 里只有 CPU 占用统计，**没有任何温度字段**。温度由 `thermal_sampler.sh` 用 `hidumper -s ThermalService -a -t` 每 30 秒采一次。注意 `-t` 不能加引号，加了会被当字面量，这是之前误判"该设备读不到温度"的原因。
4. **内存判定 `INCONCLUSIVE` 是脚本的保守口径**，它要求阶段对齐的证据（哪段是推理、哪段是空闲）才给结论，本次未做阶段标注。本报告的"饱和型"判定来自分段中位形态，是我的分析，不是脚本的判定。

## 5. 建议

1. **发热可以结案**：净自发热 +2.2°、70 分钟进入平台、末段斜率 +0.22 °/小时。长会工况无发热风险。对外报数用**净值 +2.2°**，不要用原始 +5.6°（含房间升温 3.4°）。
2. **把内存峰值立为跟进项**：RSS 峰值 1000.6 MB、HWM 1044 MB，平台中位 805 MB 与峰值之间波动近 200 MB。要查的是**那 200 MB 的瞬时占用来自哪个阶段**，而不是查泄漏（形态已排除无界泄漏）。
3. **给压测脚本补温度采样**。`--sample-power` 名字像是采功率，实际只有 CPU。否则每次发热测试都要外挂采样器，且容易再次误判"读不到温度"。
4. **补 `--expected-tail-manifest` 测试资产**，否则 `continuous-long-session`（真正的单会话长跑）无法使用，只能用反复起停的 `paced` 近似。
5. **若要回答"声纹身份的发热/内存代价"，需补一次 `model` 模式对照臂**。本次无对照，不能从这份数据推断。

## 6. 复现

```bash
# 温度采样（必须单独跑，压测脚本不采温度）
<scratch>/thermal_sampler.sh <输出>/thermal.csv 30 &

# 两小时压测（2100 cycles ≈ 143 min，语料平均 3.58 s/条）
HDC=<绝对路径>/hdc python3 delivery/harmony-dingqiao/delivery/run_device_stress.py \
  --mode paced --cycles 2100 --timeout 9000 --pace-ms 20 \
  --enable-diarization --speaker-identity-mode voiceprint \
  --sample-power --diarization-display-may-turn-off \
  --sample-interval 2.0 --installed-package \
  --output-root <输出>

# 报告
python asr/tools/speaker/31_report_thermal_longrun.py \
  --run-dir <输出>/<run-id> --thermal <输出>/thermal.csv
```

踩过的坑，供下次参考：
- `HDC=~/...` 在 `env` 赋值里 `~` 不展开，必须用绝对路径
- `--skip-build-install` 与 `--installed-package` 互斥
- `--mode continuous-long-session` 强制要求 `--expected-tail-manifest`
- cycles 的含义是**文件数**，不是语料遍数；默认语料平均 3.58 s/条，260 cycles 只有 17.7 分钟
