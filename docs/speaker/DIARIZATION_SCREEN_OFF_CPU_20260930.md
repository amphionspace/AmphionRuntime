# 息屏期间角色流水线的实测行为与限定（2026-09-30）

**结论：息屏后角色流水线的吞吐掉了约一个数量级并最终完全停滞；进程级 CPU 记账从约 2.8
CPU-s/墙钟秒直接归零。机制类别是"后台可用算力"，不是降频、也不是计算量不足。但本次复现的
"完全停摆"极可能是测试载体造成的，尚不能算到 SDK 头上，需用真实采集路径复核。**

本轮为只读测量，未修改 SDK 运行代码。

## 测量口径的更正

前一版用 `/proc/<pid>/stat` 的 utime/stime 逐线程汇总，得出"工作时 0.058 CPU-s/秒"，
与诊断记录的工作量矛盾；该文件在设备 shell 下被截断，口径不可用。**改用 OS 自身的
`ps -o TIME -p <pid>`（进程累计 CPU 时间，1 秒分辨率）**后，工作期间为 1.1–2.8 CPU-s/秒，
与多线程流水线相符。后续所有 CPU 速率均以此为准。

## 实测

同一台 Mate 80（`7GK0226326015655` / OpenHarmony-6.1.1.120）、960 秒会议语料、实时 20 ms 步长、
ASR 配置 `cpuIds=[4..11] spinning=false numThreads=4`、角色开启、`numThreads=4`。

### 进程 CPU（`ps -o TIME`）

| 阶段 | CPU-s/墙钟秒（中位） | 采样 |
| --- | ---: | ---: |
| 亮屏且在工作 | **2.799** | 6 |
| 息屏之后 | **0.000** | 57 |

CPU 累计停在 279 s 后连续约 520 秒零增长，屏幕状态 118/127 采样为 `SLEEP`。

### 逐核频率

息屏前后逐核最高频率 2112 → 1805 MHz（−15%）。**频率基本没降，所以不是降频。**

### 应用自报诊断（设备事件文件）

| 指标 | 亮屏 | 息屏 |
| --- | --- | --- |
| 单窗墙钟 `elapsedMs` | 约 620 ms | 5,764–7,522 ms |
| `embeddingMs`（encoder+pooling） | 429 ms | 4,458–4,911 ms |
| `audioDelayMs` | 620 ms | 48,800 ms 单调增长 |
| `pendingJobs` | 0 | 触顶 |
| 结果 | SDK PASS | 30 分钟等不到会话摘要，诊断冻结在 121.5 s 音频（ASR 仅到 66.4 s） |

## 关键限定：这很可能不是客户的条件

1. **完全冻结无法由绑核解释。** 用户反馈是"之前绑核解决了息屏解析变慢"，说明客户现场息屏后
   进程**仍在跑、只是变慢**；而本次测得的是 **CPU 精确归零的硬冻结**，绑核对硬冻结没有任何作用。
   两者不是同一个现象。
2. **载体没有真实音频活动。** 压力载体确实持有 `BackgroundMode.AUDIO_RECORDING` 连续任务
   （`EntryAbility.runStressWithBackgroundRecording`），但它**从文件喂入、不打开麦克风**。
   为复现息屏，载体还释放了窗口常亮锁。系统很可能因此判定该应用没有正在进行的音频活动而将其挂起。
   客户应用持续采集，不受这一条影响。

因此本次量的"息屏停摆"只能说明**机制类别**（后台可用算力），不能作为"SDK 在息屏下卡死"的证据。

## 与历史观察的一致性

- 只跑 ASR 时负载低、余量大，息屏带来的算力损失可以靠绑核 / `allowSpinning=false` 补回来，
  所以当时症状消失：**那治的是调度症状，不是计算量**。
- 角色开启后每 1 秒音频要花约 0.6 秒 CPU（单窗 native 中位 575 ms：segmentation 124 + fbank 22 +
  encoder/pooling 429），余量只剩约 1.6 倍；同一量级的后台损失就会造成无界积压。

## 下一步（判定性）

用**真实采集**（或保持一个活跃的 AV 会话）重跑同一息屏配方，再比较：

- 若 CPU 仍约 2.8 CPU-s/秒但单窗仍旧变慢 → 问题在推理路径内部（内存/锁/调度），不在后台配额；
- 若 CPU 部分下降（非归零）→ 属于后台调度，修复方向是后台执行与 QoS/绑核覆盖到角色线程与
  XNNPACK worker，而不是削减计算。

复现脚本与遥测位于 `.cache/speaker-screen-repro-acf477c2/`（`run_arm.sh`、`sample_cpu.py`、
`analyze_arm_thermal.py`、`armOffScreenCpu/`）。

## 与跨窗复用证伪的关系

同一轮另证明"每秒重算整窗"的计算冗余**不可消除**（逐窗 mel 去均值使特征与窗口绑定）。因此
"降低单窗成本"这条路只剩模型层改动，需要独立的身份精度评估；后台调度这条路则依赖上面的判定。
