# 离线角色分离：发烫与锁屏变慢的结论（2026-09-30）

本文是这两条用户问题的汇总结论，细节与原始数据见三份专题记录：

- `docs/speaker/DIARIZATION_SCREEN_OFF_CPUSET_20260930.md`（锁屏变慢的根因与产品配置实测）
- `docs/speaker/DIARIZATION_THREAD_OVERHEAD_20260930.md`（角色链路的 CPU 成本与线程预算）
- `docs/speaker/DIARIZATION_CROSS_WINDOW_REUSE_FALSIFIED_20260930.md`（跨窗复用证伪）

设备口径：Mate 80 `VYG-AL30` / OpenHarmony-6.1.1.120 / `7GK0226326015655`；ASR 统一
`cpuIds=[4..11] spinning=false numThreads=4`；CPU 用 OS 自身 `ps -o TIME -p <pid>` 记账。

语料口径（区分冻结资产与派生切片）：

| 语料 | 来源 | SHA-256 |
| --- | --- | --- |
| 960 秒会议 | 由带标注的 `S_R003S01C01.flac`（源 `e4a8a763…`）自第 540 秒起截取 960 秒，配尾清单 | `66133c62a0f6da69d2b98d96a5d193816e73899fa28340313beb146309c9167d` |
| 120 秒切片 | **由上面 960 秒语料中段派生**（非仓库冻结资产），仅用于短臂对比 | `2fc6d548fa3393e19e0e…` |

因此涉及"仓库冻结语料"的结论只取 960 秒长臂；120 秒切片上的对比（线程预算、成本构成）标注为派生
语料，不当作冻结资产证据。

## 结论一：发烫来自角色分离自身的推理计算量

**原因：角色链路在 1 秒步长下持续占用 CPU，其中 encoder 占 70–76%。它不是空转、不是绑核问题、
也不是并发屏障可回收的浪费。**

证据：

1. 同机、同语料、同 ASR 参数下**只有角色开关不同**：角色关闭 30–31 ℃ 20 分钟全程平；角色开启
   30.7 → **41.4 ℃**（16 分钟），电池到 42 ℃。
2. 产品配置（关诊断）下角色链路增加 **+1.641 CPU-s/墙钟秒**（关闭 0.850、4 线程 2.491）。
3. 单窗成本构成：**encoder + pooling 占 70%（亮屏）/ 76%（锁屏）**，segmentation 15–19%、
   fbank 3–4%、聚类 6–7%。
4. **空闲空转被证伪**：把 XNNPACK 线程池的 spin 常量约束到 4096 后重测，CPU 2.641 → 2.675（噪声内），
   补丁已撤回，重建的库与修复前逐位一致。
5. **唯一零精度代价的可回收项**：encoder 4 → 2 线程，省 0.29（诊断）/ 0.34（产品）CPU-s/墙钟秒，
   约整进程的 11–14%，单窗耗时不变且判定 PASS。1 线程会让角色链路降级，不可用。

**已交付**：`SpeakerDiarizationConfig.numThreads` 现在**真的生效**（此前因原生参数解析缺陷从未生效，
见下）；调用方可据此选择预算。

**未解决**：剩余降本必须改模型。可行性前置实验已给出两端数据：

| 维度 | 结果 |
| --- | --- |
| 体积 | 21.3 MB → **5.4 MB** |
| **设备端（ARM）单窗 encoder** | **427 → 315 ms（1.36×）** |
| **设备端整进程 CPU** | **2.665 → 1.474 CPU-s/墙钟秒（−44.7%）** |
| 整窗 embedding 偏移 | **13.4% 相对 L2（余弦 0.991）** |
| 管线运行 | 两臂均 PASS（生命周期判定通过） |
| 同输入角色输出差分（120 秒） | 轮数、轮时长、句级标签、每窗人数**逐项相同** |
| 同输入角色输出差分（**360 秒**） | **有 1 处身份翻转**：同一 405 ms 区间 FP32=说话人 1、INT8=说话人 0；轮数/时长/句级标签相同 |

收益足以覆盖目标：角色链路占 +1.79 CPU-s/墙钟秒，可回收约 1.2；按 encoder 快 1.36× 推算，锁屏
RTF 0.962 有望降到约 0.7，正是所需余量。代价是 13.4% 的 embedding 偏移**足以影响 PLDA 打分与聚类
判定**，因此**必须先过身份精度门禁**（两臂无身份真值，不能据此判定身份精度）；在此之前发烫没有可交付
的修复。

## 结论二：锁屏变慢是系统把应用限制到 4 个小核

**原因：屏幕熄灭后 HarmonyOS 把该应用的 cpuset 从 `0–11` 收窄到 `0,1,2,3`。所有推理阶段因此均匀
变慢 3.5–4.8 倍。应用无法放宽自己的 cpuset，所以"绑核"在锁屏下从机制上不可能生效。**

证据：

1. `Cpus_allowed_list`：亮屏 `0–11`；锁屏 **229/230 个采样是 `0,1,2,3`**。
2. 所有阶段均匀变慢，**包括完全没有线程池的 fbank（3.7 倍）**，倍数在 977 秒内稳定。
3. 预算算术解释客户现场：仅 ASR 需 0.85 CPU-s/s，×3.7 后 4 个小核够用（0.3.13"不延迟很多"）；
   ASR+角色需 2.64，×3.7 后远超预算（0.3.19 明显变慢）。
4. 产品配置（关诊断）960 秒锁屏实测：角色 **RTF=0.962、未降级、识别出 2 位说话人**——角色能跑，
   但只剩 4% 余量。
5. **收尾失败**：4% 余量使 960 秒会议累计落后约 38 秒，`finish` 后仍需处理完才能定稿，超过载体
   30 秒等待窗，因此没有 `isLast`/`complete`。**对照**：同样 960 秒、同样角色配置，亮屏臂
   `overall=PASS, completes=1`。

**已交付**：
- 引擎级调度（QoS/绑核）已覆盖到角色链路，并有**运行时证据**：亮屏下开启角色后新增 2–3 个亲和性被
  收窄为 `4..11` 的线程（与 XNNPACK 池规模一致），进程掩码仍为全部 12 核；
- 真实麦克风采集载体 `--hold-mic-capture`（判定"冻结"是否为载体假象的前提）。

**明确限定**：调度覆盖只对**亲和性**成立，QoS 不会被 `pthread_create` 继承；且在锁屏 cpuset 为
`0,1,2,3` 时请求 `4..11` 无法生效。**调度层不能修复锁屏问题。**

**未解决**：把锁屏 RTF 从 0.96 压到 ≤0.7（约需再降 30% 计算量）只能靠模型层改动；收尾等待随会议
时长增长需要有界定稿或更快的流水线。

## 已证伪或撤回的假设（避免重走）

| 假设 | 结论 | 依据 |
| --- | --- | --- |
| 跨窗复用 fbank/encoder 可消除"每秒重算整窗" | **证伪** | 逐窗 mel 去均值使特征与窗口绑定；共享帧差异 0.2533 且均匀遍布整窗；encoder 输出网格 80 ms 与 1 s 步长是 12.5 帧非整数关系 |
| 锁屏是进程被硬冻结 | **部分证伪** | 硬冻结是"文件喂入、无真实采集"的载体假象；真实存在的是小核限流 |
| 锁屏下角色完全跑不动 | **证伪** | 产品配置 RTF 0.962、未降级、有角色输出；此前结论来自诊断构建 |
| 发烫来自 XNNPACK 线程池空闲空转 | **证伪并撤回补丁** | 约束 spin 后 CPU 无变化（2.641 → 2.675） |
| 有 0.73 CPU-s/墙钟秒的并行开销可回收 | **撤回** | 依据的 1 线程臂实为 FAIL（`degraded speaker result`），CPU 低是因为停止工作 |
| 长会"无法收尾" | **部分撤回后重新确认** | 早先两臂 `--timeout 900` < 960 秒语料，结论无效；用 1800 秒重跑后确认收尾确实失败，机制见上 |

## 过程中修掉、且此前会让修复失效的缺陷

1. **`numThreads` 从未生效**（`b94e53d3`）：原生 `Queue()` 把线程预算绑定在"参数个数正好 2/6"上，
   而 ArkTS 始终传 3/7 个参数。所有 Harmony 调用方静默退回 4 线程。
2. **QoS 借用线程策略泄漏**：`OH_QoS_GetThreadQoS` 失败时仍改写并重置未知策略；现改为跳过。
3. **平台头文件被包含在匿名 namespace 内**（`<sched.h>`/`<qos/qos.h>`），宿主切片掩盖了它。
4. **提交缺少 `libqos.so` 链接**，OHOS 分支会缺符号。
5. 上述四项均有会在旧行为下变红的行为测试；分支共 20 个提交，鸿蒙契约测试 499 项全绿。

## 仍需决策

1. **是否启动 encoder 量化/换小模型**（唯一能同时降发烫、并把锁屏 RTF 压到 ≤0.7 的路）。前置实验
   已完成：体积降到约 1/4，但 embedding 偏移中位 13.4% 相对 L2，**需先过身份精度门禁**；
2. ~~**默认线程预算是否改为 2**~~ **已由真机数据否决**：锁屏（4 小核）下 2 线程会让角色链路降级
   （`cycle 0: degraded speaker result`，`completed_sessions=0`），而 4 线程同条件 RTF 0.962、未降级。
   保持默认 4；2 仅适合确定不锁屏运行的场景，不能作为会议录音默认。**发烫在软件层已无可回收空间**，
   只剩模型层；
3. **是否实现有界定稿**（`finish` 后限时用已到证据定稿，尾部标记角色不可用），把随会议时长增长的
   等待变成有界。
