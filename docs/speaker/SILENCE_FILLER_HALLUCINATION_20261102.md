# 不说话时被转写出"嗯"（2026-11-02）

客户报：鸿蒙离线识别在**没有人声输入**的情况下，会多次转写出"嗯"。客户提供了复现音频
`嗯问题.wav`（52.22 s）。

本文件记录机制定位、为什么原有门禁挡不住、修法、以及实测出来的阈值安全带与**一条已知限制**。

## 一、客户音频的事实

| 区间 | 内容 |
|---|---|
| 0~7 s | **逐位精确的数字零**（−240 dBFS） |
| 7~10 s | 真实人声，右声道 RMS −27.5 dBFS（峰 −18.2） |
| 10~52 s | RMS **−92.7 dBFS**，最大 20 ms 窗 RMS **−89.9 dBFS** |

16 位的 1 LSB 是 −90.3 dBFS，所以 10 s 之后整段幅度只有 ±1~3 个量化级——是量化残渣，
不是房间噪声。

文件是 **16 位立体声**，左声道逐样本全零，内容全在右声道。而 SDK 的输入契约是单声道
16 kHz Float32，**所以这个文件不是 SDK 实际吃进去的数据**；0~7 s 的精确零与之后的抖动
是两种不同的静音，也说明它经过处理。下面的分析都在右声道单声道化之后做。

## 二、这个文件过我方链路不复现

主机链路（`decode_streaming.py` + 警务模型 1.4.0 + 流式端点）：

- **原始音频**：42 秒近静音里 **0 条文本**，只在 10.9 s 吐出一句 `呃好的现在就`（对应真人声）。
- **过真实 AGC 后**：AGC 只加 **7.2 dB** 固定增益（封顶是 4 dB 固定 + 20 dB 自适应），静音段
  完全不爬升，输出 −85 dBFS；解码仍然 0 条多余文本。**AGC 排除**。
- **部分结果**：单调延伸 `呃好的` → `呃好的现在就`，没有反复发布同一个字。

## 三、但顺着它挖出了机制：前面的真人声给解码器"上膛"

拿该文件 10~52 s 的真实尾段噪声做对照实验，只改前缀：

| 尾段电平 | 前面放 3 秒真人声 | 前面放 3 秒数字零 |
|---|---|---|
| −92.7（原始） | 29.5 s「是」 | — |
| −90 / −88 / −82 | — | — |
| −86 / −84 / −80 / −75 / −70 | 32~38 s「是」 | — |
| 放大到 −20（加 72.7 dB） | — | **—** |

两条结论：

1. **"数字零在前"九个电平全部不出文本。** 这段噪声本身哪怕放大 72 dB 也不会被幻听成语音。
2. **"真人声在前"就会出**，包括原始未放大的 −92.7 dBFS，且随电平跳动、不单调。

所以**与输入电平无关**，是前面的真人声让解码器状态带上了上下文，之后在长静音里吐出
零散短 token。（注意：客户报的是"嗯"，这里复现出的是"是"、`ESPECIALLY`、`商家` 等；
同一类现象，具体 token 不固定。）

## 四、为什么原有门禁挡不住

`EffectiveSpeechBuffer.resolveFinal` 两端逻辑相同，**只在文本为空时才可能不发布**：

```
if (publicText.length === 0) { ... return Decision(false, empty); }
return Decision(true, take(asrSpeechConfirmed));   // 非空文本无条件发布
```

它算的 RMS/ZCR run 是给**说话人打分挑样本**用的（`boundary.samples`）；`hasEvidence` 也只是
"识别器吐了东西"，不是声学证据。唯一会丢弃无声学支撑文本的是 `InitialSilenceTracker`，
而它**只管会话开头的静音**——一旦前面出现过真人声就不再适用。这正好与第三节的实验吻合。

## 五、修法

给**文本发布**加一道独立判定：非空文本必须有**独立于识别器**的证据，否则按
`RESULT_SUPPRESSED` 丢弃。证据取两者之一：

1. 按新增的 `PUBLISH_RMS_THRESHOLD = 0.0002`（≈ −74 dBFS）确认的声学 run
   （连续 ≥3 个 20 ms 窗、ZCR ∈ [0.005, 0.35]、run 内 `maxRms ≥ minRms × 3`）；
2. 原生 VAD 确认过的 run（新增 `vadConfirmed`，**只由 `confirmSpeech()` 置真**）。

两个关键设计点：

- **不能复用 `externallyConfirmed`。** 它也会被 `asrSpeechConfirmed` 置真，而那来自识别器
  自己，拿它验证识别器的文本是**循环论证**。所以新增了只由原生 VAD 置真的 `vadConfirmed`。
- **不能复用 0.01 那条阈值。** 见下节：拿它决定发布会丢掉 13.3% 的真实远场结果。它继续
  只服务说话人打分。
- `processedWindows == 0`（自上次 reset 起一个窗都没喂过）时放行：这时没有判据，且那段
  音频已在上一次 terminal final 发布过。运行时持续喂音频，幻觉场景不会落到这里。

## 六、阈值安全带（实测）

用**真实 Kotlin 门禁**跑三组真实音频（全程不调 `confirmSpeech()`，所以只认声学那一支）：

| 阈值 | 远场语音丢弃 | AISHELL-3 丢弃 | 客户静音尾段 |
|---|---|---|---|
| 0.01（原值，−40 dBFS） | **12/90 (13.3%)** | **61/500 (12.2%)** | 丢弃 ✅ |
| 0.005（−46） | 2/90 | 3/500 | 丢弃 ✅ |
| 0.002（−54） | 0/90 | 0/500 | 丢弃 ✅ |
| **0.0002（−74，采用值）** | **0/90** | **0/500** | 丢弃 ✅ |

被丢的真实语音在 −39.5~−42.2 dBFS，而通过的最弱在 −41.7 dBFS——**两者重叠**，所以 0.01
这条线不是"略紧"，是正好压在远场语音的分布中间。

安全带：**上沿 −54 dBFS**（再高就开始丢真实语音），**下沿 −89.9 dBFS**（客户尾段的最大窗
RMS，阈值必须高于它才拦得住），宽约 36 dB。取 −74 dBFS，两头各留 20 / 16 dB。

原生 VAD 这一支也实测过不会被绕过：Silero（阈值 0.5、窗 512、`minSpeechDuration` 0.25 s）
在客户那段 42.2 s 近静音上判出 **0 段**，在同文件真人声上判出 1.38 s。

> Python 复刻的门禁在阈值 0.01 下与 Kotlin **逐条一致**（丁桥 78/12，客户三段一致），
> 上表的扫描据此可信。

## 七、已知限制（必须一并交代）

丁桥现场 **204 段真实房间静音**（录音里无文本的端点段，≥1 s）的最大窗 RMS：
**中位 −24.4 dBFS、p5 −38.7、最低 −44.2** —— 全部远在安全带上沿之上。

**所以这道门禁挡的是近似数字静音，挡不住普通房间噪声里的幻觉。** 在任何能保住真实远场
语音的阈值下，真实房间静音都会放行（0.0002 时 196/204 放行）。

因此**本修法是否覆盖客户现场，取决于 SDK 实际收到的是近似数字零还是房间噪声**。客户
提供的文件显示是前者，但该文件不是 SDK 输入（第一节），不可作准。

## 八、还需要客户侧的一件事

要一次**SDK 侧的输入转储**（SDK 实际收到的单声道 16 kHz PCM），或者告知 `嗯问题.wav`
是怎么生成的。若现场其实是房间噪声，本修法不够，需要另找信号。

## 九、变更的对外可见性

非空文本在无独立证据时不再发布。实测对真实语音的影响为零（丁桥远场 90 段、AISHELL-3
500 条均 0 丢弃），但这毕竟是行为变化，已写入两端变更日志。
