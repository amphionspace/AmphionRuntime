# 安卓整机（BRA-AL00）离线 ASR 发热：方案与结论

- 日期：2026-11-10
- 对象：`分报告-整机锁屏离线ASR一小时长时验证-20261103.md` 所述发热问题（BRA-AL00，Android 12，12 核）
- 状态：方案 + 结论；本轮**未在手机上跑真机**（无设备，用户决定先不跑）
- 适用范围：安卓手机侧离线 ASR 长时运行的功耗/温升治理；EC521S 记录仪同源

## 1. 手机侧事实（来自既有报告）

| 项 | 数值 |
| --- | --- |
| 时长 / 形态 | 60.7 分钟，锁屏，mic 型 FGS 豁免 |
| 后壳温升 | 31.1 → 41.6 °C（**+10.5 °C**） |
| 电池 | 30.0 → 41.0 °C（+11.0 °C），约 12 %/小时 |
| 温控 | Thermal 0 → 2（10 min）→ **3（40 min 起）** |
| 应用 CPU | 语音段瞬时 **234~434 %**，静音段回落约 50 % |
| 及时率 | lag 均值 1.9 s、峰值 5.4 s，≈99.9 % 实时 |
| 对照（鸿蒙） | 同场景 +4.5 °C，因鸿蒙 encoder 走 NPU |

报告自身给出的跨端结论是：**安卓侧把离线推理全压在 CPU 上**，这是温升高于鸿蒙的直接原因。

## 2. 根因拆解

1. **CPU 推理是主因，且无法整体搬走。** `DIARIZATION_NPU_THERMAL_MATRIX_20261008.md` 第 8、9 节已判定 **ASR encoder 上 NPU 不可行**；角色分离 encoder 上 NPU 只省约 2 °C（−23~31 %），而本场景无角色分离。CHANGELOG 亦写明「主要发热仍来自真实推理（约 1.0 W），本项不能消除温升」。
2. **旧构建的线程与空转。** 该报告使用 2026-11-03 的 `1.1.0.089`，早于 2026-11-07「停止 ORT 空转 + 识别线程 4 → 2」。空转表现为 `Run` 之间自旋，直接推高频率档；这正是 NPU 矩阵 §8.6 证明的「发热主因是操作点而非算力总量」。
3. **App 侧调试负载。** 同报告 8.2：一小时把 `10MB × 10 片`日志轮转 3 次（≈300 MB/小时）；debug wav 落盘在 EC521S 上直接 OOM。这部分与推理无关，属纯额外开销。
4. **温控 3 说明大核被推高。** 及时率未受影响，但频率档抬升会把同样 CPU 时间换成更高能耗。

## 3. 已落地的 SDK 修改（对手机同样生效）

| 修改 | 生效范围 | 是否需要 App 改配置 |
| --- | --- | --- |
| `session.force_spinning_stop=1`（sherpa 补丁 `0038`） | **所有安卓 ORT session** | 否 |
| 鼎桥默认线程 4 → 2 | `DingqiaoEngineConfig.DEFAULT_ASR_NUM_THREADS` | 否 |
| 静音段不送 encoder（`EncoderIdleGate`） | 只要 `vad != null`（默认开）就自动创建 | 否 |
| 10 ms 编码帧对齐（本轮修复） | 同一喂入路径 | 否 |

手机上要拿到这些，**只需用新 SDK 重新构建应用**，无需改调用参数。

## 4. EC521S 同源实测（可作为方向与量级参考，不可外推为手机数值）

同条件（插电 + 锁屏、鼎桥 2 线程、同一音频窗口、同一 APK，仅切门控）：

| 指标 | 门控开 | 门控关 |
| --- | --- | --- |
| 509 秒窗口 CPU | 460.8 s（90.4 %） | 674.9 s（132.4 %） |
| 每秒音频 CPU | 0.904 核·秒 | 1.324 核·秒 |
| 前壳 / 后壳温升 | **+1.85 / +0.59 °C** | +4.85 / +1.29 °C |
| 边框 / AP 温升 | **+3.09 / +6.0 °C** | +6.44 / +10.0 °C |
| PMIC 温升 | **+6.10 °C** | +9.96 °C |

同条件 CPU **−31.72 %**，各测点温升全面更低；26 字参考与分块稳定性不变，七项契约 7/7 通过。

线程与空转那一项此前已单独量过：USB 输入功率 1.47 → 1.24 W、进程 CPU 约 2.7 → 1.3 核、SDK 增量功耗 −18 %。

## 5. 关键新证据：门控决定长跑能否持续

同一 60 分钟循环音频、插电锁屏、同一二进制、2 线程：

| 门控 | 结果 |
| --- | --- |
| 开 | 跑到 **3,590 s**（99.7 %），CPU 89.6 %，终点前 9.5 s 因 `processed_progress_lag` 判失败 |
| 关（第一次） | **718 s** 因 `processed_progress_lag` 中止 |
| 关（第二次，滞后阈值放宽到 30 s） | **1,227 s** 因 `feed_clock_late` 中止 |

门控开 60 分钟曲线（插电，后壳起点 36.5 °C）：后壳 +6.4 °C（36.5→42.9，35 分钟后走平）、前壳 +6.2、边框 +5.6。

这说明在 2 线程配置下，**门控不是省电优化而是持续实时的前提**；关掉后连 12~20 分钟都撑不住。

## 6. 结论

1. 对手机（BRA-AL00）这类"CPU 推理 + 长时锁屏运行"的场景，新 SDK 的三项修改（停止空转、2 线程、静音门控）**方向明确且无需 App 改动**，预期把 CPU 与温升同步压低；EC521S 上同源测得 CPU −31.7 %、温升 −3 °C 量级。
2. **幅度必须在手机上实测**，不能由 EC521S 外推：两端核数、频率档、热设计、App 负载都不同。
3. **软件无法消除剩余真实推理功耗（约 1.0 W）**；ASR encoder 上 NPU 已被证据链判定不可行。因此"彻底解决"= 降载 + 产品热设计接受剩余温升，而不是把手机做成不发热。
4. 手机侧还有一半开销来自 **App 调试行为**（日志、wav），需应用团队配合，SDK 无法代劳。

## 7. 行动项

**SDK（本仓库）**
1. 已交付：空转停止、2 线程默认、静音门控、10 ms 对齐（工作区未提交）。
2. 待办（需评估）：ASR 线程 QoS/优先级开关——NPU 矩阵 §8.6 证明这是最大杠杆（只改操作点不改算力），但会影响实时性，必须先有手机可验证。
3. 待办：`processed_progress_lag` 在 60 分钟尾段的偶发触发需定位（可能来自 GC 或系统负载），不能靠放宽阈值掩盖。

**App（小乔）**
1. 用新 SDK 重新构建；
2. 长跑场景降低日志量（当前 ≈300 MB/小时）；
3. debug wav 改流式或关闭（否则长会话停止必 OOM）。

**验证（有手机时）**
1. 同 61.9 分钟协议：飞行模式、锁屏、FGS、每 10 分钟插线采温；
2. 同机同音频对照"旧构建 vs 新构建"，输出背壳/前壳/边框温升与 CPU 均值；
3. 判据：CPU 均值、温控到达时间、背壳峰值；不以"回调正常"替代温升对比。

## 8. 边界与未测项

- 手机侧真机数据：**无**。本文所有幅度数字来自 EC521S。
- 门控开 60 分钟那轮**未通过资格**（终点前 9.5 s 失败），其温度曲线只能作测量参考。
- 手机端 ASR 线程数与调用参数由客户 App 决定，若其显式设置 4 线程，需要应用侧同步改为 2。
- 环境温度、表面测点未标定，跨设备比较只能看相对变化。
