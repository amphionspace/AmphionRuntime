# Sortformer 长会议出现成片无输出（2026-10-30 立项）

四条丁桥现场录音里，两条在中段出现**长达一两分钟完全没有角色输出**的区间，而那些区间里有人
在说话。鸿蒙与安卓表现一致，所以根源在两端共用的那一层，不是哪一端的移植引入的。

本条是在安卓换 Sortformer 的真机验证中发现的，但**它早于那次移植，已经随 0.3.26 交付出去了**。

## 证据

安卓与鸿蒙在 `meetingMinutes-20260918-100350-257`（369.1 s）上的输出：

| 项 | 安卓 | 鸿蒙 |
|---|---:|---:|
| turn 条数 | 191 | 189 |
| turn 覆盖总时长 | 140.4 s | 140.4 s |
| 最大空洞 | 207.0~343.8 s（136.8 s） | 207.0~343.8 s（136.8 s） |
| 覆盖率 | 38.1% | 38.1% |

空洞区间**不是静音**。该 wav 的分段 RMS：

| 区间 | RMS |
|---|---:|
| 整段 0~369 s | −24.4 dBFS |
| 空洞 207~344 s | −24.2 dBFS |
| 对照 0~207 s | −24.4 dBFS |

空洞内逐 10 秒都在 −22 至 −26 dBFS 之间，只有最后 337~344 s 掉到 −40.6 dBFS。也就是说
整个空洞的能量与正常说话段相同。

另一条 `meetingMinutes-20260918-102010-230` 也有 23.4 s 的空洞（鸿蒙侧数据，cycle 000002）。

## 为什么 DER 没有暴露它

四条录音的参考是**局部听审标注，总计 78.542 s**，而音频总长约 900 s。评分按 UEM 受限口径，
只在标注范围内计分，而这些空洞落在未标注区，既不计漏检也不计误报。所以：

- 全集 DER 12.10% 这个数字**在它自己的口径里是对的**，两端对比也有效；
- 但它**不能当作整体准确率**，交付包 `rttm-derived/README.md` 对此有明确警告。

## 已定位：模型行为，不是我们的实现（2026-11-01 补）

主机参考实现（交付包自带的 `sf_infer.py`，ORT 1.16.3 + 厂商为 1.16.3 做的
`encoder_layers.int8.ort1163.onnx`）在同一条录音上**复现了完全相同的空洞**：

| 区间 | 任一槽位活跃 | 模型概率峰值 |
|---|---:|---:|
| 0~207 s | 131.68 / 207.0 s | 0.961 |
| **207~344 s** | **0.22 / 137.0 s** | 多数 20 s 窗低于 **0.05** |
| 344~369 s | 7.23 / 25.0 s | 0.914 |

空洞内逐 20 秒的概率峰值：0.330 / 0.002 / 0.046 / 0.009 / 0.017 / 0.053 / 0.856。
227~247 s 那段峰值只有 **0.002**。

主机全程活跃 139.1 s，设备侧 140.4 s，两者一致。所以共用的 C++、提交时钟与轨道累积
**没有丢数据**：是模型在这 137 秒上输出的概率本身趋近于零，并在 344 s 左右部分恢复
（峰值回到 0.914）。该段音频 RMS −24.2 dBFS 属正常说话电平。

**因此上一节列的第一条待查方向成立、第二条排除**：问题在说话人缓存的状态，不在提交侧。
**调 `kActiveThreshold` 无用**——峰值 0.002 离任何合理阈值差两个数量级。

## 原先列的待查方向（保留以记录排查过程）

两端共用 `sortformer_diarization.cpp` 与同一套权重，表现一致，所以嫌疑集中在共用层：

1. **引擎是否在某个状态后不再吐出发声段**。说话人缓存（`spkcacheLen=188`、FIFO 188、
   `spkcacheUpdatePeriod=144`）在长会议上会反复压缩/替换，需要确认它进入某种饱和或退化状态后
   `speaker_head` 的输出是否整体低于 `kActiveThreshold = 0.5`。
2. **是不是提交侧丢的**。`finalTracks` 只在 final 事件里累积，提交区间由提交时钟决定；需要确认
   那段音频对应的 final 事件本身是否存在、runs 是否为空。
3. **是否与喂入速率无关**。安卓这两次分别用 0 ms 与 20 ms 速率，空洞位置与长度不变；鸿蒙那轮
   是产品链路实时速率，同样如此。所以与排队/批量无关。

最便宜的下一步：把这条录音在**主机参考实现**上跑一遍（`dq5-diar-eval-20261027/sf_infer.py`
已有现成的宿主链路），看主机输出在 207~344 s 有没有发声段。有，则问题在我们的 C++ 或提交侧；
没有，则是模型在这段音频上的行为，需要连同音频一起反馈给模型提供方。

## 不要做的事

- 不要在未定位根因前调 `kActiveThreshold`。阈值能让空洞"消失"，但那是把误报换成覆盖率，
  DER 在受限口径下还看不出代价。
- 不要用这条去质疑 12.10%。那个数字与鸿蒙同口径同录音，两端一致，它成立；成立的是对比，
  不是整体准确率。
