# 角色链路的并发开销与发烫归因（2026-09-30）

**结论：离线角色分离的发烫来自它本身的计算量与"每算子唤醒全部 worker"的并发开销，而不是线程池
空闲空转。实测约束 pthreadpool 的 spin 常量没有任何收益，该补丁已撤回。当前唯一被实测支持的降温
手段是减少 encoder 线程预算，代价是实时余量；要同时保速度与温度只能改模型。**

以下数据来自同一台 Mate 80（`VYG-AL30` / OpenHarmony-6.1.1.120）、同一 HAP 与同一 120 秒会议切片、
实时 20 ms 步长喂入、亮屏、ASR 统一为 `cpuIds=[4..11] spinning=false numThreads=4`，全部 SDK PASS。
CPU 口径为 OS 自身的 `ps -o TIME -p <pid>`（进程累计 CPU 时间，1 秒分辨率）。

## 实测

| 臂 | 进程 CPU-s/墙钟秒 | 相对角色关闭 | embeddingMs 中位 | audioDelayMs |
| --- | ---: | ---: | ---: | ---: |
| 角色关闭 | 0.850 | — | — | — |
| 角色开启，encoder 4 线程 | 2.641 | **+1.791** | 429 | 首 640 → 末 0，最大 900 |
| 角色开启，encoder 2 线程 | 2.348 | +1.499 | **408** | 首 620 → 末 0，最大 900 |
| 角色开启，encoder 1 线程（无线程池） | **1.908** | **+1.058** | 未取到 | 未取到 |

1 线程不使用 pthreadpool，所以它的 +1.058 是角色链路**有用计算的上限**。4 线程比它多花
**0.73 CPU-s/墙钟秒**，约占角色链路 CPU 的 41%、整进程 CPU 的 28%。

## 证伪：这不是空闲空转

上游 pthreadpool 在 worker 与调度线程上都先 `sched_yield` 一百万次再阻塞（`src/pthreads.c`），
而仓库既有的 worker-spin 补丁只覆盖 ORT 自己的线程池。据此先假设 4 线程多出的 CPU 是空闲空转，
并把常量约束到 4096（补丁 `0002-bound-xnnpack-pool-idle-spin.patch` + 构建驱动钩子）后重测：

| 臂 | CPU-s/墙钟秒 | embeddingMs 中位 |
| --- | ---: | ---: |
| 角色开启 4 线程，约束空转前 | 2.641 | 429 |
| 角色开启 4 线程，约束空转后 | **2.675** | 419 |

**约束后 CPU 没有下降**（差异在噪声内），单窗耗时也没有变化。所以多出的开销不是"没有任务时的空转"，
而是每个算子都要把 3 个 worker 唤醒再等回来的**并行段屏障开销**：它只随 worker 数增长，减少 spin
迭代次数不影响它。该补丁无实测收益，已按最小修改原则撤回，派生源码恢复上游值。

注意 2 线程与 4 线程的 encoder 耗时几乎相同（408 vs 429 ms），说明该 encoder 在这个设备上接近
内存带宽受限，增加 worker 换不到速度，只增加并发开销。

## 产品配置（关诊断）复核与线程预算缺陷

上述对比来自诊断构建。用**代码相同、仅关诊断**的产品配置（HAR 内 `BUILD_MODE_NAME` 由
`diagnostics` 改为 `release`，该常量只被诊断模块读取）重测同一 120 秒切片、亮屏：

| 臂 | CPU-s/墙钟秒 | 角色链路增量 |
| --- | ---: | ---: |
| 角色关闭（诊断构建参考） | 0.850 | — |
| 角色开启 t=4 | 2.491 | **+1.641** |
| 角色开启 t=2 | 2.149 | **+1.300** |

产品配置下 t=2 比 t=4 省 **0.342 CPU-s/墙钟秒**（整进程的约 14%），两臂均 PASS。

**重要缺陷（已修复）：** 在此之前 `SpeakerDiarizationConfig.numThreads` **从未生效**。原生
`Queue()` 把线程预算绑定在"参数个数正好等于 2/6"上，而 ArkTS 始终传 3/7 个参数（追加调度串），
于是所有 Harmony 调用方都静默退回默认 4 线程。修复见提交 `b94e53d3`，并补了会在旧行为下变红的
行为测试。**因此上表中 t=2 的收益只有在修复之后才拿得到。**

## 对发烫的结论（更新）

- 角色链路的固定计算量是发烫主因，产品配置下每秒音频多耗约 **1.6 CPU 秒**；
- 其中可回收的部分只有线程预算这一项（t=2 省约 14%），且**不改变任何特征值、embedding 与聚类结果**；
- 空闲空转不是主因（已证伪并撤回补丁），所以"消除无效 CPU"的空间有限；
- 要把发烫降到客户可感知的程度（以及把锁屏 RTF 从 0.96 压到 ≤0.7，见
  `DIARIZATION_SCREEN_OFF_CPUSET_20260930.md`），需要模型层改动，且必须重走身份精度门禁。
- **默认值建议：** 本机上 t=2 与 t=4 的单窗耗时相同（408 vs 429 ms）而更省电，但慢设备上 2 线程的
  实时余量更小。这属于产品取舍，除非明确要求，不擅自更改默认值；调用方可通过
  `SpeakerDiarizationConfig.numThreads` 自行选择。
