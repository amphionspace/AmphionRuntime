# Harmony 手机端长会议离线 ASR 突发输入测试报告

## 1. 测试目的

验证 Amphion Harmony 离线语音识别 App 在不按照实时音频速度等待的情况下，将一段长 WAV 文件的 PCM 帧快速、连续送入 SDK 后：

- ASR 是否会发生真正的死锁或永久无结果；
- SDK 在什么位置表现为长时间没有新识别结果；
- `finish`、最终结果、`onComplete` 和原生流释放是否符合生命周期契约；
- 突发输入对队列、耗时和内存的影响。

## 3. 测试方法

1. 读取 WAV 文件并去除 WAV 文件头，取得原始 PCM 数据。
2. 按 SDK 约定切成 640 字节、20 ms 的音频帧。
3. 启动一个 ASR session。
4. 不按 20 ms 实时时钟等待，不等待上一帧推理完成，连续快速调用 `writeAudio()` 提交全部 127,018 帧。
5. 全部 PCM 帧提交后调用 `finish(sessionId)`。
6. 等待 SDK 排空内部任务队列，记录所有 final、`isLast`、`onComplete`、error、原生流和进程资源数据。

本测试中的“突发输入”表示所有帧连续快速提交，并不表示把 81 MB PCM 作为一个不符合接口契约的巨大单帧传入 SDK。

为区分“真正死锁”和“处理时间超过测试超时”，诊断版本将隐藏压力测试载体的完成等待时间由 30 秒临时延长至 15 分钟。测试结束后，源码中的该诊断改动已还原。

## 6. 根因分析

### 6.1 PCM 输入队列没有背压

Harmony 鼎桥适配层的公开 `writeAudio()` 不会同步等待该帧推理完成。它把音频交给 `SessionAudioDispatcher`，后者会：

1. 使用 `audio.slice(0)` 为每一帧创建快照；
2. 为每一帧创建异步任务；
3. 通过静态 `executionTail` 将任务串行执行；
4. 将 `finish()` 排在所有已提交 PCM 任务之后。

因此，快速提交 127,018 帧会迅速构造 127,018 个 PCM 快照和异步队列任务。调用方虽然已经完成“投帧”，但 SDK 仍需要在后台串行消化全部队列，`finish()` 也必须等待此前任务完成。

这解释了突发输入时的以下现象：

- 输入 API 很快返回，但识别仍持续数分钟；
- 内存峰值明显升高；
- `finish()` 后较长时间没有 `onComplete`；
- 等待期间原生 stream 仍处于存活状态。

### 6.2 VAD 形成超长端点段

音频约 25:07.26 至 35:23.04 被合并为一个 615.78 秒的端点段。在该端点结束之前没有 final。由于本次没有启用 partial 文本，调用方在 161.57 秒墙钟时间内看不到任何新识别文本。

### 6.3 固定 30 秒测试超时造成误判

原压力测试载体的 `COMPLETE_TIMEOUT_MS` 为 30,000 ms。第一次测试在 30 秒内只得到 5 条非空 final，尚未等到 `onComplete`，因此报告：

- complete 为 0；
- live native stream 为 1；
- SDK 生命周期检查失败。

将等待时间延长后，同一输入最终在约 665 秒完成，得到唯一一次 `onComplete`，原生流归零。这证明第一次失败是“队列仍在处理但测试提前超时”，而不是固定位置死锁。

### 6.4 中间结果转为最终结果时发生边界文本丢失

在 Amphion 离线语音识别 App 中还观察到一个独立的文本结果错误：当中间结果（partial）转换为最终结果（final），同时下一段中间结果开始更新时，前后两段的交界处会损失部分识别信息。

具体表现为：

- 当前已经转为 final 的最后一句话末尾可能缺少部分文字；
- 即将转为 final 的下一组中间结果，其第一句话开头也可能缺少部分文字；
- 丢失内容位于“上一条 final 的尾部”和“下一条 partial/final 的头部”之间；
- 最终拼接得到的全文因此出现不连续、短语残缺或上下文断裂。

该问题不能简单归因于模型没有识别出对应语音。它也可能发生在 App 合并 partial 和 final、按 endpoint 替换显示文本、清理上一段缓存或计算增量文本的过程中。需要同时保存每次回调的原始完整文本、`sessionId`、endpoint/utterance 序号、`isFinal`、`isLast` 和回调时间，才能区分以下两类问题：

1. SDK 输出的 final 本身已经缺少边界文字；
2. SDK 回调文本完整，但 App 在 partial → final 状态转换和全文拼接时删除或覆盖了边界文字。

该缺陷与本报告前述“长时间没有新 final”是两个不同问题：前者属于结果拼接或回调边界的信息丢失，后者属于长端点、关闭 partial 和后台队列处理导致的结果可见性问题。

## 7. 结论

1. 本音频以突发方式一次性快速投帧时，ASR **不会永久卡死**，最终可以完成。
2. 用户可见的主要“卡住”位置是音频约 **25:07.26 至 35:23.04**；该处形成 615.78 秒长端点段，约 161.57 秒墙钟时间没有新 final。
3. 根本工程问题是 `writeAudio()` 缺少可观察、可等待的背压机制。一次性提交长音频会制造大量 PCM 副本和 Promise 队列任务。
4. VAD 超长端点和关闭 partial 会进一步放大“没有识别结果”的用户感知。
5. 固定 30 秒的完成等待不足以验证 42 分钟音频的突发推理，会把“仍在处理”误判为“卡住”。
6. App 在 partial 转为 final、并开始处理下一段 partial 时存在边界文本丢失：上一条 final 的末尾与下一条结果的开头之间可能缺少部分信息。该问题需要通过原始 SDK 回调与 App 最终拼接文本的逐条差分进一步定位。

## 8. 修复建议

### 8.1 SDK 输入接口

- 增加可等待的 `writeAudioAsync()`、`waitUntilWritable()` 或等价背压接口。
- 设置队列的最大帧数或最大 PCM 字节数，达到高水位时让调用方等待。
- 提供队列深度、已接受帧数、已处理帧数和剩余音频时长等指标。
- 避免为整段长音频同时保留十几万个独立 Promise 任务和 PCM 副本。

离线推理仍然可以快于实时速度；背压的目标是让生产速度跟随 SDK 实际消费能力，而不是强制每帧等待 20 ms。

### 8.2 端点和结果可见性

- 开启 partial 结果，或增加独立的处理进度回调。
- 为连续离线转写提供最大端点时长或安全的强制切段策略。
- UI 应显示“已提交”“正在处理”“已完成”的不同状态，不能仅根据是否出现新 final 判断 SDK 是否存活。

### 8.3 Partial/Final 文本拼接

- App 不应根据字符串前缀或字符长度直接裁剪下一条 partial；应以明确的 session 和 endpoint/utterance 标识管理结果。
- 收到 final 时，应先原子化保存该 endpoint 的完整 final，再创建下一 endpoint 的 partial 缓冲区，不能复用或提前清空同一个文本缓冲区。
- 不应假设下一条 partial 一定完整包含上一条 partial，也不应假设相邻 endpoint 的文本存在可安全删除的公共前缀。
- 保存“SDK 原始回调文本”和“App 合并后的显示文本”两条独立记录，并逐条比较，确定信息是在 SDK 层还是 App 拼接层丢失。
- 增加跨 endpoint 回归用例：上一句尾部和下一句头部使用容易辨认且不能互相包含的标记文本，验证最终全文与所有非重叠 final 的顺序拼接结果一致。
- 回归测试必须覆盖连续多个 partial、partial 内容回退或改写、final 到达后立即出现下一条 partial，以及最后一次 `isLast` 等边界情况。

### 8.4 完成和超时

- `finish()` 的等待时间应根据待处理 PCM 时长、队列深度和设备吞吐动态计算。
- 超时时记录最后已处理音频位置、队列深度、最后一次回调时间及原生流状态。
- 延长超时只能避免误判，不能替代队列背压和端点治理。

## 11. 修复实现与复测（2026-08-18）

本节记录初始诊断完成后在分支 `codex/fix-harmony-offline-long-audio` 上实施的生产代码修改。第 10 节“没有修改生产 SDK 实现”只描述修复前的诊断轮次，不适用于本节。

### 11.1 修改范围

1. **有界异步音频队列**
   - `SessionAudioDispatcher` 从“每帧创建一条独立 Promise 链”改为单一 FIFO 排空循环。
   - 默认高水位为 2 MiB，低水位为 1 MiB；达到高水位后只等待队列回落到低水位，不按 20 ms 实时时钟逐帧等待。
   - SDK 新增 `writeAudioAsync()` 和 `getAudioQueueStats()`，离线文件和 burst 压力测试均使用该接口。
   - ArrayBuffer/Float32Array 在入队时复制，避免调用方复用缓冲区造成后续帧内容被覆盖。

2. **长转写端点参数化**
   - 新增 `extraParams.endpointMaxUtteranceMs`，映射到 sherpa-onnx `rule3MinUtteranceLengthSec`。
   - SDK 默认值保持 20,000 ms，以兼容已有调用方；参数限制为 10,000～120,000 ms。
   - PTT、长文本转写和 burst 测试场景设为 55,000 ms；点击 VAD 场景仍为 20,000 ms。
   - 静音端点规则仍可在 55 秒之前自然产生 final；55 秒只是连续语音的强制切段上限。

3. **session 轮换期间不丢 PCM**
   - App 增加 `SessionRotationBuffer`。旧 session 执行 `finish()` 到新 session 启动完成之间到达的 PCM 帧被暂存，并在新 session 中按原顺序补写。
   - 触发轮换的当前帧也进入缓冲区；停止录音发生在轮换过程中时，尾部帧仍会排空后再结束。

4. **结果可见性和诊断能力**
   - burst 与 paced 测试均启用 partial。
   - 压力测试保存每条原始 TEXT 回调，包括 partial/final、`elapsedMs`、`isLast` 和 `textHex`；每 5,000 帧记录一次队列统计。
   - 保持 `isFinal` 与 `isLast` 的生命周期语义：允许多个 final，只允许最后一条带 `isLast`，随后恰好一次 complete。

### 11.4 Partial/Final 边界真机复测

测试输入为：

```text
D:\1资料\20260608实习\ASR Datasets\chaohuasishe_02_lu_64kb.mp3
```

首先以相同 20 秒端点分别执行旧投帧方式和新背压方式，两次 raw final 文本逐条一致，说明有界队列不会改变模型输出，也证明该轮压力测试中边界缺字不是由 App 字符串拼接引入。随后将长转写强制端点从 20 秒提高到 55 秒，并与用户指定的维基文库原文进行去标点字符级对齐：

| partial 回调 | 1,025 | 1,070 |
| final / 非空 final | 47 / 46 | 29 / 28 |
| final 字符数（含标点） | 2,940 | 3,019 |
| 处理耗时 | 203,256 ms | 203,224 ms |
| 原文遗漏字符 | 105 | 37 |
