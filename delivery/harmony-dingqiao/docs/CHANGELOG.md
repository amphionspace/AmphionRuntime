# Changelog

## 0.3.26 - 2026-10-29（角色分离换模型：Sortformer-66M-4spk）

- 基于 0.3.25。**角色分离模型与链路整体替换**：pyannote 分割 + WeSpeaker 嵌入 + PLDA/VBx 聚类（Community-1）换为 Sortformer-66M-4spk 端到端流式模型，CPU（ORT 1.16.3）运行。识别模型、热词、公共接口、回调顺序与角色结果格式不变，接入代码无需修改。
- **效果**（同一台我方测试机、同音频、同评分口径 openbench-der-v1）：丁桥现场 5 条 DER **23.10% → 12.10%**，4 条可计分录音 3 条大幅改善、1 条（111223-816）退化；AliMeeting 20 窗 12.74%，人数判对 19/20。混淆（说错是谁）是主要改善项。
- **时延语义变化**：最终角色按 9.92 s 块提交（原链路 10 s 窗 / 2 s 步），临时角色由新增的预览通道提供，默认每 5 s 刷新（`scheduling.diarizationPreviewMs`，可 0 关闭或 2500–9920）；120 s 公共提交周期、`isSessionFinal`、降级原因不变。临时角色与最终角色的标签翻转率实测 1.7%~2.4%。
- **算力**（同一台我方测试机、丁桥 5 条、识别与角色分离同时运行的产品链路实测）：角色分离推理墙钟 RTF **0.25~0.27**（0.3.25 为 0.07~0.09，约 3 倍）；整进程 CPU 均值 1.76 核（0.3.25 为 1.58 核，+11%），p95 2.68 核（2.21 核）；进程峰值 RSS 711 MB（581 MB，+130 MB）；结束到最终角色结果 1.1~2.4 s（0.7 s）。单独运行（无识别竞争）时每块推理约 0.4 s、整文件 RTF 0.045，含 5 s 预览 0.075~0.080。2 小时长会内存待复测。
- **包体**：角色分离模型由 21.3 MB 变为 73.2 MB（+51.9 MB）；Community-1 资产（WeSpeaker encoder/pool、PLDA、特征表、MindIR）不再随包。
- **字段弃用但保留**：`scheduling.diarizationEncoder`、`scheduling.diarizationHopMs` 不再改变行为（无 NPU 路径、无滑动窗），取值校验不变；`SpeakerDiarizationResult.encoderBackend` 恒为 `cpu`。
- **热词不再吞掉后续文字**：两端共用的解码器修复。此前调用方热词的首字加分在没有任何证据时即全额发放，且随分数放大，一个常用词热词（如「遣返」）可能把语音里的「幺」换成「遣」，并且停在该半匹配前缀上只输出空白不结算回退扣分，导致后续整段（现场为 11 位手机号）被删除。本版：半匹配前缀连续 1 s 无进展即收回加分并停发至回到根节点；首字加分封顶 1.0（逐词分数引入前的历史档），其后每字保持调用方分数。公开接口与热词入参格式不变。主机 500 条热词语料回归：整体 CER 1.021% → 1.075%，热词召回 97.25% → 97.09%（619 个热词实例丢 1 个）；两字热词在任何分数下都无法强推首字。
- **机主识别：换人时不再把非机主首句录入机主句**。两处修复：(1) 机主离场已由声纹连续低分确认、但换人分割模型把两人聚成同一标签时，收尾路径此前直接放行混合句，现改为继续走声学边界复核，仍定不出边界则退到保守前缀；(2) 自然停顿导致非机主独立成句、且短于流式判定所需时长（约 2 s）时，此前只需过 0.35 声纹阈值即被当作机主，现要求同时过实测空带下沿 0.45。被判为非机主的段仍为空 final + `SPEAKER_VAD_REJECTED` 事件，接口不变。
- **相邻同人句子合并**：`SpeakerDiarizationResult.utterances` 内相邻、同一已确认角色、中间无其他已确认角色发言的原 ASR final 合并为一项；新增 `DiarizedUtterance.sourceUtteranceIds` 列出被合并的原 final，`utteranceId` / `sourceUtteranceId` 取首句；`speakerIndex=-1` 不参与合并；`speakerTurns` 不变。调用方按 `sourceUtteranceIds` 替换临时句。
- 身份策略：四个槽位是模型按出场顺序给出的整场稳定身份；公开角色号在槽位首次出现在最终块时分配，`maxSpeakers` 封顶、超出保持匿名；仅出现在预览里的新槽位在其块提交前显示为未归属（-1）。
- 诊断事件：`DIARIZATION_SORTFORMER_CHUNK` / `_PREVIEW` / `_COMMIT` 取代 `DIARIZATION_COMMUNITY_*`；`DIARIZATION_QUEUE` 字段语义保持（积压秒数、在飞调用、音频延迟）。
- **交付边界**：本批语种范围为中英（ZH_EN），**不包含**粤英模型；**不包含** TTS 模型；目标说话人增强仅保留接口，**不包含**所需模型，因此**不能启用**。
- **已知**：Sortformer 的算法时延为 10 s，预览只能缩短首次等待，不能缩短最终确认；低时延档位（1.04 s）本包未交付且交付方实测 DER 翻倍。公开角色编号不连续（0.3.25 遗留）在新身份策略下按出场顺序连续分配，但仍以真机复测为准。

- **这是一次输出文本变更**：调用方热词由全局 1.0 提升为逐词 3.0，此前被同音词压过的业务专名现在能正确命中。若界面或下游对识别文本做字符串匹配或正则抽取，升级前须复核。
- 修复一（问题 #36，仅有未识别次要人声重叠时丢弃主讲人）：显示句的归属门禁此前只要与该句相交的任一声学片段带重叠标记、或带任何次要人物编号，就放弃整句归属。实际上「次要人物是未识别的 UNKNOWN」并不证明主讲人换了人。客户录音上，0.69 秒的重叠作废了 6.12 秒文本、0.66 秒的重叠作废了 3.48 秒文本，且两段都超过有界 UNKNOWN 回填的 2500 ms 上限而无法补救。本版复用同文件已有的 `blocksBackfill` 契约规则——已识别的次要人物、或没有任何具名来源的重叠才阻断，仅为 UNKNOWN 的次要人物不阻断——使显示层与回填层一致。同时修正「句子一旦成功归属就清空已发布次要人物编号」的问题，该行为会吞掉这句话实际观测到的未识别人声。客户录音实测：`speakerIndex = -1` 的句子 2 → 1 句，被修复空隙的次要人物编号 `[1, -1]` → `[-1]`。
- 修复二（调用方热词被预置池权重压低）：调用方热词（`sysGeneralLexicon`）此前与警务预置池（车牌/派出所/术语）共用同一全局权重，而该权重曾为抑制车牌过度偏置从 3.0 下调到 1.0，调用方热词被一并压低——实测中一个两字机构简称在每一句里都被替换成了与它同音的常用词。本版把调用方热词改为逐词显式加权 3.0，预置池不带显式分数、继续沿用全局 1.0，保持 Police 1.4.0 校准与车牌 A/B 证据有效。3.0 为评测工作点（热词精确命中率 **76.41% → 96.12%**）。调用方热词与预置词重复时按裸词去重，只入图一次。
- 接口语义收窄：`AsrConfig.hotwordsScore` 由「全局热词权重」收窄为「未逐词标注时的兜底分」，入参格式不变。
- 诊断字段修正：`hotwordCount` 此前读取 `StartParams` 上并不存在的 `hotwords` 键，因此恒为 0，排查热词未生效时会误导成「热词没传进来」；现改为统计引擎级 `sysGeneralLexicon`。仅诊断用，不影响识别。
- 0.3.24 引入的角色分离计算量上限（训练集 512、短 run 候选 32）保持不变。
- **交付边界**：本批语种范围为中英（ZH_EN），**不包含**粤英模型；**不包含** TTS 模型，TTS 由独立 TTS SDK 交付；目标说话人增强仅保留接口，**不包含**所需模型，因此**不能启用**。
- **仍未解决（公开角色编号）**：部分录音上公开角色编号不从「角色1」开始、或中间号段跳号；说话人数较多时部分语音落入「其他角色」。编号不连续部分可在集成侧做一次号段压缩即消除，本版未改动 SDK 侧编号发放逻辑。成因、实测证据与处置建议见 `DIARIZATION_ROLE_NUMBERING_29_77_EXPLAINED_20261022.md`。

## 0.3.24 - 2026-10-17（角色分离的两处成本缺陷）

- 基于 0.3.23。只改角色分离的计算成本，**不动识别模型、角色分离算法、阈值、窗口长度、hop 与提交周期**。识别文本、公共接口、回调顺序与角色结果格式均与 0.3.23 一致，接入代码无需修改。
- 修复一（聚类代价随会议时长失控）：每次提交都会把整场会议从第 0 秒重新聚类，而 `Ahc` 对训练向量数是二次的、且每次聚类被调用两次；当说话人数尚未达到上限时，短 run 准入循环还会对每个候选重跑一次全量 `Ahc`，候选数也随时长增长，整体变成立方。主机实测（合成 2 秒 hop 会话）：四说话人 40 分钟 0.59 s、2 小时约 5.3 s；两说话人 20 分钟 9.93 s、2 小时约 35 分钟。本版给训练集设 512 的上限（按时间均匀抽样）、短 run 候选设 32 的上限，并复用准入检查已算过的 `Ahc` 拟合。真机实测增长指数由约 2.0 降至 **0.85**。
- 修复二（预览聚类是角色分离里最大的单项）：预览是会被提交取代的临时结果，却按音频时长的十分之一自限流，在 7332 秒实测中占到 **534.1 s / 1183.5 s**，超过窗口推理的 450.7 s。本版把该比例改为二十分之一，预览预算减半。取二十而非四十，是因为该会话末期单次预览耗时 4858 ms，二十分之一的间隔为 109 秒音频、仍落在 120 秒的提交周期内，预览得以在整场会议里保持每个提交周期刷新一次；四十分之一则为 208 秒，预览会比提交还稀疏，在它本为之设计的长会议里悄然失效。
- 真机验证（Mate 80，我方测试机）：同机、同语料（客户原始录音循环至 7332 秒的单一连续会话）、同参数与 0.3.23 对照——**角色分离总计算 1183.5 s → 924.4 s，RTF 0.1614 → 0.1261，降 21.9%**；会话质量两轮一致（785 条 final、30800 字、说话人 4、`degraded=0`、原生流泄漏 0、意外回调 0）。
- 说话人归属未移动：该会话 65 次提交全部经两版聚类器重放并送入真实的 `CommunitySpeakerIdentity` 比对，工具本身以设备记录的 `clusterToFrozenId` 校验（65/65 一致）。上限以下真实数据逐位相同；上限以上内部标签最多差 9.61%，但经注册表吸收后公开说话人只有 **5.90 s / 7332 s（0.08%）**不一致，其中真正"一个具名说话人变成另一个"仅 **0.61 s（0.0083%）**，且无任何槽位丢失原有标签。
- 另含警务词条跨端对齐（`PoliceTermsV2`、同音词表与双端一致性夹具）。
- 修复三（独立 Demo 源码无法编译）：交付包里的 `demo-source` 只随附公共的 `amphion_dingqiao.har`，而 `SdkSelfTest.ets` 仍从 `amphion_police` 取词条回归用例，该模块只在 Diagnostics SDK 里。客户按文档独立构建会在 `Cannot find module 'amphion_police'` 处失败。本版在组包时剥掉这段用例，并把组包门禁从只查一个已知内部模块改为查每一个裸模块导入——`amphion_police` 当初正是这样漏过去的。0.3.23 的 `MindirProbe.ets` 是同一类缺陷。
- **交付边界**：本批语种范围为中英（ZH_EN），**不包含**粤英模型；**不包含** TTS 模型，TTS 由独立 TTS SDK 交付；目标说话人增强仅保留接口，**不包含**所需模型，因此**不能启用**。
- **未覆盖**：本版验证所用音频为单一录音循环，说话人数很早达到上限，因此"长静音后换人"与短 run 候选上限的等价性均未被触发；二者记录在 `docs/speaker/DIARIZATION_CLUSTERING_BOUND_20261016.md`。
- **仍未解决**：2 小时会话进程内存峰值约 1.1 GB。已定位到增长在 ArkTS 堆（103 分钟 +243 MB，占 RSS 增量 84%），并已排除 native 分配器扩张、证据缓冲堆积与诊断事件拷贝三种成因；对象级归因未完成。另：SDK 无遇热或按积压降级的机制。

## 0.3.23 - 2026-10-15（两处文本后处理缺陷与绑核恢复）

- 基于 0.3.22。只修文本后处理与绑核恢复三处缺陷，**不动识别模型、角色分离算法与任何默认调度参数**。
- **这是一次输出文本变更**，公共接口、回调顺序与角色结果格式沿用 0.3.22，接入代码无需修改，但连续念出的数字其转写结果会变，日期/金额/小数两侧原先多出的空格会消失。若界面或下游对数字文本做字符串匹配或正则抽取，升级前须复核。
- 修复一（ITN 数字串）：中文 ITN tagger 把 `一二三四五六七八九十` 读成 `cardinal { value: "123 4567 80~90" }`，既切组又把结尾的"十"当概数渲染成范围。识别本身无误（`rawText` 十字齐全），错在归一化。本版在 tagging 前把连续单字数字串折叠成数字。实测 `一二三四五六七八九十` → `12345678910`、`八九十` → `8910`；`三十八` → `38`、`八十` → `80`、`幺三八零零一三八零零零` → `13800138000`、`二零二六年五月十五日` → `2026/05/15` 均不受影响。
- 修复二（标点层空格）：标点模型（ct-transformer）本应只插标点，却同时对 ASCII 串重新加空格，把 ITN 正确输出的 `2.58万` 改成 `2 . 58万`、`2026/05/15` 改成 `2026 / 05 / 15`——这也抵消了此前已做的小数修复。本版按对齐保留它插入的标点、丢弃它新插的空格，对不齐则原样采用模型输出。该项影响面大于修复一，覆盖所有经 ITN 产出符号的文本。
- 修复三（绑核在锁屏后失效）：ORT 工作线程在启动时绑核一次，而系统切换 cpuset 调度组时会重写全部线程掩码，此后只有解码调用自身的线程会被重绑——即现场报告的"26 个绑核线程变 1 个"。本版记录 SDK 自建工作线程 id，在检测到调度组迁移后对这些线程重新下发 `cpuIds`，并因内核逐线程异步重写而持续重试 3 秒。实测 `cpuIds=[0-3]` 熄屏再解锁：解锁后持有配置掩码的线程 1 → 9~10 个。
- 真机验证（Mate 80，我方测试机，系统 6.1.0.135）：8 条数字用例全部达标；523 秒多人会议无回归——79/79 条 utterance 的 `speakerTextSpans` 完好、说话人标签与角色回调计数与修前完全一致，客户原始录音里那段报数由 `234 52456464560` 变为 `23452456464560`。
- **已知残留**：以"十"结尾的数字串其 `textNormalization.spans` 为空（文本正确，区间失败关闭）。成因是折叠后上游语法改为逐位记录，而"十"一个汉字要产出两个字符，必然出现宽度为 0 的区间被既有校验拒绝；UTF-8 字符中间无法切分。523 秒会议实测未出现该模式。
- **基线更正**：贵方 10-14 测得的锁屏实时率 ≈0.80× 是在我方 10-13 被 diagnostics 构建污染的包上测的。该开销已量化为 **≥0.22× 实时率**；干净包锁屏期为 **0.856× / 0.866×**，真实缺口 **0.134×**（其中角色分离链 0.091×、ASR 主链路自身 0.043×，即关掉角色分离也只到 0.957×）。后续报告与平台诉求请改用干净包数字。
- **绑核可移植性**：同为 Mate 80，`cpuIds=[4..11]` 在 6.1.2.329 上 `affinity-exact result=1`、在 6.1.0.135 上为 `0`。贵方现有配置不需要改，但绑核不是跨机型/跨版本可移植的能力，换机型或升级系统后须抓 `AmphionScheduling` 日志确认；读不到精确生效时退回 `[4,5,6,7]`。熄屏场景下该参数填什么都无效。
- SDK、Diagnostics、签名 Demo 和独立 Demo 源码统一为 0.3.23；版本日期为 2026-10-15，授权维护期限须覆盖该日期。
- 本批语种范围为中英（ZH_EN），不含粤英模型；不包含 TTS 模型；目标说话人增强仅保留接口，不包含所需模型，不能启用。

## 0.3.22 - 2026-10-10（角色分离发热：三个调度开关默认开启）

- 新增 `prepareRuntime` / `unloadRuntime` 和 `unloadModel`，形成 License、Runtime、Model 三层控制；`unloadRuntime` 保留已验证授权，模型未卸载时跟随释放。
- `createEngineAsync` / `createEngine` 在模型未加载时加载，同语言、同配置已加载时复用。
- 新增 HarmonyOS 客户接口文档和十轮全流程耗时、SDK 净内存报告及甲方简版摘要，并纳入客户交付包。

## 0.1.0 - hotfix 2026-07-13（声纹模型与生命周期）

- 声纹模型内置到 `amphion_dingqiao.har` 并由 SDK 直接加载，Demo 和宿主不再导入模型。
- 声纹注册与 Android 对齐：至少 1 条 3~8 秒样本，不限制样本数量上限。
- 明确生命周期：`prepareRuntime()` 不读取声纹模型；`unloadModel()` 确定性卸载内存 extractor，但保留 HAR 模型和已注册 embedding。
- 普通 final 声纹校验改为 N-API 后台加载 extractor，ASR 启动、音频写入和中间结果不等待；只有 final 必要时等待。Speaker VAD 因流式打分仍在冷启动时同步加载。

## 0.1.0 — hotfix 2026-07-12（Harmony ASR 冷加载）

- `zhen` encoder/INT8 decoder/joiner 与标点模型在构建期转换为 ARM CPU ORT 格式，运行时关闭重复图优化并直接使用 rawfile 映射模型字节。
- recognizer 与标点异步并行加载；transducer Session 采用 encoder 关键 lane 与 decoder/joiner 辅助 lane，相同配置使用 single-flight 与进程内 pool。
- 鼎桥配置使用 4 个 ORT worker，并跳过收益不足的 800 ms eager warmup。
- 新增独立进程 `createEngineAsync` 加载基准，固定设备构建、模型源哈希、HAP/native hash、线程数、预热样本和标点状态。
- 真机 `zhen` 冷加载 p50 从 3884.5 ms 降至 774.5 ms，p95 为 810.25 ms；pool hit 为 0–1 ms。48 轮真实音频回归通过。

## 0.1.0 — hotfix 2026-07-08（声纹 ASR 崩溃）

- 修复：开启「声纹校验」启动识别时 native abort 崩溃。`amphion_asr` 的 `Runtime.ets`
  `createSpeakerExtractor` 对绝对路径模型（`${workPath}/eres2net.onnx`）不再传 `resourceManager`，

- 说明：`eres2net.onnx` 为合法 ONNX（非 `.pth`），无需重导；模型文件不变。
