# 鼎桥专网离线 License 授权方案

## 1. 背景与目标

鼎桥侧提出的实际部署环境包含两个关键场景：

- 纯专网环境隔离：设备开机后处于与互联网完全物理或逻辑隔绝的内部专网中，无法通过公网进行 License 在线验证。
- 后装与系统升级：软件不一定在出厂生产阶段全部预装，设备上线后可能通过后装或升级方式安装新版本并完成授权。

补充条件：鼎桥侧可以提供授权范围内的全部设备 SN。

本方案目标是在不依赖公网、不要求设备访问我方服务器的前提下，实现可离线验证、可限制设备范围、可支持后装与升级的授权机制。

交付前鼎桥需提供的信息清单见 [`../../docs/dingqiao-offline-license.md`](../../docs/dingqiao-offline-license.md)。

## 2. 关键约束

不可违背的约束：

- 设备运行环境不能依赖公网。
- License 验证必须在设备本地完成。
- 后装和升级包进入专网后，应能独立完成安装与授权闭环。
- 授权文件不能被未授权 App、未授权设备或未授权版本随意复用。

工程约定：

- 由我方私钥签发 License，SDK 内置公钥本地验签。
- 授权绑定客户 App 标识和签名证书指纹。
- 授权绑定设备 SN 白名单，但 License 文件中不直接存储明文设备 SN。
- 小版本升级尽量复用原授权，大版本或维护期外升级重新签发授权。

## 3. 方案结论

推荐采用“应用绑定 + 设备 SN 白名单 + 维护期升级权益”的离线签名 License 方案。

整体思路：

1. 鼎桥提供授权设备 SN 清单、客户 App 标识、签名证书指纹。
2. 我方生成 License 授权声明，并对授权声明进行数字签名。
3. License 随 SDK/HAR、模型和升级包一起进入鼎桥专网。
4. 设备安装或升级后，SDK 初始化时读取本机设备 SN，在本地完成验签和白名单匹配。
5. 校验通过后启用 SDK；校验失败时返回明确错误码，便于现场排查。

该方案不需要公网激活，不需要设备访问我方服务，也不要求软件必须在出厂阶段预灌。

## 4. License 文件结构

License 文件采用 UTF-8 JSON 信封格式。签名覆盖授权声明原始字节，避免不同 JSON 序列化方式导致验签不一致。

```json
{
  "payload_b64": "<base64(UTF-8 JSON claims)>",
  "alg": "SHA256withECDSA",
  "sig_b64": "<base64(ECDSA signature)>"
}
```

授权声明建议字段：

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| customer | 客户名称 | 例如 Dingqiao |
| licenseId | 授权编号 | 用于交付、续期、排障追踪 |
| bundleName | HarmonyOS 应用 bundleName | 防止授权被其他应用复用 |
| signingCertDigest | 客户应用签名证书指纹 | 防止换包或重签名后复用授权 |
| deviceIdHashAlg | 设备 SN 哈希算法 | 建议 SHA-256 |
| deviceIdSaltId | 哈希盐编号 | 用于区分客户或授权批次 |
| authorizedDeviceHashes | 已授权设备 SN 哈希白名单 | 不存储明文设备 SN |
| features | 授权能力列表 | 仅允许 ASR、TTS |
| sdkMajor | 授权 SDK 大版本 | 例如 1 表示 1.x |
| maintenanceUntil | 可升级维护期 | 控制可升级到哪些发布时间的版本 |
| issuedAt | 签发日期 | yyyy-MM-dd |
| expiresAt | 运行到期日 | 可为空，空表示已授权版本不因时间停机 |

示例：

```json
{
  "customer": "Dingqiao",
  "licenseId": "AMP-DQ-2026-0001",
  "bundleName": "com.dingqiao.example",
  "signingCertDigest": "AB:CD:EF:...",
  "deviceIdHashAlg": "SHA-256",
  "deviceIdSaltId": "DQ-TIASSISTANT-20260623-69CD375699165832C1D2E9EA77C8BE71",
  "authorizedDeviceHashes": [
    "4F1B...",
    "9A02..."
  ],
  "features": [
    "ASR",
    "TTS"
  ],
  "sdkMajor": 1,
  "maintenanceUntil": "2027-06-30",
  "issuedAt": "2026-06-18",
  "expiresAt": ""
}
```

## 5. 设备 SN 白名单

鼎桥侧提供设备 SN 清单后，我方不建议将明文设备 SN 写入 License。推荐写入：

```text
SHA-256(normalizedSn + deviceIdSaltId)
```

其中：

- `normalizedSn` 是规范化后的设备 SN，例如去除首尾空格、统一大小写。
- `deviceIdSaltId` 是项目固定盐编号，当前实现也作为哈希盐材料。本项目固定为 `DQ-TIASSISTANT-20260623-69CD375699165832C1D2E9EA77C8BE71`。
- 哈希不是加密，不能还原设备 SN 的主要原因是 SDK 不保存明文清单；但它不等同于密钥保护，授权文件仍应按客户资料妥善管理。

SDK 侧流程：

1. 读取本机设备 SN。
2. 按同样规则计算设备 SN 哈希。
3. 在 `authorizedDeviceHashes` 中查找。
4. 命中则设备授权通过，未命中则拒绝启用 SDK。

需要鼎桥确认的前置条件：

- 设备 SN 在 HarmonyOS 端是否有稳定读取 API。
- 设备 SN 在系统升级、恢复出厂、主板维修后是否保持稳定。
- 设备 SN 是否在同一客户范围内唯一。
- 设备 SN 是否允许提供给我方用于签发授权。

如果授权设备数量很大，白名单可以按批次拆分为多个签名授权包，例如按省份、项目、批次或设备型号拆分。SDK 初始化时只需任一授权包匹配即可。

## 6. 后装与升级流程

后装和升级不依赖设备联网，采用“升级包携带授权文件”的方式完成闭环。

推荐流程：

1. 鼎桥侧确认本次后装或升级覆盖的设备 SN 范围。
2. 鼎桥侧提供 App 标识、签名证书指纹、设备 SN 清单和目标版本信息。
3. 我方签发对应 License。
4. 我方或鼎桥将 SDK/HAR、模型、License 文件和校验清单打入升级包。
5. 升级包通过鼎桥专网升级平台、运维工具或离线介质进入现场。
6. 设备安装后，SDK 本地完成验签、App 绑定校验、设备白名单校验和版本维护期校验。
7. 校验通过后启用功能；校验失败时输出明确错误信息。

该流程支持出厂预装，也支持上线后的后装和系统升级。

## 7. 版本升级权益

建议将“运行授权”和“升级权益”拆开。

- `expiresAt` 控制已安装版本是否会因时间到期而停机。
- `maintenanceUntil` 控制客户可升级到哪些发布时间的 SDK 或模型版本。
- `sdkMajor` 控制授权覆盖的大版本范围。

推荐策略：

- 对专网和警务类现场设备，`expiresAt` 默认留空，避免因设备时间错误导致已部署系统停机。
- 小版本升级，例如 `1.2.0` 到 `1.2.3`，在同一 `sdkMajor` 内且版本发布时间不晚于 `maintenanceUntil` 时复用原 License。
- 大版本升级，例如 `1.x` 到 `2.x`，或新增收费功能模块时，重新签发 License。
- 维护期到期后，已安装且已授权的版本继续运行；若要升级到维护期之后发布的新版本，需要续期并重新签发 License。

这种设计能满足专网环境下的稳定运行要求，也能把后续版本升级纳入商务和交付控制。

## 8. 新增设备、换机与吊销

新增设备：

- 鼎桥侧提供新增设备 SN。
- 我方签发新的全量 License 或增量设备授权包。
- 授权包随下一次升级包或运维包进入专网。

换机或维修：

- 如果设备 SN 不变，原授权继续有效。
- 如果设备 SN 变化，需要将新设备 SN 纳入授权清单并重新签发授权。

吊销设备：

- 纯离线环境无法实时吊销已离线安装的旧授权。
- 可在下一次升级或运维包中下发新的白名单，旧白名单不再包含被吊销设备。
- 若需要更强约束，可引入授权包版本号，SDK 只接受不低于本地已记录版本号的新授权包，避免回退到旧白名单。

## 9. 授权保护能力

本方案可提供以下授权保护能力：

- 未经我方私钥签名的 License 被 SDK 接受。
- License 内容被篡改，例如修改设备清单、维护期或功能模块。
- License 被复制到其他 App 使用。
- License 被复制到非授权设备使用。
- 维护期外的新版本继续复用旧升级权益。

正式交付包可结合代码混淆、签名校验、交付清单和合同约定共同管理授权范围。涉及离线环境本身的技术取舍，见附录。

## 10. 对鼎桥侧需要确认的信息

为进入实施阶段，需要鼎桥侧确认以下信息：

1. 设备 SN 的字段名称、样例和读取方式。
2. 设备 SN 在系统升级、恢复出厂、主板维修后的变化规则。
3. 首批授权设备 SN 清单和后续新增设备的同步方式。
4. 客户应用的 bundleName 和正式签名证书指纹。
5. 授权功能范围，例如 ASR、警务增强、目标说话人声纹、TTS。
6. 升级维护期和大版本授权范围。
7. 后装或升级包由哪一方组包，以及 License 文件在包内的固定路径。

## 11. 建议结论

在纯专网隔离、支持后装和系统升级、且可获得全量设备 SN 的条件下，推荐采用应用绑定、设备 SN 白名单和维护期升级权益三者结合的离线 License 方案。

该方案的核心价值是：

- 不依赖公网，不要求在线激活。
- 能随后装包或升级包进入专网。
- 能限制授权设备范围。
- 能支持新增设备和后续升级。
- 能把运行稳定性和升级权益分开管理，降低现场停机风险。

## 附录：方案边界与取舍说明

本附录用于技术评审或深入沟通。正文方案优先描述交付机制和授权能力，本附录补充离线授权方案在工程上的边界、原因和进一步增强的代价。

| 情况 | 为什么不能完全依赖技术手段阻断 | 当前方案收益 | 进一步增强的代价 |
| --- | --- | --- | --- |
| 客户端 SDK 被逆向并修改验签逻辑 | License 验签发生在客户设备本地。只要代码和运行环境都在端侧，理论上就存在被反编译、篡改或替换的可能，离线环境下没有服务器可以做二次仲裁 | 使用私钥签发、公钥验签、App 绑定、设备白名单和代码混淆，可以防止普通复制、篡改和误用，并提高逆向成本 | 可将关键验签逻辑下沉到 native 层、增加完整性校验和反篡改逻辑，但会增加开发、适配、排障和升级维护成本，也不能从物理上做到绝对不可改 |
| 已进入完全离线现场的旧授权无法实时吊销 | 设备与外部网络隔离后，我方无法主动触达设备，也无法实时下发吊销状态；吊销信息只能随下一次升级包、运维包或离线介质进入现场 | 不依赖公网，能满足专网隔离和现场稳定运行要求，不会因为网络不可达影响业务 | 可引入授权包版本号、本地防回退记录和吊销清单，但需要设备有可靠本地存储，并要求后续运维流程持续分发最新授权包 |
| 设备 SN 不稳定导致授权维护成本 | 设备 SN 如果在系统升级、恢复出厂、主板维修或换机后变化，本地白名单会把它识别为新设备。SDK 无法判断这是合法维修还是未授权设备 | 使用设备 SN 白名单可以在无公网条件下限制授权设备范围，比只按 App 授权更可控 | 需要鼎桥确认设备 SN 稳定性，并建立新增、换机、维修后的设备 SN 重签流程；也可使用多个设备标识组合，但会增加隐私说明、适配和故障排查成本 |
