# HarmonyOS ASR SDK 0.3.23 升级说明

本版只做文本后处理与绑核恢复三处修复，**不动识别模型、角色分离算法与任何默认调度参数**。

**这是一次输出文本变更。** 公共接口、回调顺序与角色结果格式沿用 0.3.22，接入代码无需修改，
但**连续念数字的识别文本会变**，日期/金额/小数里原先多出来的空格会消失。若界面或下游有按
字符串匹配、正则抽取数字的逻辑，请先读完"输出文本变更"一节再升级。

运行时版本为 0.3.23，版本日期为 2026-10-15；商用授权的维护期限须覆盖该日期。

> **为什么跳到 0.3.23 而不是再发一个 0.3.22。** 贵方已经先后收到两个不同的 0.3.22 制品
> （10-13 与 10-14），而本版又改了识别文本。再沿用同一版本号会让现场报告无法对齐，
> 所以这里换新号。

---

## 一、输出文本变更（必读）

### 1.1 连续念出的数字不再被拆组，也不再被当成概数范围

现象来自贵方 10-15 的反馈。修前后同一段音频（我方以 TTS 合成同一句话、真机四次复现，结果一致）：

| 念出的内容 | 0.3.22 输出 | **0.3.23 输出** |
|---|---|---|
| 一二三四五六七八九十 | `123 4567 80 ~ 90。` | **`12345678910。`** |
| 八九十 | `80 ~ 90。` | **`8910。`** |

成因在 ITN（逆文本归一化）的上游语法：中文 ITN tagger 把 `一二三四五六七八九十` 读成
`cardinal { value: "123 4567 80~90" }` —— 既把数字串切成三组，又把结尾的"十"当成汉语口语里的
概数（"八九十岁"≈八十到九十）渲染成范围。**识别本身没有错**，SDK 诊断流里的 `rawText`
十个字一个不少；错的是归一化。

本版在 tagging 之前把连续单字数字串直接折叠成数字，不再交给上游语法分组。

**不受影响的输入**（与 0.3.22 完全一致，均已真机复测）：

| 输入 | 输出 | 说明 |
|---|---|---|
| 三十八 | `38` | 复合基数，"十"在中间，不折叠 |
| 八十 | `80` | 只有一位数字 + "十"，不折叠 |
| 一二三 / 一二三四五 | `123` / `12345` | 本来就正确 |
| 幺三八零零一三八零零零 | `13800138000` | 手机号，本来就正确 |
| 二零二六年五月十五日 | `2026/05/15` | 数字串后紧跟"年"，交回日期语法 |

折叠的触发条件是：连续单字数字（零〇一二三四五六七八九幺么两）**至少三项**；结尾的"十"
只有在前面已有两位以上数字、且其后不接数字或量词时才并入为 `10`；数字串后紧跟
`年月日时分秒点元块角毛度岁号个百千万亿` 等量词时整段不折叠。

### 1.2 日期、金额、小数两侧多出来的空格消失了

| 念出的内容 | 0.3.22 输出 | **0.3.23 输出** |
|---|---|---|
| 两点五八万 | `2 . 58万。` | **`2.58万。`** |
| 二零二六年五月十五日 | `2026 / 05 / 15。` | **`2026/05/15。`** |

成因是标点模型（ct-transformer）：它本应只插入标点，但同时会对 ASCII 字符串重新加空格。
ITN 的输出本来是正确的 `2.58万` / `2026/05/15`，被标点这一步改成了带空格的样子。
本版改为按对齐保留它插入的标点、丢弃它新插入的空格；上游本来就有的空格因为能对齐而保留，
对不齐则原样采用模型输出（失败安全）。

**这一项影响面比 1.1 更广**：所有经过 ITN 产出符号的文本（日期、金额、百分比、小数）都在其中。

### 1.3 已知残留

**以"十"结尾的数字串，`textNormalization.spans` 会为空**（例如念"一二三四五六七八九十"）。
文本本身正确，只是该次回调不再带归一化区间。

原因：折叠后上游语法改为"每位数字一条记录"，而"十"这一个汉字要产出 `1`、`0` 两个字符，
必然出现一条宽度为 0 的区间，被既有的区间校验判为非法而整体清空（失败关闭，不会给出错误区间）。
UTF-8 字符中间无法切分，这条暂时绕不过去。

**对调用方的影响**：若贵方使用 `textNormalization.spans` 做文本到原文的回溯，遇到这类句子需要
容忍空数组。我方 523 秒多人会议实测中 **79/79 条 utterance 的区间完好**，该模式未出现。

## 二、绑核在锁屏后不再失效

贵方 10-15《绑核场景验证测试报告》测到"解锁回前台后 1 分钟仅恢复 1/26"。该现象成因确定：

ORT 推理工作线程在**线程启动时绑核一次**，而系统在进程切换 cpuset 调度组时（锁屏进
`key-background`、解锁回 `top-app`）会重写**全部线程**的亲和掩码。此后只有解码调用自身那个线程
会被重新绑定，引擎初始化时建立的那批工作线程不再有人重绑——所以"26 → 1"里的那个 1 就是调用线程。

本版记录 SDK 自己创建的工作线程 id，在检测到调度组迁移后对**这些线程**重新下发配置的 `cpuIds`
（绝不触碰不属于 SDK 的线程）。内核的掩码重写是逐线程异步完成的，单次扫描会被覆盖，因此迁移后
持续重试 3 秒。

实测（Mate 80 我方测试机，`cpuIds=[0,1,2,3]`，录音中途熄屏 → 解锁，同一协议对照）：

| | 亮屏起始 | 解锁后 |
|---|---|---|
| 0.3.22 | 9~11 个线程持有配置的掩码 | **1 个** |
| **0.3.23** | 同 | **9~10 个（恢复）** |

**需要贵方注意的两点**：

1. 这条修复让 SDK **忠实执行**配置。若 `cpuIds` 配的是小核，解锁后也会被重新绑回小核——
   这是正确行为，但请确认配置值是想要的。
2. 我方实测中，**绑核丢失本身对排空速度影响很小**：解锁后全核自由调度实测 1.550× 实时率，
   而绑中核 4-7 为 1.000×、不绑核 0.997×（ASR 滞后 40 ms 对 140 ms，用户不可感知）。
   这条修复的价值是"绑核功能在经历锁屏后仍然有效、行为可解释"，不是性能救援。

## 三、关于 `scheduling.cpuIds` 的可移植性（新增说明）

同为 Mate 80，两台设备行为不同：

| | 我方 | 贵方 |
|---|---|---|
| 机型 | Mate 80（我方测试机） | Mate 80（贵方设备） |
| 系统 | 6.1.0.135 / OpenHarmony-6.1.1.120 | 6.1.2.329 |
| `cpuIds=[4..11]` 前台 | `affinity-exact result=0`（未精确生效） | `affinity-exact result=1`（精确生效） |

我方逐组实测：`0-3`、`4-7`、`0-5` 精确生效；凡含 CPU 编号 ≥ 8 的（`8,9` / `10` / `11` /
`10,11` / `8-11` / `4-11`）一律读回不一致。**更新的系统放开了大核绑定。**

**结论：贵方现有配置 `[4..11]` 不需要改。** 但请注意绑核不是跨机型/跨版本可移植的能力——
部署到新机型或系统升级后，请抓一次亮屏会话的 `AmphionScheduling` 日志确认
`affinity-exact result=1`；若为 `0`，退回 `[4,5,6,7]`（我方实测该取值可精确生效，
且亮屏效果与 `[4..11]` 等同）。

**熄屏场景下这个参数填什么都没有效果**：系统已把全部线程压进小核，请求小核只是重合、
请求大核则交集为空直接 `EINVAL`。我方实测绑 `0-3` 与完全不绑核的锁屏期实时率一字不差。

## 四、锁屏变慢：基线更正（重要）

贵方 10-14 测得的锁屏实时率 **≈0.80×**，是在我方 10-13 那个**被 diagnostics 构建污染**的包上
测出来的。该污染值我方已量化：

| 协议 | 构建 | 锁屏期实时率 |
|---|---|---|
| 140 s（锁 80 s） | diagnostics（= 10-13 那版） | ≤ 0.631× |
| 140 s（锁 80 s） | **debug（干净包）** | **0.856×** |
| 220 s（锁 160 s） | debug（干净包） | **0.866×** |

**诊断日志开销 ≥ 0.22× 实时率。** 干净包的真实缺口是 **0.134×** 而不是 0.20×。
我方进一步把缺口拆开（同为干净包、受控对照）：角色分离链的全部代价 **0.091×**、
ASR 主链路自身欠缺 **0.043×**；**即使把角色分离整个关掉也只到 0.957×**。

**请不要在后续报告里继续沿用 0.80×。** 该问题本版未解决，方向结论不变（SDK 侧仅靠角色分离
优化补不上缺口），但向平台方提诉求时请用干净包的数字，否则对方复现不出来。

## 五、替换方式

与 0.3.22 相同，只需替换 HAR 并同步依赖：

1. 用包内 `release-sdk/` 的 `amphion_dingqiao.har` 替换现有依赖
2. `ohpm install --all`
3. 依赖声明里的版本号由 `0.3.22` 改为 `0.3.23`

无需修改任何接入代码。若界面对数字文本做过字符串匹配或正则抽取，请按第一节复核。

## 六、仍未解决的事项（请勿理解为已修复）

- **锁屏变慢未解决**。真实缺口 0.134×（见第四节），SDK 侧无独立解法；唯一确定有效的规避是
  会议进行中保持屏幕常亮（亮屏实时率 ≥0.99×）。
- **锁屏期"点亮屏幕"不够，必须解锁**。我方实测仅点亮时进程仍在受限调度组，排空速率只有
  0.618×；滑动解锁后才回到 1.550×。产品提示建议明确引导解锁。
- **停录时必须等待排空**。我方实测在积压 133 秒时停止录音、30 秒后拆除会话，最终文本少 15%；
  给够排空时间则与亮屏逐字节一致。丢的是时间不是识别能力，但固定超时拆引擎会真的丢文字。
- **吐字慢（0.3.22 问题二）主要症状仍在**：最大无输出空档由 105 秒降到 72.5 秒。残余部分我方
  判断为该段录音没有可转写的语音，**该判断仍待贵方确认**。本版未新增改动。
- **角色结果迟到（0.3.22 问题三）现场效果未验证**：机制已在 0.3.22 修订版改好并三臂真机验证，
  贵方现场那次 21.6 秒尚未用新包复测。
- **以"十"结尾的数字串 `textNormalization.spans` 为空**（见 1.3）。
- 本批语种范围为中英（ZH_EN），不含粤英模型；不包含 TTS 模型；目标说话人增强仅保留接口，
  不包含所需模型，不能启用。

## 七、建议的升级路径

1. 先在测试机替换 HAR，按第一节的用例确认数字文本的新形态符合界面预期
2. 若界面有数字正则，同步调整后再上生产
3. 升级后抓一次亮屏会话的 `AmphionScheduling` 日志，确认 `affinity-exact result=1`（第三节）
4. **用本版重跑一轮锁屏场景**，把基线从 0.80× 换成干净包的数字（第四节）
