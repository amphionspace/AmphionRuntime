# HarmonyOS ASR SDK 0.3.24 升级说明

本版只改角色分离的**计算成本**，**不动识别模型、角色分离算法、阈值、窗口长度、hop 与提交周期**。

**识别文本与 0.3.23 完全一致**，公共接口、回调顺序与角色结果格式不变，接入代码无需修改。
与 0.3.23 那次不同，本版**不是输出文本变更**，不需要复核界面上的数字正则。

运行时版本为 0.3.24，版本日期为 2026-10-17；商用授权的维护期限须覆盖该日期。

---

## 一、本版做了什么

角色分离在长会议上的计算量此前会失控增长。两处成因，均已修复。

### 1.1 聚类代价随会议时长增长

每次提交都会把整场会议从第 0 秒重新聚类一遍。其中 `Ahc` 对训练向量数是二次的，而且每次
聚类被调用两次；当说话人数尚未达到上限时，短 run 准入循环还会对**每个候选**重跑一次全量
`Ahc`，候选数同样随时长增长，整体变成立方。

主机实测（合成 2 秒 hop 会话，修复前）：

| 场景 | 13 min | 20 min | 40 min | 2 h |
|---|---|---|---|---|
| 四个说话人 | 0.12 s | — | 0.59 s | ~5.3 s |
| 两个说话人 | 2.92 s | 9.93 s | ~79 s | **~35 min** |

本版给训练集设 512 的上限（按时间均匀抽样，仍覆盖整场会议）、短 run 候选设 32 的上限，
并复用准入检查已经算过的 `Ahc` 拟合。**真机实测增长指数由约 2.0 降至 0.85。**

### 1.2 预览聚类是角色分离里最大的单项

预览是会被提交取代的临时结果，却按音频时长的十分之一自限流。7332 秒实测中它占
**534.1 s / 1183.5 s**，超过窗口推理的 450.7 s。本版改为二十分之一，预览预算减半。

取二十而非四十：该会话末期单次预览耗时 4858 ms，二十分之一的间隔是 109 秒音频，仍落在
120 秒的提交周期内，预览得以在整场会议里保持每个提交周期刷新一次；四十分之一则是 208 秒，
预览会比提交还稀疏，在它本为之设计的长会议里悄然失效。

**对调用方的影响**：提交之间的**临时**说话人标签刷新频率降低一半。已提交的结果不受影响——
预览会复刻身份注册表、不推进提交时钟与已发布边界，而每次提交都整体覆盖转写时间线。

## 二、实测收益

Mate 80（我方测试机），同机、同语料（客户原始录音循环至 7332 秒的单一连续会话）、同参数，
与 0.3.23 对照：

| 指标 | 0.3.23 | **0.3.24** |
|---|---|---|
| 角色分离总计算 | 1183.5 s | **924.4 s（−21.9%）** |
| RTF | 0.1614 | **0.1261** |
| 窗口推理 | 450.7 s | 453.0 s（持平） |
| 提交聚类 | 198.7 s | 202.2 s（持平） |
| 预览聚类 | 534.1 s | **269.3 s（−49.6%）** |

会话质量两轮一致：785 条 final、30800 字、说话人 4、`degraded=0`、原生流泄漏 0、意外回调 0。

> 提交聚类在定长会话上持平是正确的：该项消除的是**随会议时长的增长**，不是定长成本。

## 三、说话人归属未移动（本版最需要确认的一点）

训练集抽样会改变聚类内部的簇编号，因此我方做了端到端验证：该会话 65 次提交全部经修复前后
两版聚类器重放，再送入**真实的身份注册表**比对公开说话人。

- **对照工具自身的校验**：模拟出的公开映射与设备记录的 `clusterToFrozenId` 在 **65/65 次提交
  上完全一致**，因此它反映的是设备行为而非近似。
- **上限以下**：真实数据**逐位相同**。
- **上限以上**：内部标签最多差 9.61%，但注册表按声学窗口投票映射、不引用簇号，吸收了其中约
  99%——公开说话人不一致仅 **5.90 s / 7332 s（0.08%）**，其中真正"一个具名说话人变成另一个"
  只有 **0.61 s（0.0083%）**。**没有任何片段丢失原有的说话人标签。**

## 四、替换方式

与 0.3.23 相同，只需替换 HAR 并同步依赖：

1. 用包内 `release-sdk/` 的 `amphion_dingqiao.har` 替换现有依赖
2. `ohpm install --all`
3. 依赖声明里的版本号由 `0.3.23` 改为 `0.3.24`

无需修改任何接入代码，也无需复核数字文本。

## 五、仍未解决（请勿理解为已修复）

- **长会议进程内存**：2 小时会话峰值约 1.1 GB。已定位到增长发生在 ArkTS 堆（103 分钟 +243 MB，
  占进程内存增量的 84%），并已排除 native 分配器扩张、证据缓冲堆积与诊断事件拷贝三种成因；
  对象级归因尚未完成，本版未修。
- **SDK 无遇热或按积压降级的机制**：降级只在存储不可用、推理不可用与收尾超时三种情况触发，
  热等级与队列深度都不是输入。
- **锁屏变慢未解决**（与 0.3.23 相同）。干净包锁屏期实时率 0.856×/0.866×，缺口 0.134×。
  确定有效的规避仍是会议进行中保持屏幕常亮且应用在前台。
- **以"十"结尾的数字串 `textNormalization.spans` 为空**（与 0.3.23 相同，文本正确、区间失败关闭）。
- **本版验证未覆盖两种场景**：所用音频为单一录音循环，说话人数很早达到上限，因此"长静音之后
  换人"与短 run 候选上限的等价性均未被触发。前者是唯一可能让公开说话人编号错位的机制。
- 本批语种范围为中英（ZH_EN），不含粤英模型；不包含 TTS 模型；目标说话人增强仅保留接口，
  不包含所需模型，不能启用。
