# HarmonyOS ASR SDK 0.3.30 升级说明

本版相对 0.3.29 是**行为修复版**：识别模型、热词、公共接口与回调顺序不变，无破坏性变更。
修复集中在角色分离的角色编号与归属、通话静音时的"嗯"幻听，以及 `speakerCount` 的口径，
对应客户工单 #29、#92（第二轮）、#35；另附 #77、#36、#98 的复核结论。

运行时版本为 0.3.30，版本日期为 2026-11-19；商用授权的维护期限须覆盖该日期。

## 一、三人依次说话被编成「角色2 / 3 / 4」，带号码的句子落成「其他角色」（#29）

### 1.1 现象

安静环境三人依次朗读，输出为"角色2""角色4"和"其他角色"，没有"角色1"；含电话 / 证件号的句子被归到"其他角色"。

### 1.2 原因

- 录音开头约 1.3 秒的按键 / 环境声被分割模型报成一段"发言"。它没有语音、也没有识别出任何文字，却第一个到达，领走了身份 0；三位真人只能拿 1 / 2 / 3，显示为角色 2 / 3 / 4。
- 含数字的句子经过文本规范化（"幺三八"→"138"）后对不回识别 token，此前一律判为"其他角色"，哪怕声学上整句只有一个人。

### 1.3 本版改法

- 分割轨道开身份前必须有语音证据（区间内有识别 token）；没有证据的轨道先挂起，证据到了再按到达顺序补分配，始终没有证据的保持"其他角色"且不带文字，不再占用编号。
- 文本对不回 token 时，整句只有一个已知角色就归属该角色；多人同句、重叠、未知仍为"其他角色"。

客户录音复测：A / B / C = 角色 1 / 2 / 3，第一句含号码的句子归角色 1；客户会议录音回归 DER 5.66% 不变，角色混淆 0.9% → 0.0%。

## 二、通话静音时反复转写出"嗯"（#92 第二轮）

### 2.1 原因

0.3.27 加的"非空文本须有独立于识别器的语音证据"门禁，只在开机主识别或 Speaker VAD 时才被喂音频，普通转写（含通话文本转写）场景实际没有生效；通话静音时的底噪是普通电平，能过门禁的声学分支。

### 2.2 本版改法

- 门禁对所有场景无条件喂音频；
- 去掉标点后只由填充词（嗯 / 呃 / 啊 / 哦 … ≤4 字，或 um / uh / hmm）构成、且本句原生 VAD 从未判出语音的句子不发布；真人说的"嗯"有 VAD 语音照常发布，含实词的文本不受影响。

真机用客户真人声接四档底噪（−40 ～ −70 dBFS）复测：修前 57 秒内多出 1 ～ 4 条"嗯。/呃。"，修后只剩真人声。

## 三、`speakerCount` 跟随声纹身份（#35）

单人连续朗读被分割模型放进两个槽位时，全部文字已归角色 1，`speakerCount` 却报 2。本版开启声纹身份时 `speakerCount` 数已开出的声纹身份数；关闭时仍数模型槽位。客户 #35 录音复测 speakerCount 1、文字全部归角色 1。

**仍按契约保留的现象**：弱尾音的末句（−31 dBFS 左右，模型无说话段）仍为"其他角色"，不跨句补全；若希望"整场只有一个已知角色时末句也归该角色"，请与我方确认后再改契约。

## 五、调用方需要做什么

无需改动业务代码。替换 `har/amphion_dingqiao.har` 后重新编译安装即可。

- 角色分离：无需改参数；如需逐句显示，按 `sourceUtteranceIds` 拆开合并后的句子。
- 机主识别：已有声纹档案继续可用。

## 六、回退

0.3.30 无数据格式或接口变更，回退到 0.3.29 只需换回旧 HAR 并重新编译。
