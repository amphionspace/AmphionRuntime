# 问题 #29 / #77 成因说明与结论归属

撰写日期：2026-10-22
适用版本：SDK 0.3.24，git `10aa01f6`
证据来源：nova 15 实测 `.local/perf/nova15-baseline-rerun/20261022-015410-diarization-windows-6a349e45`

## 0. 结论速览

| 编号 | 客户描述 | 问题实质 | 归属     | 结论 |
|---|---|---|----------|---|
| **#77** | 单个讲话人录入文本时，角色编号未从「角色1」开始 | **纯标号问题** —— 话都有归属，只是号段稀疏 | 集成侧   | **集成侧改呈现即可彻底消除**。SDK 侧改会伤精度，不建议动 |
| **#29** | 离线语音多角色时只返回「角色2」和「其他角色」 | **归属缺失** —— 真实说话人的话落进「其他角色」 | 模型能力 | **集成侧改不了**。换/调模型也收敛不了，只能内部持续改进 |

两个问题出自同一套号池机制（第 2、3 节），但落在该机制的两种不同后果上，因此修法和归属不同：#77 是「号不好看」，#29 是「号不够用」。

## 1. 公开编号的契约

SDK 对外只给 `speakerIndex`，UI 文案由它换算：

- `speakerIndex = -1` → 显示「其他角色」
- `speakerIndex ∈ [0, maxSpeakers-1]` → 显示 `角色(speakerIndex + 1)`
- `maxSpeakers` 由 `SpeakerDiarizationConfig` 给定，取值范围 **[1, 4]**（`SpeakerDiarizationConfigPolicy.ts:8`）
- **一旦某个 `speakerIndex` 被发布，它就被冻结**，后续聚类结果再变也不会改写

## 2. 共同机制：号池是怎么发的

分配发生在 `CommunitySpeakerIdentity.assign()`（`asr/harmony/sdk-dingqiao/src/main/ets/com/amphion/dingqiao/diarization/CommunitySpeakerIdentity.ts:64`）：

```ts
for (const cluster of appearanceOrder) {
  const hasActivity = (visibleClusters === undefined || visibleClusters[cluster]) &&
    hard.some((label, index) => label === cluster && publishedActivity[index] > 0);
  if (hasActivity && best[cluster] < 0 && this.nextId < this.maxSpeakers) best[cluster] = this.nextId++;
}
```

三个要点：

1. **`appearanceOrder` 按 `firstAppearanceTimes` 升序** —— 谁先出现谁拿小号。
2. **准入条件只有两条**：该簇在本次发布区间内可见（`visibleClusters`），且在该区间内有非零分割活动（`publishedActivity > 0`）。
3. **`nextId` 单调递增、发布即冻结**，上限 `maxSpeakers`（最大 4）。

门禁数据来自 `SpeakerDiarizationSession.ets:474-520`：

- `publishedActivity` 是分割模型 powerset 输出的逐帧活动在发布区间内按通道**累加求和**（`:494`）—— 只要有**一帧**活动落在区间内，和就 > 0。
- `visibleClusters` 是「该簇有任一声学 turn 与发布区间相交」（`:514`）。

**关键：这里完全不参考 ASR 是否在该簇上识别出任何文字。** 一个只有背景噪声、远场串音或呼吸声的簇，只要分割模型给了它一帧活动并生成了一个 turn，就能合法占住一个公开角色号。

## 4. #77：纯标号问题 —— 集成侧改呈现即可

### 4.1 为什么是标号问题

#77 报的是「编号未从角色1开始」。这类现象里**话都有归属**，只是号段稀疏（起始号不是 1，或中间跳号）。把稀疏号映射成从 1 开始连续的展示号，现象即彻底消除。

按本次实测数据套用压缩：

| 音频 | 现状编号 | 压缩后 | 效果 |
|---|---|---|---|
| 257 | 角色3、角色4 | 角色1、角色2 | 消除 |
| 230 | 角色3 | 角色1 | 消除 |
| 无角色4 | 角色1、角色3、角色4 | 角色1、角色2、角色3 | 消除 |
| 816 | 角色1 | 角色1 | 本就正常 |
| 039 | 角色1、角色2 | 角色1、角色2 | 本就正常 |

### 4.2 参考实现

仓库里已有实现并带单测：

- `delivery/harmony-dingqiao/samples/dingqiao-demo/entry/src/main/ets/util/SpeakerDisplayIndex.ts` 的 `compactSpeakerDisplayIndexes()`
- 单测 `asr/tools/tests/test_harmony_customer_scenario_demo.py:194-196`，断言 `[0,3,0,3] → [0,1,0,1]`、`[-1,3,1] → [-1,0,1]`、`[2,2,0] → [0,0,1]`

约二十行，不碰任何声学逻辑，**零精度影响**。

**需要明确**：该函数**尚未接入我们的 demo**。`Index.ets:624` 的 `refreshSpeakerDisplayIndexes()` 目前是直通赋值：

```ts
private refreshSpeakerDisplayIndexes(segments: FinalSegment[]): void {
  for (const segment of segments) segment.displaySpeakerIndex = segment.speakerIndex;
}
```

所以 demo 与客户端一样会显示稀疏编号。对外应表述为「提供参考实现」，**不能**表述为「我们 demo 已采用该方案」。

### 4.3 为什么不建议在 SDK 侧改

两条路都有实打实的退化：

| SDK 侧改法 | 代价 |
|---|---|
| 直接改 `speakerIndex` 的含义使其连续 | 破坏「发布即冻结」契约 —— 客户界面上已显示的历史文本会在录音过程中反复跳号 |
| 在发号处加判别式挡掉伪簇 | 误杀安静/远场的真实说话人，详见第 5.2 节三组反例 |

若希望由 SDK 承担，推荐的折中是**新增 `displaySpeakerIndex` 字段与 `speakerIndex` 并存**，`speakerIndex` 契约不变；代价是客户端需切换取值字段。

## 5. #29：归属缺失 —— 模型能力边界，集成侧改不了

### 5.1 为什么是归属问题

#29 报的是「只返回角色2和其他角色」。这里的要害**不是编号难看，而是真实说话人的话落进了「其他角色」**。号段压缩只重映射 `speakerIndex ≥ 0`，对 `-1` 不做任何处理，因此**压缩对这部分完全无效**。

实测：

| 音频 | speakerCount | 落地角色号 | `-1` 句 | `-1` 字占比 | registry |
|---|---|---|---|---|---|
| 230（200.8 s） | 4 | 只有角色3 | **7 / 9** | **81.5%** | 0 → 4（打满） |
| 816（164.1 s） | 4 | 只有角色1 | **9 / 13** | **69.0%** | 打满 |

五条合计 52 句中 25 句为 `-1`，占总字数 39.3% —— 这部分压缩后依旧是「其他角色」。

号池上限 4 个（`SpeakerDiarizationConfigPolicy.ts:8`），这两条都已被伪簇占光，真实说话人拿不到号。

### 5.2 为什么无法在发号时挡掉伪簇

要回收槽位，就必须在发号那一刻区分「伪簇」与「一个安静/远场的真人」。实测反复否决了这条路：

**（a）质心距离不可分（2026-10-22 本轮新验证）**

从本次 `clusterCentroids`（256 维）计算簇间余弦相似度：

| 音频 | 簇对 cos 范围 | 说明 |
|---|---|---|
| 039（**两个确凿真人**，编号正常） | **0.0992**（唯一一对） | 真人 vs 真人 |
| 230（含伪簇，槽位打满） | 0.0504 ~ 0.2036 | 六对 |
| 无角色4（含伪簇，角色2 空缺） | 0.0160 ~ 0.2281 | 六对 |

039 那对确凿真人的 0.0992 **正落在含伪簇区间的中间**。任何基于质心距离的阈值，要么放过伪簇，要么把 039 的真人合并掉。

**（b）其余三种判别式（2026-10-21 调查结论；当时音频已不在仓库，数据未在本文档重新验证）**

| 判据 | 否决依据 |
|---|---|
| 活动占比 ≥ 10% 才发号 | 合法说话人占比 5.88% / 9.31%，**低于**伪簇的 6.7% |
| PCM 相对电平 ≥ 0.3 才发号 | AliMeeting 远场合法说话人电平 0.227 / 0.300，**低于**伪簇的 0.173 |
| 改为「首次出现语音时」才发号 | 设备数据 `firstSpeechTimes = [3240, 3240]` 完全相同，无法分辨先后 |
| 必须有 ASR 文本才发号 | 破坏 `test_public_speaker_ids_follow_first_acoustic_appearance`（`asr/tools/tests/test_harmony_community_diarization.py:143`，其用例完全无文本输入） |

本轮 230 给出同方向新反例：四个簇活动占比 24.0% / 11.9% / 21.0% / 43.1%，**全部高于任何可用的最小占比阈值**，但这 117 秒没有任何一个字。说明在「该不该发号」这件事上，**分割活动这个信号本身就不携带足够信息**。

### 5.3 为什么换模型也解决不了

同机同五条音频实测 Conformer ep29（收敛点 `best_ep29.pt`），其纸面指标全面优于基线：

| 指标 | 基线 | ep29 |
|---|---|---|
| cn118 weighted DER | 21.27% | 18.74%（−2.53） |
| cn98 weighted DER | 21.09% | **16.98%（−4.11）** |
| 误报 FA | 5.90 | 4.35 |
| 漏检 Miss | 9.64 | 8.67 |

**结果：基线 5 条中 4 条编号异常，ep29 仍有 3 条异常。**

即该现象不随 DER 收敛 —— 模型指标变好，编号该错还是错。且 ep29 代价为 RTF 0.0750 → 0.1363（1.82×），厂商自报在 alimeeting_sdm（+2.33）、aishell4（+4.58）等远场会议集上反而退化，恰是丁桥的实际录音条件。

因此 #29 不属于「模型再训一版即可修」的问题，只能内部在聚类与发布层持续改进。

## 6. 为什么现有 SDK 逻辑不算写错

需要说清楚：**现有分配逻辑在忠实执行两条刻意的约束。**

1. **编号稳定性优先** —— 已发布的 `speakerIndex` 不可改写，否则客户界面上的历史文本会在录音过程中反复跳号。`test_appearance_order_does_not_renumber_frozen_or_enroll_preview_ids` 锁定了这一点。
2. **编号按首次声学出现排序**，不按原生聚类标签。`test_public_speaker_ids_follow_first_acoustic_appearance` 明确断言「public IDs must follow acoustic appearance, not arbitrary native cluster labels」—— 因为原生簇标签在每次 commit 都会重新编号（第 3.2、3.3 节相邻区间的 `clusterToFrozenId` 发生置换即此现象）。

在「每个有活动的簇都是一个真实说话人」这一前提下，上述约束产出的编号是连续的、从 1 开始的、稳定的。问题出在前提不成立：**分割模型会为非语音内容产生带活动的簇**，而分配层没有任何机制把它们挡在门外。

准确的说法是：这不是编号逻辑的缺陷，而是**「分割活动」被当作了「存在一个值得编号的说话人」的充分条件** —— 一个过强的假设。

## 7. 对外表述建议

1. **#77**：「集成侧做一次号段压缩即可彻底消除；SDK 侧修改会影响精度，不建议动。」参考实现可直接提供。
2. **#29**：把两半说开 —— 「#29 现象里编号那部分与 #77 同源，集成侧改呈现即可;剩余部分是说话人数超出可分配能力后落入「其他角色」，属于模型能力边界，我们内部持续改进。」
   若只说「模型能力问题，等内部改进」，客户按 #77 建议接入压缩后会看到编号也变正常，会回头质疑 #29 为何需要等待。
3. **避免「单点问题」的措辞**：客户这五条音频基线 4 条异常、ep29 3 条异常，客户手上有反例。改用「这不是靠迭代模型能收敛的问题」，由第 5.3 节的 ep29 数据支撑，立得住。
4. **不要把 demo 当案例**：压缩函数未接入 demo（第 4.2 节），对外只能说「提供参考实现」。
