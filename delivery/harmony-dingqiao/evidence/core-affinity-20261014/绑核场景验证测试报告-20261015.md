# SDK 绑核场景验证测试报告（2026-10-15）

> 目的：验证 SDK 绑核功能（AsrSchedulingConfig，affinity 模式，目标核 cpuIds=[4-11]）在各使用场景下的实际表现，以及绑核异常后能否自动恢复
> 设备/版本：Mate80，amphion_dingqiao v0.3.22-1013，会议纪要离线转写会话（pid 6742）
> 方法：同一识别会话连续穿越 5 个场景，每步用 hdc 抓取 `/proc/<pid>/cpuset`（进程调度组）与 `/proc/<pid>/task/*/status` 的 `Cpus_allowed_list`（全部线程亲和掩码）；全程以 2 秒粒度采样记录 cgroup 切换时刻

---

## 一、测试概览

### 1.1 背景知识

- 系统按前后台状态把进程放入不同 cpuset 调度组：前台 `top-app`（12 核全可用），锁屏/后台 `key-background`（受限核集）
- SDK 绑核是**线程级** `sched_setaffinity` 请求：线程实际可运行的核 = 请求掩码 ∩ 所在 cpuset 允许域；交集为空时内核返回 EINVAL(22)
- 因此绑核是否生效，取决于"线程掩码"与"进程 cpuset"两个层面，日志只能看到前者请求结果，后者需读 /proc 闭环

### 1.2 测试场景序列（同一会话连续穿越）

```
前台识别中 → 锁屏(音频持续) → 解锁回前台 → 亮屏切后台 → 切回前台
   每 步 均 抓 取 cpuset + 全线程掩码快照
```

## 二、场景结果汇总表

| # | 场景 | 系统实际可用核 | SDK 绑核动作 | 生效绑定线程数（4-11） | 失效后自动恢复？ |
|---|---|---|---|---|---|
| 1 | 前台识别中 | 0-11（全 12 核） | 引擎初始化主动绑定 | **26 个**（4-11 大中核） | — |
| 2 | 锁屏（音频持续） | **仅 0-3（4 小核）** | 尝试重绑 → EINVAL(22) 失败 | **0 个**（原 26 个被系统强制改写为 0-3） | ❌ 锁屏期间无恢复（系统限制持续） |
| 3 | 解锁回前台 1 分钟 | 0-11（全 12 核） | 重新绑核（惰性） | **1/26 个**（其余掩码 0-11 为系统自动还原，非 SDK 绑核） | ⚠️ 调度域自动恢复 ✅；SDK 绑核自愈 ✗ |
| 4 | 亮屏切后台 1 分钟 | **0-5（4 小核+2 中核）** | 未新增重绑 | **0 个**（1 个线程残留 4-5 = 原 4-11 与允许域 0-5 的交集改写） | ❌ 同锁屏（限制较浅一档） |
| 5 | 切回前台 1 分钟 | 0-11（全 12 核） | 重新绑核（惰性） | **1/26 个** | ⚠️ 同场景 3 |

**一句话读表**：前台 ✅ 26 个线程绑在 4-11；**锁屏/切后台 ❌ 绑定全部失效、SDK 重绑失败（EINVAL），实际只能用小核/小核+2 中核**；解锁/回前台后调度自动恢复 12 核全可用 ✅，但 **SDK 不会自动重新绑核**（1 分钟仅恢复 1/26，绑定线程池实质丢失）。

### 恢复结论（分两层）

| 层面 | 异常表现 | 自动恢复 |
|---|---|---|
| 系统调度域（cgroup + 全线程掩码 0-11） | 锁屏/切后台时全部线程被压到受限核集 | ✅ **回到前台即自动、完整恢复**（场景 3、5 两次验证），无需 App/SDK 干预 |
| SDK 绑核（4-11 专属掩码） | 进入 key-background 即被改写，运行期重绑 EINVAL | ❌ **不自愈**：解锁后 SDK 有重新绑核动作，但 1 分钟仅恢复 1/26，绑定线程池实质丢失 |

### 性能排序推论

前台（0-11 + 26 绑核）＞ 亮屏切后台（0-5）＞ 锁屏（0-3）。与 10-14 定量的锁屏实时率 ≈0.80×（滞后随锁屏时长线性累积）一致。

## 三、日志分析方法与判断逻辑

### 3.1 第一步：确认绑核配置已下发（App 日志）

```
[OfflineAmphionEngine.ets:1159] OfflineAmphionEngine createEngine schedulingMode=affinity
    cpuIds=[4,5,6,7,8,9,10,11] qos=default spinning=false numThreads=4
```

- **判断**：出现此行 = App 配置下发成功；若缺失，先查 App 侧配置（AmphionSchedulingConst）与引擎创建路径

### 3.2 第二步：看 SDK 绑核执行结果（SDK 日志，tag 含 ionScheduling）

```
A06666/com.tdt...ionScheduling  I  affinity-set   result=0    ← 宽松绑核失败
A06666/com.tdt...ionScheduling  I  affinity-exact result=1    ← 精确绑核成功
A06666/com.tdt...ionScheduling  I  affinity-exact result=0    ← 精确绑核失败
A06666/com.tdt...ionScheduling  I  affinity-set   result=22   ← 回退宽松绑核，22=EINVAL
```

**判断逻辑链**：

| 日志组合 | 含义 |
|---|---|
| `affinity-exact result=1` | 该线程绑核成功（本测试中出现于引擎初始化/前台阶段） |
| `affinity-exact result=0` → `affinity-set result=22` | 精确、宽松两次均失败，EINVAL(22)=请求掩码与进程允许域**交集为空** → 高度怀疑调度域限制，需第三步闭环 |
| 失败时间点与 `handleScreenEvent isScreenOff: true` 相邻 | 失败由场景切换引起，而非参数错误 |

### 3.3 第三步：读 /proc 闭环定位根因（系统侧，hdc）

```bash
# 1) 进程当前调度组
hdc shell cat /proc/<pid>/cpuset
#    top-app = 前台；key-background = 锁屏/后台

# 2) 全线程亲和掩码分布（关键命令）
hdc shell "cat /proc/<pid>/task/*/status | grep Cpus_allowed_list | sort | uniq -c"

# 3) 单线程详情（Name / Cpus_allowed_list / 实际运行核）
hdc shell cat /proc/<pid>/task/<tid>/status
```

**判断逻辑**：

- cpuset=`key-background` 且全部线程 `Cpus_allowed_list: 0,1,2,3` → 请求 4-11 ∩ 允许 0-3 = ∅ → **EINVAL(22) 的必然原因**，排除 SDK 参数/实现问题
- cpuset=`top-app` 且出现 `4,5,6,7,8,9,10,11` 掩码线程 → SDK 绑核成功且生效
- 注意：`Cpus_allowed_list` 是线程请求掩码；cgroup 收缩时掩码可能被改写（本测试场景 2 实证），因此掩码"看起来对"不代表当时可调度，需结合 cpuset 一起看

### 3.4 第四步：验证恢复能力（回前台后重复第三步）

- 全线程掩码自动回到 `0-11` → **系统调度域自愈**（本测试场景 3、5 证实，无需干预）
- `4-11` 掩码线程计数与绑核前对比（本测试 26 → 1）→ **SDK 绑核自愈程度**；本例仅惰性恢复 1 个，判定为不自愈
- 辅助手段：2 秒粒度 cpuset 采样脚本（`pidof` + `cat /proc/$pid/cpuset` 循环），精确记录调度组切换时刻，与场景操作时间对齐

### 3.5 采样脚本（可直接复用）

```sh
# /data/local/tmp/monitor.sh，hdc shell "sh /data/local/tmp/monitor.sh" 后台执行
i=0
while [ $i -lt 600 ]; do
  p=$(pidof com.tdtech.hmtiassistant)
  if [ -n "$p" ]; then
    for one in $p; do
      echo "$(date '+%H:%M:%S') pid=$one cpuset=$(cat /proc/$one/cpuset 2>/dev/null)"
    done
  fi
  sleep 2
  i=$((i+1))
done
```

## 四、最终测试结论

1. **绑核配置下发与前台生效正常**：v0.3.22 在前台可成功绑定 26 个解码相关线程到大中核 4-11（较旧版本仅 1~2 个有明显增强）
2. **锁屏/切后台时绑核必然失效且不可对抗**：系统将进程压入 `key-background`，线程掩码被强制改写（锁屏 0-3 / 亮屏后台 0-5），SDK 运行期重绑 EINVAL(22)——属系统调度域限制，非 SDK 缺陷
3. **恢复能力分层**：系统调度域掩码**回前台即自动完整恢复**（两次验证）；**SDK 绑核不自愈**（1 分钟仅恢复 1/26，绑定线程池实质丢失）
4. **业务影响**：锁屏期解码仅剩 4×1.6GHz 小核，实时率 ≈0.80×，滞后线性累积（10-14 定量）；亮屏切后台（0-5）预计好于锁屏（待滞后曲线验证）
