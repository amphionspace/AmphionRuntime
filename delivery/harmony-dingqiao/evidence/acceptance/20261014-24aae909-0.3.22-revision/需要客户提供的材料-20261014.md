## 第一优先：cpuset 权限探测（5 分钟，决定技术路线）

### 为什么是它

锁屏问题的两条常见入口已被**实测排除**：

| 入口 | 结果 |
|---|---|
| `scheduling.cpuIds = [4..11]` | 熄屏后 `EINVAL`，只能在 cpuset 内收窄、无法扩大，root 亦然 |
| `scheduling.qos` 调到最高档 | 无效，最高档与最低档可用核相同（均为 `0,1,2,3`） |

剩下唯一未排除的方向是**改 cpuset 归属本身**。这需要写 `/dev/cpuset/*/tasks` 的权限，而
**我方设备以 hdc shell 读该路径即被拒**，取决于贵方应用的 selinux 域与签名权限，我方无法代验。

### 怎么做

```sh
# 必须以应用自身身份执行（在应用进程内，或用应用的权限上下文），不是 hdc shell
cat /proc/self/cgroup
ls -l /dev/cpuset/
echo $$ > /dev/cpuset/foreground/tasks && echo OK || echo DENIED
```

请回传三条命令的完整输出。

### 结果怎么用

| 返回 | 后续 |
|---|---|
| **`OK`** | 我方可以做「只把角色分离的工作线程移入宽松 cpuset、每个分析窗口自动重新下发」的方案。粒度比整进程迁移小得多（不动贵方其余 80 个线程的调度域），且不需要应用侧监听屏幕事件 —— 我方绑核作用域构造在每次解码调用里，一秒重试多次 |
| **`DENIED`** | SDK 侧确实无路。需走平台调度保障（计算型长时任务 / cpuset 豁免 / 厂商白名单），或产品方案（屏幕常亮、锁屏期降级、录完统一转写） |

⚠️ 一个必须注意的点：**系统在每次屏幕状态切换时都会把进程挪回受限域**，所以无论谁来做这个
迁移，都要在熄屏事件里重新下发，不能只做一次。

## 第四优先：问题仍在时的材料清单

### 4.0 通用前提：hilog 必须在复现期间流式抓取

**这一条请务必照做，否则材料会白费。** 设备 hilog 是按域滚动的缓冲，事后导出抓不到会话启动期：
我方实测导出的文件跨了 5 天 8059 行，而当轮的 `AmphionMetrics` 只剩 13 条，`role-qos`、
`kind=LOAD`、`kind=SESSION_CONFIG` 全部丢失。`hilog -r` 在该环境清不掉缓冲。同一配置下改用流式
抓取，得到 91031 行完整日志。

```sh
hdc shell hilog > live.txt &          # 点"开始录音"之前就启动
# 在手机上正常操作：进入会议纪要 → 开始录音 → 复现问题 → 停止
kill %1                              # 停止录音之后再关
```

贵方 10-14 这次提供的分段原始 hilog **正是我方需要的形态**，覆盖了会话建立期，非常有帮助。

### 4.0b 最优选项：用 Diagnostics SDK 跑一次复现

包内 `diagnostics-sdk/` 能产出一样东西是任何其他途径都给不了的：**每个 session 的
`sdk-input.wav`，即 SDK 实际收到的音频**。有了它，问题二可以一次定性 —— 到底是麦克风没收到
声音，还是 SDK 收到了却没识别出来。

接口与正式 SDK 完全相同，无需改代码。复现后导出：

```sh
python3 tools/collect_asr_diagnostics.py --device auto --last 1 \
  --bundle <贵方 bundle name> --note "锁屏仍变慢" --include-all-sessions
```

`--bundle` 必须传贵方自己的包名（工具默认读随包 Demo）。多 HAP 应用再加 `--module`。
工具会自行校验、脱敏 hilog、打 ZIP 并给出 SHA-256，直接回传该 ZIP 即可。

### 4.1 锁屏仍变慢

| 材料 | 说明 |
|---|---|
| 两次对照会话的流式 hilog | 同一台机器、同一段话、相近时长，一次亮屏一次熄屏 |
| 两次会话的原始音频 | 未转码、未重采样、未裁剪 |
| 应用的线程相关调用 | 有没有自己绑核、设置线程 QoS、申请长时任务？给出具体调用和参数 |
| cpuset 迁移是否已下发 | 若已按第一项做了迁移，请说明下发时机与是否在熄屏事件里重发 |
| 熄屏期间的 CPU 状态采样（可选但很有用） | 每秒一次：`cat /sys/devices/system/cpu/cpu*/online` 和 `.../cpufreq/scaling_cur_freq` |

partial 间隔不需要贵方统计，我方会从 `CALLBACK_RESULT` 自行计算。

**先看一眼就能分流：**

| hilog 中的现象 | 含义 |
|---|---|
| `affinity-set result=22` 仍在 | cpuset 迁移未生效或未重新下发 |
| `affinity-exact result=1` 已出现但仍慢 | 大核已拿到，瓶颈另有其因，需上表的 CPU 采样继续查 |

### 4.2 吐字慢仍在

| 材料 | 说明 |
|---|---|
| 流式 hilog + 同一次会话的原始音频 | 两者必须是同一次会话，否则无法对齐 |
| 空档的起止时间 | 用手机本地时间，精确到秒 |
| 那段时间实际说了什么 | 口述大意即可，不需要逐字 |
| 说话人距麦克风多远、是否外放/免提/蓝牙耳机 | 决定输入增益是否够 |
| 录音链路参数 | 采样率、声道数，以及音频是否经过 AEC / 降噪 / AGC |

最有价值的仍是 4.0b 的 `sdk-input.wav`。若确实无法提供，退一步的办法是**复现时用另一台设备或
录音机并行录一份**：若并行录音里听得清而 SDK 没出文字，问题在我方；若并行录音里也听不清，
问题在采集链路。

### 4.3 角色结果仍迟到

| 材料 | 说明 |
|---|---|
| 覆盖整段会话的流式 hilog | 不能只给尾部。我方此前因只拿到尾部日志而得出过错误结论 |
| **`kind=DIARIZATION_FINISH` 那一行** | 本版新增，正式包即可见。**它一行就能区分三种原因**，是这一项最关键的材料 |
| 会议实际人数 | `maxSpeakers` 上限为 4；超过 4 人时角色结果本身就会不准 |
| 两个回调的到达时间 | `onSpeakerDiarizationUpdate` 与 `onSpeakerDiarizationResult`，应用侧打点即可 |
| 会话总时长 | 权威角色结果按 120 秒提交周期产出，短会话本就会「迟到」 |

`kind=DIARIZATION_FINISH` 的读法：

| 字段 | 指向 |
|---|---|
| `stopToAsrTailMs` 大 | ASR 排空慢（该段不受角色预算约束） |
| `backlogWindowsAtStop` / `stopToDrainedMs` 大 | 角色推理落后于音频 |
| `lastCommitClusterMs` 大 | 聚类本身慢 |
| `inferenceEndMs` ≪ `audioEndMs` | 尾部未被角色覆盖（截断量） |

### 4.4 材料怎么整理

- **一次会话一个目录**，内含 hilog、原始音频、一行说明（时间、机型、系统版本、SDK 版本、是否开
  说话人分离、是否锁屏、现象一句话）。
- **音频不要转码，不要重采样。** 若因会议内容敏感必须裁剪，请**保留空档前后各 2 分钟**并说明
  已裁剪 —— 我方需要这段上下文来判断输入增益和有声占比，裁得太紧就判不了。
- **不要只给截图。** 我方需要可检索的文本日志。
- 日志里如含敏感内容，可自行替换，但请保留 `AmphionMetrics` / `AmphionRuntime` / `AmphionScheduling`
  这几个标签的行不变 —— 定位全靠它们。
