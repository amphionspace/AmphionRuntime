# 三个现场问题的成因分析（2026-10-14）

> 适用版本：HarmonyOS ASR SDK 0.3.22 修订包（源码提交 `24aae909`）
> 设备：Kirin 9020 / Mate 80（同一颗 SoC，`kirin9020_v2_0`），OpenHarmony-6.1.1.120
>
> 本文只写有证据支撑的结论。**我方对问题一的归因错过两次，两次都写在这里**，因为客户按第一版
> 归因做过配置、浪费了一轮测试，这个过程本身是第二版归因的证据。

---

## 一、锁屏后识别变慢（问题一）：未解决，且 SDK 侧无独立解法

### 1.1 根因：熄屏时系统把整个进程移入仅含 4 个小核的调度域

三条互相独立的证据：

| 来源 | 证据 |
|---|---|
| 客户现场巡检 | `/proc/<pid>/cpuset` 由 `top-app` 变 `key-background`；79~83/83 线程掩码全为 `0-3` |
| **客户日志里我方 SDK 自己打的** | 熄屏后 `affinity-exact result=0` → `affinity-set result=22`（`EINVAL`） |
| 我方设备直接读取 | 熄屏时 `/proc/<pid>/cpuset = /cpuset/key-background`；后台态 `Cpus_allowed_list: 0,1,2,3` |

`EINVAL(22)` 的含义是确定的：请求掩码 `{4..11}` 与进程允许集的**交集为空**。内核会把
`sched_setaffinity` 的掩码与所属 cpuset 的 `cpus` 求交，空集即 `EINVAL`。

时间上也吻合：第一场熄屏 09:29:15，`affinity-exact result=0` 在 09:29:14、`result=22` 在 09:29:20；
第二场熄屏 09:41:03，对应两行在 09:41:02 和 09:41:08。

### 1.2 两条常见入口都已被实测排除

| 入口 | 结果 |
|---|---|
| `scheduling.cpuIds = [4..11]`（客户已配） | 亮屏 `affinity-exact result=1` 成功；熄屏 `EINVAL`。**只能在 cpuset 内收窄，无法扩大，root 亦然** |
| `scheduling.qos` 调到最高档 | **无效**。实测熄屏下持 `QOS_USER_INTERACTIVE`（最高档）的识别线程与持 `QOS_BACKGROUND`（最低档）的角色线程，`Cpus_allowed_list` 相同，均为 `0,1,2,3`，进程全部 54 个线程亦然 |

**QoS 决定的是既定核集合内的调度权重，核集合本身由系统指派。** 这两件事在该设备上是独立的。

### 1.3 我方两次归因错误

**第一次（10-12）**：认为根因是 SDK 自己在 `hop ≥ 2000` 时把角色线程降到 `QOS_BACKGROUND`，
据此交付了 `scheduling.displayMayTurnOff` 开关。

**否证**：客户开启该开关后复测两场，全量 hilog 中 `role-qos` 一条都没有（证明开关生效、SDK 不再
申请降档），而实时率仍为 0.80×、滞后随锁屏时长线性累积至峰值 67.6 s。

**第二次（同一前提的更深一层）**：上述归因依赖我方写进源码注释和交付文档的一句论断 ——
「background QoS 隐含 background cpuset，所以应用侧绑核拼不过它」。**该论断经实测否证**（见 1.2）。

所以 `displayMayTurnOff` 不是实现有缺陷，而是整条因果链从一开始就错了。该开关的实际作用仅是
「不让角色线程在已被限制的那几个核里再被降权」，现场复测未测出可辨识收益。本包保留它只为不
破坏已按它配置的集成。

### 1.4 成本在哪：segmentation 占 73%，而我方优化的 encoder 只占 5%

我方在**相同的 4 小核**约束下实测 24 分钟、716 个窗口（hop 2000）：

| 阶段 | 中位 | 占比 |
|---|---|---|
| **segmentation**（pyannote 分割） | **446.1 ms** | **73%** |
| fbank | 89.7 ms | 15% |
| pooling | 44.2 ms | 7% |
| encoder（已在 NNRt 加速器上） | 32.3 ms | 5% |
| 单窗合计 | 612 ms | |

0.3.21 / 0.3.22 把 encoder 搬上 NPU，动的是这 5%。客户报告把 v0.3.19 → v0.3.22 的
0.54× → 0.80× 归因于它，**该归因缺少依据**。

### 1.5 为什么 SDK 侧补不上

从 0.80× 到 1.0× 需腾出 **0.20×**。而角色分离链**全部**开销只有 **0.180×**
（258.7 s 墙钟 / 1440 s 音频）：

| 杠杆 | 可腾出 | 状态 |
|---|---|---|
| 放宽 hop（2000 → 4000） | ~0.090× | 被挡住：`CommunityHopSamples` 取相邻窗口起点的**最小**间距，中途改 hop 会使 VBx 的 Fb 按密集证据缩放而后半段实际稀疏，正是 #260 要修的失败模式 |
| 分割换 MS Lite CPU 运行时 | ~0.083× | 未验证。10-08 探针显示同一张图 35.2 vs ORT 97 ms/窗，但非受控对比，且未在小核域验证 |
| **分割改用 2 线程** | **0.018×（本包已实施、已实测）** | 分割模型含 4 个双向 LSTM，沿时间步串行，加线程只能并行前端卷积 |
| 停用角色分离（理论上限） | 0.180× | **仍 < 0.20×** |

**连把角色分离整个删掉都补不上缺口。** 这不是一个能由 SDK 单独关闭的问题。

### 1.6 一个必须排除的变量

客户测出 0.80× 用的 10-13 包，其**正式 SDK 被我方误用 diagnostics 模式构建**（诊断模块含逐回调
事件落盘）。在 1.6 GHz 小核上这笔开销不可忽略，**0.80× 中有多少来自它目前未知**。本包已修正为
`debug` 模式，需用本包复测才能得到干净基线。

### 1.7 剩下的方向

| 方向 | 性质 | 状态 |
|---|---|---|
| 把进程或其工作线程移入含大核的 cpuset | 需系统权限，且每次屏幕状态切换后需重新下发 | **唯一能独立解决的，待客户确认权限** |
| 平台提供面向后台持续推理的调度保障 | 需平台方 | 客户已向平台方提出 |
| 产品方案：屏幕常亮 / 锁屏期降级 / 录完统一转写 | 需产品决策 | — |

客户亮屏稳态 lag ≈ 0.5 s，证明大核下本来就 ≥1×，所以第一条若可行即可彻底解决。

**注**：若客户确认有权限，我方可以做「只把角色分离的工作线程移入宽松 cpuset、每个分析窗口自动
重新下发」的方案 —— 粒度比整进程迁移小得多，且不需要应用侧监听屏幕事件（我方绑核作用域构造在
每次解码调用里，一秒重试多次）。但该方案依赖权限，必须先确认。

## 二、开说话人分离后吐字慢（问题二）：机制已修，主要症状仍在

### 2.1 根因：两条端点规则互相抵消

| 规则 | 原状 | 后果 |
|---|---|---|
| rule3（20 秒句长兜底） | 长录音模式按设计禁用（为长文本无损） | 没有句长上限 |
| rule1（静音即切句） | 全局开启 | 在没有文字的静音处把解码流切掉，使句长计数永远累积不到 rule3 的阈值 |

两者叠加的结果是：长段朗读只能等自然停顿。实测最长 **105 秒**无输出。

### 2.2 已做的修正与实测

长录音模式关闭 rule1，并由 25 秒句长上限接替兜底：

| 语料 | 指标 | 修前 | 修后 |
|---|---|---|---|
| 客户稀疏语音 120 s | 最大无输出空档 | 105.1 s | **72.5 s** |
| 客户稀疏语音 120 s | final 数 | 3 | 5 |
| 去静音连续语音 301 s | 最大 final 间隔 | 77.8 s | 66.7 s |
| 去静音连续语音 301 s | final 数 | 22 | 24 |
| 去静音连续语音 301 s | final 间隔 p90 | 24.8 s | 24.7 s |

p90 的 24.7 s 与 25 秒上限吻合，说明上限确实在起作用。

本包进一步让 `endpointMaxUtteranceMs` 在长录音模式真正生效（此前被接受后忽略），客户可调小它
换更快上屏。

### 2.3 残余部分：判断该段音频无可转写语音，待客户确认

最大空档仍有 72.5 s。我方做了三种**互相独立**的干预，结果全部停在同一地板：

| 干预 | 最大空档 |
|---|---|
| 基线 | 105.1 s |
| 仅放大输入 4 倍 | 73.2 s |
| 仅关闭 rule1 | 72.5 s |
| 两者组合 | 73.1 s |

三臂落在 72.5–73.2 s 同一地板，据此判断瓶颈不在端点策略，而是那段录音没有可转写的语音。
该段（`0937.wav` 约 09:59:56–10:01:02）有声占比 8–47%（正常区间 49–73%），RMS 125–520
（可转写段落 561–2180）。

**该判断未经客户确认。** 需要客户回答那几十秒内是否有人在正常说话、距麦克风多远。

### 2.4 顺带更正客户分析中的两点

- **中间结果没有被压制。** 该会话共 999 条 partial，中位间隔 0.66 s。日志里的 `RESULT_SUPPRESSED`
  全部是空结果，不是被压住的文本。
- **日志中 14.22 s 的那个「空档」是会话边界**，不是识别停顿；3 倍这个比较跨了两个会话，不是同一
  条件下的对比。

### 2.5 一个重要发现：锁屏期文字本身是跟得上的

从客户 10-14 日志统计 `kind=UTTERANCE`：

| 阶段 | 首个 partial | 句末→final | 扣掉句长后的真实滞后 | 句长中位 |
|---|---|---|---|---|
| **锁屏期**（29 句） | **803 ms** | **405 ms** | **1.65 s** | 12.4 s（最长 25.0 s） |
| 亮屏排空期（20 句） | 500 ms | 51 ms | — | 5.7 s |

识别器在锁屏期没有落后。落后的只有角色标签：**26/29 个 final 的 `speakerIndex = -1`**。

所以客户报告中的「锁屏实时率 0.80×」量的是**角色窗口的吞吐**，不宜表述为「离线解析实时率」。
而用户感知的「说完等 30~40 秒才上屏」，更可能是界面只渲染 final（要等整句说完 12~25 s）叠加
等角色标签（滞后 13~67 s）。**改渲染策略不需要改 SDK，可能解掉大部分可见延迟。**

## 三、角色结果迟到（问题三）：机制已修，现场效果未验证

### 3.1 根因：预算的计时起点与调用方度量的区间不一致

原版 `SpeakerDiarizationFinishBarrier` 的预算**自 ASR 尾部到达才起算**，不是自停录；而打捞宽限
是在预算之后**追加**的。所以结构上的最坏值是：

```
停录 → 结果  =  ASR 排空  +  15 s  +  3 s
```

客户报告的 24 分钟录音 21.6 s 完全落在这个包络内 —— **代码并无缺陷，但我方从未承诺客户正在量的
那个指标**。

### 3.2 已做的修正

把截止锚到停录，并把打捞预留从截止**内部**切出：

| 项 | 原版 | 本包 |
|---|---|---|
| 计时起点 | ASR 尾部 | 停录 |
| 打捞宽限 | 追加 3 s | 内部切出 |
| 结构最坏值 | `ASR 排空 + 15 + 3` | **`max(ASR 排空, 14 s)`** |

ASR 仍豁免：它必须排空全部已接受音频，否则会丢失已承诺的识别文本。

另加一条例外：**截止到期而 ASR 尚未排空时，不触发打捞。** 因为此时回调本来就被 ASR 堵着，提前
冻结角色一秒也省不出来、只会白丢标签。

### 3.3 三臂真机验证

| 臂 | 配置 | 结果 |
|---|---|---|
| 健康基线 | 24 分钟、亮屏、默认 | 停录→角色结果 **2.785 s**，推理零欠账，未超时 |
| 强制积压 | hop 250 + CPU encoder | **14001 ms**（旧锚点等价 18646 ms），客户可见 stop→complete **14104 ms < 15000** |
| 慢 ASR 尾部 | 再叠单线程 ASR + 全速喂入 | `stopToSalvageMs = stopToAsrTailMs = 15120`，延迟打捞成立，推理保住多出的 4.1 s |

**一个只有真机能暴露的设计错**：内部截止最初设成正好 15000 ms，实测客户可见值为 15099 ms、
仍越界 —— 截止触发之后还要走 barrier 完成、构造降级结果、三次回调分发，这段开销 99 ms。
单元测试用假定时器看不到它。故内部截止取 **14000 ms**，留约 1 秒余量。

### 3.4 新增的可观测性

`kind=DIARIZATION_FINISH`，每会话一条，走 `[AmphionMetrics]` hilog 通道、正式包可见。它把收尾
时间拆成三个可判别的分量：

| 字段 | 指向的原因 |
|---|---|
| `stopToAsrTailMs` | ASR 排空（截止时间压不动的那段） |
| `stopToDrainedMs` / `backlogWindowsAtStop` / `pendingCommitsAtStop` | 角色推理落后于音频 |
| `lastCommitClusterMs` | 聚类本身 |

另附 `inferenceEndMs` / `audioEndMs`（角色覆盖到哪）、`encoderBackend`（实际后端）、
`timedOut` / `salvaged`。

### 3.5 未验证

三臂均为我方构造场景（通过 hop 250 + CPU encoder 人为制造积压）。**客户现场那次 21.6 s 未用本版
复测。**

## 四、三个问题的状态汇总

| 问题 | 根因 | 状态 |
|---|---|---|
| 一、锁屏变慢 | 进程级 cpuset（系统行为） | ❌ **未解决**，SDK 侧无独立解法；缺口 0.20× 而角色链全部开销 0.180× |
| 二、吐字慢 | rule1 与 rule3 互相抵消 | ⚠️ **机制已修**（105 → 72.5 s），**主要症状仍在**；残余归因待客户确认 |
| 三、角色结果迟到 | 预算计时起点与调用方度量区间不一致 | ⚠️ **机制已修并三臂验证**（18646 → 14001 ms），**现场效果未验证** |

## 五、我方在本轮中出的错，一并记录

1. **正式包被 diagnostics 污染**（`8e9b4678` 10-12、`c23c8f3d` 10-13 两个包）。成因是组包时先执行
   diagnostics 构建，而自包含 HAR 组装脚本只重打已构建的 HAR。**该缺陷影响了现场结论** —— 客户
   的 0.80× 是在被污染的包上测的。本包按正确顺序执行并显式核验。
2. **问题一归因错两次**（见 1.3）。客户按第一版归因做过配置并浪费了一轮测试。
3. **把 `endpointMaxUtteranceMs` 静默忽略**。客户配了 60000，长录音模式下实际生效的是硬编码的
   25 s，且没有任何日志说明。本包改为采纳并回显有效值。
4. **两轮修订的行为变更未写进客户升级说明**。10-12 那轮的 rule1 关闭、25 秒上限、
   `displayMayTurnOff` 一条都没写，客户拿到带默认行为变更的包却没有对应说明。本包补齐。
