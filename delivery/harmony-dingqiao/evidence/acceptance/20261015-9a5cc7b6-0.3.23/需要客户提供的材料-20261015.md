## 第零优先：豁免生效之后的六项（本轮新增，按重要性排）

贵方 10-15 晚的长测把问题推进了一大步，但也暴露出几个**没有人在盯**的指标。我方按 `日志3`
的原始数据复核后，认为下面六项决定"长时锁屏转写能不能上生产"。详细论证见《交付邮件》第五节。

### 0.1 耗电（最可能卡住量产的一项，目前完全空白）

长测全程 USB 在线、电量 100%、充电状态 `Full`，电池电流 µA 级、功率 <3 mW——**等于耗电没测**。
而 `key-background` 这个调度域存在的唯一理由就是省电；平台方要不要把豁免放进量产版本，
看的就是这个数。

**要什么**：拔掉 USB、从 80% 电量起跑同样协议的 1 小时，报（a）电量下降百分比、
（b）平均功率、（c）同机"不开会话待机 1 小时"的对照基线。

### 0.2 进程内存（比发热更硬的限制，贵方报告未提）

`功耗快照.csv` 的 `app_mem_kb` 全程单调上升：645 MB（t10）→ **949 MB（t60）**，
约 5.9 MB/min，**且每 10 分钟的增量本身在变大**（+28 / +53 / +76 / +85 MB）。
会话停止后回落到 848 MB，说明是会话内累积、非永久泄漏。

按此斜率，**2 小时会议进程内存约 1.3 GB**，很可能先于发热成为长会议的硬上限。

**要什么**：下一轮长测把 `app_mem_kb` 一并采样（沿用现有 10 分钟快照即可）。
这里有我方自己的成因（见《交付邮件》5.4、5.5），我方会同步修。

### 0.3 一轮 2 小时长会议

锁屏段 1.4 s/min 的欠账**不能线性外推**：成因是角色分离每次提交全量重聚类，代价随会议时长
超线性增长。40 分钟看着温和，2 小时未必。同时 0.2 的内存、以及后壳温度按 0.065 °C/min
外推到 2 小时约 42 °C，都要在这个时长上才看得见。

**要什么**：同一豁免配置、同样协议，锁屏 2 小时，采 lag / 内存 / 温度三条曲线。

### 0.4 `system-default` 与 `top-app` 的 `cpu.shares`（向平台方要，一个数）

豁免改的是 `cpuset`（能用哪些核），不改调度权重（竞争时能拿到多少）。这解释了贵方观察到的
"亮屏后台反而最差"——那一段整机占用从 28% 涨到 61%，我方进程份额被压缩，**而不是温控降频**
（内核 `tz shell_level` 全程为 0，最高频反而升到 1997 MHz）。

**要什么**：`/dev/cpuctl/system-default/cpu.shares`（或 `cpu.weight`）与 `top-app` 的对应值。
若确实差一档，长会议场景应引导**锁屏**，而不是"亮屏但切到别的应用"。

### 0.5 角色分离的提交周期配置值 + lag 拆成两条曲线

贵方的 lag 口径是"日志时刻 − diarization endTime"，**它天然包含最多一个提交周期**：一条在
窗口开头结束的 utterance，必须等到该窗口提交才会上报。所以报告里 115 s / 64.4 s 两个峰值里，
有多大一块是真积压、多大一块是提交周期，目前分不开。

贵方观察到的"每分钟一批、4 段 × 25 s"正是提交周期的形状，**这是设计行为**
（`DiarizationCommitClock`，默认 120000 ms，可配）。

**要什么**：（a）贵方 App 配置的提交周期值；（b）把 lag 拆成 **ASR final 的 lag** 与
**角色分离结果的 lag** 两条曲线——用户感知的"出字慢"是前者，现在量的是后者。
两条都可以从已有日志重算，不需要重测。

### 0.6 最后一条 utterance 的 endTime（一个数，证明尾部没丢）

`totalBytes = 3802.5 s = 墙钟 1×` 证明的是**采集**完整，不是**转写**完整。贵方停止会话时
lag 正在 10~100 s 之间波动，正好落在风险区——我方实测过：积压 133 秒时停止录音、30 秒后拆
会话，最终文本少 15%。

**要什么**：最后一条 utterance 的 `endTime` 是否 ≈ 3802 s。是，则尾部完整，该项关闭。

> 另：贵方报告引用的"豁免前 10.6 s/min"来自 10-13 被 diagnostics 污染的包。干净包口径下
> 熄屏欠账是 **8.0 s/min**，所以真实改善是 **约 5.7 倍**而不是 7 倍。对外引用请用后者。

## 第三优先：cpuset 权限探测（5 分钟）

### 为什么

锁屏问题的两条常见入口已被实测排除：

| 入口 | 结果 |
|---|---|
| `scheduling.cpuIds` | 熄屏后无效（见上），`[4..11]` 熄屏时 `EINVAL`，只能在 cpuset 内收窄、无法扩大，root 亦然 |
| `scheduling.qos` 调到最高档 | 无效。实测熄屏下最高档 `QOS_USER_INTERACTIVE` 与最低档 `QOS_BACKGROUND` 的 `Cpus_allowed_list` 相同，均为 `0,1,2,3` |

剩下的调度类方向是**改 cpuset 归属本身**。这需要写 `/dev/cpuset/*/tasks` 的权限，
**我方设备以 hdc shell 读该路径即被拒**，取决于贵方应用的 selinux 域与签名权限，我方无法代验。

> 与上一版的差别：上一版写这是"唯一还没被排除的方向"。**现在依然基本成立，但原因变了** ——
> 缺口虽从 0.20× 修正到 0.134×，但干净包受控实测表明角色分离侧优化的收益上限只有 0.091×，
> 仍够不到。调度类方向（本项）与 ASR 主链路调参是剩下的两条路。

### 怎么做

```sh
# 必须以应用自身身份执行（在应用进程内，或用应用的权限上下文），不是 hdc shell
cat /proc/self/cgroup
ls -l /dev/cpuset/
echo $$ > /dev/cpuset/foreground/tasks && echo OK || echo DENIED
```

请回传三条命令的完整输出。

### 结果怎么用

| 返回 | 后续 |
|---|---|
| **`OK`** | 我方可以做"只把角色分离的工作线程移入宽松 cpuset、每个分析窗口自动重新下发"的方案。粒度比整进程迁移小得多，且不需要应用侧监听屏幕事件 —— 我方绑核作用域构造在每次解码调用里，一秒重试多次 |
| **`DENIED`** | 调度类方向到此为止，转走 SDK 算法杠杆 + 平台调度保障 + 产品方案三条线 |

⚠️ **系统在每次屏幕状态切换时都会把进程挪回受限域**，所以无论谁做这个迁移，都要在熄屏事件里
重新下发，不能只做一次。我方实测已确认：解锁回到 `top-app` 时，内核会把全部线程掩码重置。

## 第四优先：三个关于现场使用方式的问题（不需要测，回答即可）

> 其中第 1 问，贵方 10-15 报告已部分回答：报告区分了"解锁回前台"与"亮屏切后台"两种状态，
> 并测到前者调度域完整自愈。仍需确认的是**现场用户的实际习惯**——是解锁，还是只点亮屏幕看一眼。

这三条来自本轮实测中发现的、与用户感受直接相关的行为，答案会影响产品侧建议。

**1. 用户在锁屏录制过程中，是"按电源键点亮看一眼"还是"解锁进入应用"？**

我方实测：`wakeup` 之后进程仍在 `/cpuset/background`（仍是 4 个小核），排空速率只有
**0.618×**；**滑动解锁后** cpuset 才回到 `top-app`、追赶速率才到 **1.550×**。
如果用户习惯只点亮不解锁，那么"亮屏后还要等很久"就有了直接解释，产品提示也应当改成引导解锁。

**2. 停止录音时，界面是否会等待转写排空？等多久？超时后怎么处理？**

我方实测：在积压 133 s 时停止录音、30 秒后拆除会话，最终文本 **1869 字**，而同一段音频正常
应为 **2199 字**，**少 15%**；给够排空时间的场次则是 2199 字、与亮屏逐字节一致。
**丢的是时间不是识别能力**，但 UI 若固定超时就拆引擎，用户会真的丢文字。

**3. 界面是只渲染 final，还是 partial 也上屏？角色标签是否作为渲染前置条件？**

这条上一封信问过，但当时我方附带的判断是错的（见下），所以重新问一次。

## 第五优先：问题仍在时的材料清单

### 5.0 通用前提：hilog 必须在复现期间流式抓取

**这一条请务必照做，否则材料会白费。** 设备 hilog 是按域滚动的缓冲，事后导出抓不到会话启动期：
我方实测导出的文件跨了 5 天 8059 行，而当轮的 `AmphionMetrics` 只剩 13 条，`role-qos`、
`kind=LOAD`、`kind=SESSION_CONFIG` 全部丢失。`hilog -r` 在该环境清不掉缓冲。同一配置下改用流式
抓取，得到 91031 行完整日志。

```sh
hdc shell hilog > live.txt &          # 点"开始录音"之前就启动
# 在手机上正常操作：进入会议纪要 → 开始录音 → 复现问题 → 停止
kill %1                              # 停止录音之后再关
```

贵方 10-14 这次提供的分段原始 hilog **正是我方需要的形态**，覆盖了会话建立期，非常有帮助。

### 5.0b 最优选项：用 Diagnostics SDK 跑一次复现

包内 `diagnostics-sdk/` 能产出一样东西是任何其他途径都给不了的：**每个 session 的
`sdk-input.wav`，即 SDK 实际收到的音频**。有了它，问题二可以一次定性 —— 到底是麦克风没收到
声音，还是 SDK 收到了却没识别出来。

接口与正式 SDK 完全相同，无需改代码。复现后导出：

```sh
python3 tools/collect_asr_diagnostics.py --device auto --last 1 \
  --bundle <贵方 bundle name> --note "锁屏仍变慢" --include-all-sessions
```

`--bundle` 必须传贵方自己的包名（工具默认读随包 Demo）。多 HAP 应用再加 `--module`。
工具会自行校验、脱敏 hilog、打 ZIP 并给出 SHA-256，直接回传该 ZIP 即可。

> ⚠️ **但不要用 Diagnostics SDK 测性能基线。** 它每次 `writeAudio` 多打 2 条事件
> （20 ms 分片即约 105 条 hilog/秒），实测在 4 小核上值 ≥0.22× 实时率。
> **测性能用正式 SDK，定位内容问题用 Diagnostics SDK。**

### 5.1 锁屏仍变慢

| 材料 | 说明 |
|---|---|
| 两次对照会话的流式 hilog | 同一台机器、同一段话、相近时长，一次亮屏一次熄屏 |
| 两次会话的原始音频 | 未转码、未重采样、未裁剪 |
| 应用的线程相关调用 | 有没有自己绑核、设置线程 QoS、申请长时任务？给出具体调用和参数 |
| **屏幕状态时间线** | 熄屏时刻、点亮时刻、**解锁时刻**（三者要分开，解锁才是算力恢复点） |
| **停录时刻与界面等待行为** | 见第四优先第 2 问 |
| cpuset 迁移是否已下发 | 若已按第三优先做了迁移，请说明下发时机与是否在熄屏事件里重发 |
| 熄屏期间的 CPU 状态采样（可选但很有用） | 每秒一次：`cat /sys/devices/system/cpu/cpu*/online` 和 `.../cpufreq/scaling_cur_freq` |

partial 间隔不需要贵方统计，我方会从回调日志自行计算。

**先看一眼就能分流：**

| hilog 中的现象 | 含义 |
|---|---|
| `affinity-set result=22` 仍在 | cpuset 迁移未生效或未重新下发 |

| `affinity-exact result=0` 且 `affinity-set result=0` | 绑核请求被系统静默改写（该机型/版本不接受此 cpuIds），退回 `[4,5,6,7]` |

### 5.2 吐字慢仍在

| 材料 | 说明 |
|---|---|
| 流式 hilog + 同一次会话的原始音频 | 两者必须是同一次会话，否则无法对齐 |
| 空档的起止时间 | 用手机本地时间，精确到秒 |
| 那段时间实际说了什么 | 口述大意即可，不需要逐字 |

| **该次会话是否锁屏** | 锁屏期的"吐字慢"与问题二的"吐字慢"成因完全不同，必须分开统计 |

录音机并行录一份**：若并行录音里听得清而 SDK 没出文字，问题在我方；若并行录音里也听不清，
问题在采集链路。

| 覆盖整段会话的流式 hilog | 不能只给尾部。我方此前因只拿到尾部日志而得出过错误结论 |
| **`kind=DIARIZATION_FINISH` 那一行** | 本版新增，正式包即可见。**它一行就能区分三种原因**，是这一项最关键的材料 |
| 会议实际人数 | `maxSpeakers` 上限为 4；超过 4 人时角色结果本身就会不准 |
| 两个回调的到达时间 | `onSpeakerDiarizationUpdate` 与 `onSpeakerDiarizationResult`，应用侧打点即可 |
| 会话总时长 | 权威角色结果按 120 秒提交周期产出，短会话本就会"迟到" |

`kind=DIARIZATION_FINISH` 的读法：

| 字段 | 指向 |
|---|---|
| `stopToAsrTailMs` 大 | ASR 排空慢（该段不受角色预算约束） |
| `backlogWindowsAtStop` / `stopToDrainedMs` 大 | 角色推理落后于音频 |
| `lastCommitClusterMs` 大 | 聚类本身慢 |
| `inferenceEndMs` ≪ `audioEndMs` | 尾部未被角色覆盖（截断量） |

### 5.4 材料怎么整理

- **一次会话一个目录**，内含 hilog、原始音频、一行说明（时间、机型、系统版本、SDK 版本、
  是否开说话人分离、是否锁屏、**是否解锁过**、现象一句话）。
- **音频不要转码，不要重采样。** 若因会议内容敏感必须裁剪，请**保留空档前后各 2 分钟**并说明
  已裁剪 —— 我方需要这段上下文判断输入增益和有声占比，裁得太紧就判不了。
- **不要只给截图。** 我方需要可检索的文本日志。
- 日志里如含敏感内容可自行替换，但请保留 `AmphionMetrics` / `AmphionRuntime` /
  `AmphionScheduling` 这几个标签的行不变 —— 定位全靠它们。
