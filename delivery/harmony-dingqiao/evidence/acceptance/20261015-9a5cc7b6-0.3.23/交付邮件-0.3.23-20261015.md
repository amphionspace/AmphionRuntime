**主题：HarmonyOS ASR SDK 0.3.23（修复念数字的转写问题，另修一处绑核在锁屏后失效的缺陷）**

各位好，

本次提供 HarmonyOS ASR SDK **0.3.23**。针对你们 10-15 反馈的"念一二三四五六七八九十，输出不含
十且中间带空格"，本版已修复，另外顺带修掉了你们在《绑核场景验证测试报告》里测到的
"解锁后只恢复 1/26"。

**识别模型、角色分离算法与所有默认调度参数均未改动**，公共接口、回调顺序与角色结果格式沿用
0.3.22，接入代码无需修改。但**识别文本会变**，请先读第一节。

**为什么换成 0.3.23 而不是再发一个 0.3.22**：你们已经先后收到两个不同的 0.3.22 制品（10-13 与
10-14），本版又改了识别文本，再沿用同名会让现场报告无法对齐。我方交付台账也只接受
`主.次.修订` 三段版本号，带日期的后缀（如 `0.3.22-1015`）不被接受。

## 一、念数字的问题已修（你们反馈的那个）

```
念：一二三四五六七八九十
0.3.22 输出：123 4567 80 ~ 90。
0.3.23 输出：12345678910。
```

**先说清一件事：识别本身没有错。** SDK 诊断流里的 `rawText` 是完整的
`一二三四五六七八九十`，十个字一个不少。错在后面两层：

**第一层（ITN 逆文本归一化）**：中文 ITN 的上游语法把 `一二三四五六七八九十` 读成
`cardinal { value: "123 4567 80~90" }` —— 既把数字串切成三组，又把结尾的"十"当成汉语口语里的
概数（"八九十岁"≈八十到九十）渲染成范围。**所谓"没有十"，是"十"被并进了 `90` 里。**
本版在归一化之前把连续单字数字串直接折叠成数字，不再交给上游语法分组。

**第二层（标点模型）**：ct-transformer 本应只插标点，但同时会对 ASCII 字符串重新加空格 ——
`~` 两侧那两个空格就是它加的。本版改为按对齐保留它插入的标点、丢弃它新插入的空格。

**第二层的影响面比第一层更大**，因为它影响所有经 ITN 产出符号的文本：

| 念出的内容 | 0.3.22 | **0.3.23** |
|---|---|---|
| 一二三四五六七八九十 | `123 4567 80 ~ 90。` | **`12345678910。`** |
| 八九十 | `80 ~ 90。` | **`8910。`** |
| 两点五八万 | `2 . 58万。` | **`2.58万。`** |
| 二零二六年五月十五日 | `2026 / 05 / 15。` | **`2026/05/15。`** |

后两行说明这个问题早就存在，只是没人报：日期和金额一直在多带空格。

**没有回归**（均真机复测）：`三十八` → `38`、`八十` → `80`、`一二三` → `123`、
`一二三四五` → `12345`、`幺三八零零一三八零零零` → `13800138000`。

**请你们注意一处**：如果界面或下游对数字文本做过字符串匹配或正则抽取，升级前请按上表复核。

**一个已知残留**：以"十"结尾的数字串，其 `textNormalization.spans` 会为空（文本正确，只是不带
归一化区间）。原因是折叠后上游语法改为逐位记录，而"十"一个汉字要产出 `1`、`0` 两个字符，
必然出现宽度为 0 的区间被既有校验拒绝，UTF-8 字符中间无法切分。若你们用这组区间做回溯，
需要容忍空数组；我方 523 秒多人会议实测中 79/79 条区间完好，该模式未出现。

## 二、绑核在锁屏后失效，本版已修

你们 10-15 报告测到"解锁回前台后 1 分钟仅恢复 1/26"。成因确定：

ORT 推理工作线程在**线程启动时绑核一次**，而系统在进程切换 cpuset 调度组时会重写**全部线程**
的亲和掩码。此后只有解码调用自身那个线程会被重新绑定，引擎初始化时建立的那批工作线程不再有人
重绑——**"26 → 1"里的那个 1 就是调用线程。**

本版记录 SDK 自己创建的工作线程 id，在检测到调度组迁移后对**这些线程**重新下发配置的 `cpuIds`
（绝不触碰不属于 SDK 的线程）。内核的掩码重写是逐线程异步完成的，单次扫描会被覆盖，因此迁移后
持续重试 3 秒。实测（`cpuIds=[0,1,2,3]`，录音中途熄屏 → 解锁）：

| | 亮屏起始 | 解锁后 |
|---|---|---|
| 0.3.22 | 9~11 个线程持有配置掩码 | **1 个** |
| **0.3.23** | 11~12 个 | **9~10 个（恢复）** |

**但要把这条的实际收益讲准**：我方实测解锁后**全核自由调度本身就是最快的排空状态**
（1.550× 实时率），而绑中核 4-7 为 1.000×、不绑核 0.997×（ASR 滞后 40 ms 对 140 ms）。
所以对你们 `[4..11]` 的配置，"绑核丢失"的性能代价接近于零。**这条修复的价值是让绑核功能在
经历锁屏后仍然有效、行为可解释，不是性能救援** —— 请不要据此排高优先级。

另外这条修复让 SDK **忠实执行**配置：若 `cpuIds` 配的是小核，解锁后也会被重新绑回小核。

## 三、关于 `cpuIds=[4..11]`：你们的配置不用改

我方原本要建议你们改成 `[4,5,6,7]`，**现在撤回**：你们 10-15 报告所附 hilog 里前台
`affinity-exact result=1`，说明 `[4..11]` 在你们设备上精确生效。两边不一致是设备与版本差异：

| | 我方 | 贵方 |
|---|---|---|
| 机型 | Mate 80（我方测试机） | Mate 80（贵方设备） |
| 系统 | 6.1.0.135 / OpenHarmony-6.1.1.120 | 6.1.2.329 |
| `[4..11]` 前台 | `affinity-exact result=0` | `affinity-exact result=1` |

我方逐组试过：`0-3`、`4-7`、`0-5` 精确生效；凡含 CPU 编号 ≥8 的一律读回不一致。
**更新的系统放开了大核绑定。**

**结论：保持现配置。** 但绑核不是跨机型/跨版本可移植的能力——换机型或系统升级后，请抓一次亮屏
会话的 `AmphionScheduling` 日志确认 `affinity-exact result=1`；若为 `0`，退回 `[4,5,6,7]`。
亮屏下两者实测差异只有 ASR 滞后 20 ms 对 40 ms，都远低于可感知。

**熄屏场景下这个参数填什么都没用**：系统已把全部线程压进小核，请求小核只是重合、请求大核则
交集为空直接 `EINVAL`。我方实测绑 `0-3` 与完全不绑核的锁屏期实时率一字不差（0.712× 对
0.712×/0.715×）。

## 四、锁屏变慢：请把基线从 0.80× 换掉

你们 10-14 测得的 0.80×、以及 10-15 报告第四节沿用的那个数字，是在我方 **10-13 被 diagnostics
构建污染**的包上测出来的。该污染值我方已量化：

| 协议 | 构建 | 锁屏期实时率 |
|---|---|---|
| 140 s（锁 80 s） | diagnostics（= 10-13 那版） | ≤ 0.631× |
| 140 s（锁 80 s） | **debug（干净包）** | **0.856×** |
| 220 s（锁 160 s） | debug（干净包） | **0.866×** |

**诊断日志开销 ≥ 0.22× 实时率。** 干净包真实缺口 **0.134×**，不是 0.20×。进一步拆开（同为
干净包、受控对照）：角色分离链全部代价 **0.091×**、ASR 主链路自身欠缺 **0.043×**——
**即使把角色分离整个关掉也只到 0.957×。**

**该问题本版未解决**，方向结论不变（SDK 侧仅靠角色分离优化补不上缺口），但请在后续报告和向
平台方的诉求里改用干净包的数字，否则对方复现不出来。你们 10-15 报告的"前台 ＞ 亮屏后台 ＞
锁屏"排序推论方向没问题，只是绝对值要换。

顺带一条措辞更正：你们报告 3.2 节把 `affinity-set result=0` 注为"宽松绑核失败"——`result=0`
是 `sched_setaffinity` 返回 0 即**成功**，失败是 `result=22`（EINVAL）。你们后面的判断逻辑表
写对了，只是那一行注释反了。

## 五、关于 10-15 晚长时验证里的发热：我方按日志3 的原始数据复核

先说结论：**这次的热不是熄屏推理烧出来的，也没有发生温控降频。** 以下全部出自你们
`日志3` 的一手数据（`thermal-timeline.txt` 61 个 60 秒粒度块、`功耗快照.csv` 8 个时点、
`cpuset-timeline.txt` 724 条），不引用报告里的二手结论。

### 5.1 热确实出现了，但出现在屏幕亮起之后

后壳温度（`tz shell_back`）全程曲线：

| 时段 | 时长 | 后壳温度 | 速率 |
|---|---|---|---|
| 锁屏推理 19:49→20:30 | 43 min | 33.4 → 36.2 °C | **+0.065 °C/min** |
| 亮屏（后台 + 前台）20:30→20:51 | 20 min | 36.2 → **43.6 °C** | **+0.37 °C/min** |

**熄屏持续推理的热学代价是亮屏的六分之一。** 这一条你们的报告是对的，而且是本轮最有价值的
发现——它和 10-14 "建议保持亮屏规避" 的旧结论方向相反。

### 5.2 「热等级 0→4」不是内核温控，而且本次没有降频

两点需要更正，否则向平台方提诉求时会被直接驳回：

1. **内核的 shell 温控档位 `tz shell_level` 全程为 0**，一次都没有抬过。报告里 0→1→2→3→4 的
   那条时间线来自 `com.ohos.sceneboard / OverflowViewModel: Thermal Level changed, current
   mode: N`——那是**桌面（launcher）的 UI 档位**，用来驱动界面提示，不等同于内核温控介入。
2. **本次会话没有观察到调频上限被压低。** 亮屏段实测最高频 **1997 MHz**，反而高于锁屏段的
   1210~1805 MHz。如果温控真的在压频，最高频应当被削顶，而不是升高。

所以"热等级跳到 4 并触发降频，拖累识别滞后到 115s"这条因果链，**在这份日志里找不到支撑**。

### 5.3 那么进程 CPU 从 197% 掉到 143% 是怎么回事

不是降频，更像是**争抢**。同一组快照里整机 CPU 占用是：

| 时点 | 阶段 | 整机占用 | 我方进程 CPU | 最高频 |
|---|---|---|---|---|
| t20 | 锁屏 17min | 28.1% | 190.6% | 1210 |
| t30 | 锁屏 27min | 28.1% | **196.7%** | 1600 |
| t40 | 锁屏 37min | 29.3% | 193.5% | 1600 |
| t50 | 亮屏后台 7min | **40.9%** | 178.6% | **1997** |
| t60 | 亮屏后台 17min | **60.3%** | 160.8% | 1556 |
| tend | 停止后 | **61.3%** | 143.3% | 1671 |

屏幕点亮后整机占用翻了一倍多（28% → 61%），我方进程拿到的份额相应被压缩。多出来的那部分
负载不是我们产生的——我方进程 CPU 在下降，整机在上升。

**这指向一个豁免没有覆盖到的面：** 豁免改的是 `cpuset`（**能用哪些核**），进程因此不再被关进
小核。但它不改 `cpu.shares` / 权重（**在竞争时能拿到多少**）。`system-default` 的权重低于
`top-app`，整机轻载时完全看不出来（锁屏段 28% 负载下你们实测 ≈0.98×），一旦整机到 61%
就会吃亏。这解释了为什么"亮屏后台"反而比"锁屏"差——**不是热，是权重 + 竞争。**

请向平台方确认 `system-default` 与 `top-app` 两个组的 `cpu.shares`（或 `cpu.weight`）取值。
如果确实差一档，那么长会议场景更该引导**锁屏**而不是"亮屏但切到别的应用"。

### 5.4 我方自己要认的那一份：角色分离的成本随会议时长增长

你们锁屏段有一个现象值得单独拎出来：**20 分钟后 lag 开始爬升的同时，我方进程 CPU 在上升
（190.6% → 196.7%），不是下降。** 算力被限会让 CPU 占用下降；这里反过来，说明是"同样一秒
音频要做的活变多了"。

这一条我方已定位到自己的代码：角色分离**每次提交都会把整场会议从第 0 秒重新聚类一遍**，
该成本随会议时长增长（预览路径有自限流，提交路径没有）。它同时解释三件事——
0.98× 那 1.4 s/min 的欠账、CPU 占用的缓慢上升、以及下面 5.5 的内存增长。

因此 **1.4 s/min 不能线性外推到更长的会议**：窗口数翻倍、聚类代价按超线性增长。在把"长时锁屏
可用"写进结论前，**建议先跑一轮 2 小时**。我方正在做提交侧的限流 / 增量聚类，修好后这部分的
吞吐欠账与发热会同时下降。

**在我方修复落地之前，你们可以先用的缓解手段**：调大角色分离的提交周期（提交次数减半 ≈
全量重聚类的总开销减半），代价是出字的发布延迟变大。需要的话我方给具体配置项。

### 5.5 比发热更硬的一个限制：内存，你们报告里没有提

`功耗快照.csv` 的 `app_mem_kb` 全程单调上升：

| 时点 | t10 | t20 | t30 | t40 | t50 | t60 | tend（停止后） |
|---|---|---|---|---|---|---|---|
| 进程内存 | 645 MB | 707 MB | 736 MB | 789 MB | 865 MB | **949 MB** | 848 MB |
| 每 10 分钟增量 | — | +62 | +28 | +53 | +76 | **+85** | 会话停止后回落 |

50 分钟涨了 **297 MB（约 5.9 MB/min），而且增量本身在变大**。会话停止后回落，说明是会话内
累积的状态、不是永久泄漏——但这正是 5.4 那个机制的副作用：每次提交都要把整场会议的证据
前缀读进内存，读进来的量随会议时长线性增长。

**按这个斜率外推，2 小时会议进程内存约 1.3 GB。** 这比发热更可能先成为长会议的硬上限
（系统内存压力、后台被回收）。建议你们下一轮长测把 `app_mem_kb` 一起采上，这是目前唯一
没人盯的指标。

### 5.6 本轮没有测到的：耗电

全程 USB 在线、电量 100%、充电状态 `Full`，电池电流是 µA 级（-2 ~ -683 µA）、功率 <3 mW——
**这等于耗电没有测。** 而 `key-background` 这个调度域存在的唯一理由就是省电，平台方要不要把
豁免放进量产版本，看的就是这个数。

建议补一轮：**拔掉 USB、从 80% 电量起跑同样协议的 1 小时**，报电量下降百分比与平均功率，
并与"不开会话待机 1 小时"做对照。这是整件事里最可能卡住量产的一关，现在是空白。

## 六、两条会直接改善用户感受的产品侧建议

**1. 锁屏录制时"点亮屏幕"不够，必须解锁。**
实测仅点亮时进程仍在受限调度组，排空速率只有 **0.618×**；滑动解锁后才回到 **1.550×**。
用户按一下电源键看一眼，文字不会追上来，反而更像卡死。若有"锁屏识别中"的提示，应当明确引导
**解锁**而不是"点亮看看"。

**2. 停录时必须等排空，不能固定超时就拆引擎。**
实测在积压 133 秒时停止录音、30 秒后拆除会话，最终文本 **1869 字**，而同一段音频正常应为
**2199 字**，**少 15%**。丢的是时间不是识别能力。建议停录后显示"正在转写剩余 N 秒"，
按实测 1.2× 的排空速率估算等待。

### 一处包内源码的小缺陷（不影响 SDK 本身，只影响编译包内 Demo 源码）
