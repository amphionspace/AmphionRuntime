# 构建模式对照：diagnostics vs debug（2026-10-14）

回答的问题：贵方 10-14 测出的锁屏 0.80× 里，有多少是我方把诊断模块编进正式 SDK 造成的？

## 方法：标定墙钟法

非诊断包没有逐回调事件流，无法像主矩阵那样直接读取进度曲线，因此改用墙钟标定：

```
墙钟总时长 = T0 偏移 + 音频时长 + 结束时的积压 + 载体收尾开销
```

同一构建先跑一场**全程亮屏**（积压 ≈ 0）标定出「T0 偏移 + 收尾开销」，再跑一场**熄屏**，
两者墙钟之差即为熄屏结束时的积压：

```
锁屏期实时率 = 1 − 积压 / 锁屏时长
```

两场除屏幕状态外完全相同，标定常数因此抵消。每个构建用自己的亮屏场标定（收尾开销随构建不同）。

## 场次与结果

全部为：`--cpu-ids none`、角色分离开（除 C6/C7）、`pace 20 ms`、`hop 2000`、
`numThreads 4`、`qos user-initiated`、同一段客户原始录音的前 N 秒、每场冷进程启动并降温到同一阈值。

| 场次 | 构建 | 音频 | 屏幕 | 墙钟 | 积压 | 锁屏期实时率 |
|---|---|---|---|---|---|---|
| D1 | diagnostics | 140 s | 亮屏 | 151.9 s | （标定） | — |
| D2 | diagnostics | 140 s | 熄屏 @60 s | 181.4 s | 29.5 s | **≤ 0.631×** |
| C1 | **debug** | 140 s | 亮屏 | 150.2 s | （标定） | — |
| C2 | **debug** | 140 s | 熄屏 @60 s | 161.7 s | 11.6 s | **0.856×** |
| C3 | **debug** | 220 s | 亮屏 | 229.9 s | （标定） | — |
| C4 | **debug** | 220 s | 熄屏 @60 s | 251.2 s | 21.4 s | **0.866×** |
| C6 | **debug**，**关角色分离** | 220 s | 亮屏 | 229.1 s | （标定） | — |
| C7 | **debug**，**关角色分离** | 220 s | 熄屏 @60 s | 236.0 s | 6.9 s | **0.957×** |
| C5 | **debug** | 523.7 s | 熄屏 @60 s，400 s 解锁 | **534.8 s** | ≈0 | 端到端对照，见下 |

> **D2 的 0.631× 是上界**：它撞上测试载体 `COMPLETE_TIMEOUT_MS = 30000`，`finish()` 后 30 s
> 被强制拆除，final 少一条、文本 613 字（其余三场 620 字）。真实积压 ≥29.5 s，
> 所以诊断开销 0.22× 是**下限**。

## 三个结论

**1. 诊断构建开销 ≥ 0.22× 实时率**（140 s 同协议：0.631× → 0.856×）。
来源是开启角色分离时每次 `writeAudio` 多打 2 条诊断事件 —— 20 ms 分片即约 105 条 hilog/秒，
全部落在那 4 个小核上。事件量实测：523 s 会话 55 241 条（开分离）对 1 363 条（关分离）。

**2. 干净包的缺口是 0.134×，其中角色分离只占 0.091×**：

```
干净包锁屏期（角色分离开，C4）   0.866×
干净包锁屏期（角色分离关，C7）   0.957×
──────────────────────────────────────
角色分离链的全部代价              0.091×
ASR 主链路自身的欠缺              0.043×
合计缺口                          0.134×
```

即**把角色分离整个关掉也只到 0.957×**，角色分离侧所有优化的收益上限小于缺口。

**3. 长协议端到端同向**（523.7 s，锁 60–400 s 后解锁，与主矩阵 B3/B3b 完全同条件）：

| 构建 | 总墙钟 | 识别文本 | 判定 |
|---|---|---|---|
| diagnostics（B3 / B3b） | 561.9 s / 561.9 s | 2199 字 | PASS |
| **debug（C5）** | **534.8 s** | 2199 字 | PASS |

干净包快 27.1 s，且其自身亮屏基准约 533.6 s，说明 C5 结束时积压已排空。
**所有跑完的场次识别文本都是 2199 字、逐字节一致 —— 构建模式只影响时延，不影响识别质量。**

## 怎么复现

干净包的构建（仅构建不安装，不改动仓库文件）：

```bash
NODE_ADDON_API_CACHE=<repo>/.cache/node-addon-api-c679f6f4 \
NODE_ADDON_API_PREPATCHED=<repo>/.cache/node-addon-api-c679f6f4-patched \
bash 绑核矩阵-20261014/build_only_debug.sh \
  --build-mode debug \
  --signing-config <repo>/.cache/speaker-screen-repro-acf477c2/local-signing.json
```

`build_only_debug.sh` 是仓库 `delivery/harmony-dingqiao/delivery/build_install_smoke.sh` 的副本，
两处改动：(a) 安装步骤前截断；(b) 支持 `NODE_ADDON_API_PREPATCHED`，把 node-addon-api 指向
预打补丁的本地源（`FETCHCONTENT_SOURCE_DIR_NODE_ADDON_API`），跳过 git 下载 —— debug 模式下
脚本默认的 node-addon-api 缓存路径不存在，CMake 会去联网 clone 并在交叉编译上下文里报
`GIT_VERSION_STRING=''` 失败。

跑测（以 C4 为例）：

```bash
python3 .cache/core-domain-matrix-20261014/run_scenario.py \
  --name C4 --out <out> --data-dir <220s 语料目录> --audio-seconds 220 \
  --cpu-ids none --no-capture-diagnostics --screen off --suspend-after 60 --no-wake
```

非诊断包必须加 `--no-capture-diagnostics`，否则载体会把诊断采集判为 ERROR。
关角色分离再加 `--no-diarization`。

## 限制

- 墙钟法的分辨率：1 s 墙钟 ≈ 0.0125× 实时率（80 s 锁屏）/ 0.00625×（160 s 锁屏）。
- 每个配置只跑一轮；140 s 与 220 s 两个协议给出的干净包数字（0.856× / 0.866×）相差 0.01×，
  可作为重复性的粗略参考。
- 所有锁屏场的锁定窗口都选得使积压 < 30 s，以免撞上载体的 complete 超时 —— D2 是唯一的例外，
  它的数值因此只是上界。
- 签名用的是 `~/.ohos/config/default_signing-project_k5KeK…`（bundle `com.amphion.asr.harmony.demo`、
  app-identifier 与现装包一致、含本机 UDID、有效期至 2027-09-30）。
  仓库 `.secure/signing/asr-demo/` 那套证书与 profile 已于 2026-09-15 过期。
